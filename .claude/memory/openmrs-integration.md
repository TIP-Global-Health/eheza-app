TIP/UVL Burundi partnership initiative: push E-Heza patient registrations into UVL's OpenMRS, with OpenFN as the interoperability mediator. Phase 1 is a one-way patient **create** flow PoC: patient created in E-Heza (Drupal 7 backend) → OpenFN → OpenMRS (run locally via Docker initially — no spec for UVL's real instance yet).

**Why:** next step in the TIP/UVL digital-tools ecosystem. OCL is the shared vocabulary contract layer — see [[ocl-pih-mappings]].

**How to apply:** when doing OpenMRS / OpenFN integration work in this repo, this is the active initiative. Branch `openmrs-patient-poc` (off `docs/ocl-pih-mappings`). Issue: `Gizra/ihangane#3236` (private repo; the issue tracker is `Gizra/ihangane`, code/PRs are `TIP-Global-Health/eheza-app`).

Key architecture decisions (settled with the user):
- Target = OpenMRS **REST** `POST /ws/rest/v1/patient`, **not FHIR** — REST is core/always-present (FHIR2 is an optional module of unknown coverage); REST handles `PersonAttribute`s natively; OpenFN has a dedicated `openmrs` adaptor.
- OpenFN runs **locally (Lightning)** — a cloud OpenFN cannot reach a localhost OpenMRS.
- Registration data transfers **structurally** (Patient/Person fields, identifiers, PersonAttributes), NOT concept-coded. The OCL/CIEL/PIH/UVL concept mappings are the Phase 2 (clinical observations) contract, not on the registration flow's critical path. Confirmed by checking: UVL's published dictionary has zero registration concepts — OpenMRS models demographics structurally.
- All OpenMRS-side UUIDs kept as job config so the local→UVL switch is config-only.
- Scope: one-way create only (plus a UUID write-back to avoid duplicates); no back-sync.

Branch `openmrs-patient-poc`. Drupal trigger (#9), the three OpenFN jobs transform/match/load (#12–#14, `integration/openfn/jobs/*.js`, 31 unit tests + live smokes), and the Lightning workflow (`project.yaml` deployed). `integration/openfn/README.md` is the provisioning runbook; `integration/*.md` are the design docs.

**#15 end-to-end verified.** A real E-Heza person flows queue → webhook → all three jobs → an OpenMRS patient with the national-ID identifier, UUID written back to the person node.

Lightning credential quirks worth remembering (now documented in the README):
- Lightning v2.x credentials are **per-environment**. A project with `env=nil` is labelled `unknown`; the credential's env must match or runs fail with `CredentialLoadError`. Adding an env via the UI creates a new empty `credential_body` row that needs the body filled in.
- The workflow-editor *Save* (not the per-step modal *Close*) is what cuts a fresh snapshot — runs created before that save use the older snapshot and ignore the credential. Direct DB attachment via `update_all` does **not** cut a snapshot.

Local-env gotchas: OpenMRS has no idgen source and almost no demo patients. The local Lightning login and the Drupal shared secret stay out of the repo — ask the user.

## Phase 2 — prenatal encounter transfer (2026-06-01)

Branch `openmrs-prenatal-encounter-poc` (off `openmrs-patient-poc`), **PR #1766** (base = `openmrs-patient-poc`, stacked on Phase 1's #1763). Design spec + plan under `docs/superpowers/specs|plans/2026-06-01-openmrs-prenatal-encounter-*`.

Still **generic / no-OCL** (UVL's custom OpenMRS dictionary still unavailable). One prenatal encounter → one OpenMRS `Encounter` + one obs per measurement field. Decisions (settled with user): self-provisioned concept-per-field (placeholder UUIDs, swap to UVL later — like Phase 1); scope = **everything** (all bundles carrying `field_prenatal_encounter`); coded/multi-select fields stored as **Text** obs (multi-selects comma-joined), not true coded concepts.

Key implementation facts:
- Catalog `integration/openmrs/prenatal-concept-catalog.json` (226 rows) is generated by drush `hedley-openmrs-build-prenatal-catalog`, which derives bundles from `field_info_field('field_prenatal_encounter')['bundles']['node']` (48 bundles) — NOT a hardcoded list (a hardcoded 31-list caused a coverage gap, fixed in final review). `provision.py` creates one concept per row.
- Measurement keys are namespaced `<bundle>.<field>` (bare field names collided across bundles — `test_result`/`execution_date`/`date_measured` on many bundles — silently dropping obs; fixed in final review). Each (bundle,field) = its own concept.
- Drupal side in `hedley_openmrs`: `field_openmrs_encounter_uuid` on `prenatal_encounter`; queue task + node hooks; `hedley_openmrs_build_prenatal_payload` (skips soft-deleted measurements, comma-joins multi-value via `_hedley_openmrs_field_joined`); worker; `openmrs/encounter-link` write-back endpoint (clone of `patient-link`). Encounter waits for its person: worker returns `FAILURE_RETRY` until `field_openmrs_uuid` is set.
- OpenFN jobs `transform-encounter.js` / `match-encounter.js` (create-once) / `load-encounter.js`; `prenatal-encounter` workflow in `project.yaml`. load-encounter mirrors `load.js` config keys (`openmrsBaseUrl`/`ehezaEncounterLinkUrl`/`ehezaToken`/`openmrsAuth`). Tests run with `node --test integration/openfn/jobs/*.test.js` (54 total).
- Deferred: re-sync/update of an existing encounter, true coded obs w/ answer concepts, obs groups, live OpenFN config + full e2e.

### Phase 2 validated end-to-end (2026-06-03) + setup gotchas

Full chain proven locally: prenatal e2e test (`client/e2e/prenatal-encounter-nurse.spec.ts`, the "complete all activities" test — registers a fresh person) → sync → AQ → OpenFN → **OpenMRS patient + prenatal encounter with 113 concept-coded obs**; upsert/replace works (encounter UUID rolls each run, old voided). Drive the AQ manually in dev (no cron): `ddev drush advancedqueue-process-queue hedley_openmrs_push_person` then `..._push_prenatal_encounter` (or invoke the worker directly: `hedley_openmrs_push_prenatal_encounter_worker((object)['data'=>['encounter_id'=>NID]])`). Person must link first (worker FAILURE_RETRYs otherwise).

Gotchas that cost hours (all now in `integration/openfn/README.md`):
- **`openfn deploy` (CLI) drops every UI-set credential attachment** (project.yaml has `credential: null`). Re-attach + Save all steps after each deploy, else runs get empty `state.configuration` → transform emits 0 obs.
- **`transform-encounter` needs the `@openfn/language-http` adaptor** (not language-common) so Lightning can attach the credential carrying `prenatalConcepts`/`encounterType`/`location`. It does no HTTP.
- **`prenatalConcepts` in the credential must be a single JSON *string*** — Raw JSON credentials cap sensitive keys at 50; the map has 200+. The job `JSON.parse`s it (accepts object too).
- **Per-environment credential bodies must match.** Lightning keeps one body per env (`main`, `unknown`); a run resolving an env whose body lacks the concepts → 0 obs. Keep them identical. (`credential_id` on `steps` is NOT a reliable "had config" signal.)
- **Numeric concepts need `allowDecimal=true`** or OpenMRS rejects decimal obs (`Obs.error.precision`). `provision.py` now sets it + creates the `E-Heza Prenatal` encounter type.
- **No `provider` in the credential** — encounterProviders without an `encounterRole` violates `encounter_provider.encounter_role_id` NOT NULL. Flow omits providers.
- Lightning run errors live in postgres (`openfn-poc-postgres-1`, db `lightning`): `steps.exit_reason`/`error_type`, `log_lines.message`; the run inspector UI redacts credential values. Debug local-env values (idgen, encounter type, providers) gotcha: load.js self-computes the OpenMRS-ID (`luhnOpenmrsId`), so idgen sources are NOT needed.
