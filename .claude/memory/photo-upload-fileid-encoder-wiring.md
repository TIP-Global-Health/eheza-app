In the E-Heza Elm client, a synced entity's photo is uploaded **first** (its own `SyncUploadPhoto` phase, which gets a backend `fileId`), and only then is the owning node encoded for upload with that `fileId` substituted into its image field. The substitution happens in **`client/src/elm/SyncManager/Encoder.elm`**:

- Helper **`replacePhotoWithFileId localId imageField encodedEntity`** (~lines 85-97): looks the photo up by localId in `record.uploadPhotos` (joined in JS at `app.js` ~1033-1044) and overwrites `imageField` with `maybe int row.fileId`, `Maybe.withDefault null`. It's **one-shot at node-encode time** — nothing ever re-points an already-uploaded node to a later-uploaded photo, and a missing fileId encodes the image field as **`null`** (orphaned photo).
- The per-entity dispatch is the `case entity of` inside **`encodeIndexDbQueryUploadAuthorityResultRecord`** (~lines 110-165). Each photo-bearing type has an explicit branch calling `doEncode <itsEncoder> identifier_ "<imageField>"` (or, for Person, a conditional `replacePhotoWithFileId ... "photo"` gated on `avatarUrl`). Current branches: `BackendAuthorityPerson` ("photo"), `BackendAuthorityPhoto`, `BackendAuthorityNutritionPhoto`, `BackendAuthorityPrenatalPhoto`, `BackendAuthorityWellChildPhoto`, `BackendAuthorityFamilyNutritionPhoto` (all "photo"), and `BackendAuthorityStockUpdate` ("**signature**"). Everything else hits `_ -> SyncManager.Utils.encodeBackendAuthorityEntity entity`.

**THE RULE — when introducing a new authority content type that carries an uploaded photo/image/signature, you MUST add a `case` branch for it here** (mirror the existing photo types: `doEncode <newEncoder> identifier_ "<imageFieldName>"`). If you don't, it falls through to the generic `_ ->` branch, which does **not** call `replacePhotoWithFileId` — so the node uploads with the *local* photo URL (or null) instead of the backend `fileId`, and the photo is silently never linked. Easy to miss: the new type compiles and syncs fine for everything except the photo link.

**SECOND dispatch — the DOWNLOAD side (found Round 6, R6-3).** There is a *parallel* per-type dispatch that must ALSO list every photo-bearing type: **`getImageFromBackendAuthorityEntity`** in **`client/src/elm/SyncManager/Utils.elm`** (~lines 1069-1093). On every downloaded authority entity (folded through it in `SyncManager/Update.elm` ~236-256), a `Just url` result schedules that image to be fetched into the local `"photos"` Cache-Storage (a `deferredPhotos` row); everything not listed falls through `_ -> Nothing` and is **never proactively cached**. When such a photo is later viewed on that device, the service worker has no cached copy and the in-app URL carries no `access_token`, so `photos.js` returns 404 → permanently broken photo on secondary devices (the uploader's own device still shows it from its local capture). R6-3 caught `BackendAuthorityWellChildPhoto` missing here even though it was present in the upload dispatch — proving the two lists drift independently. **So the RULE is really: add the new photo type to BOTH dispatches (upload `replacePhotoWithFileId` AND download `getImageFromBackendAuthorityEntity`), plus `backendAuthorityEntityToRevision`.** Mirror an existing photo type: download branch is `BackendAuthority<X>Photo identifier -> getImageFromMeasurement identifier` (keep alphabetical order).

Why the blocking matters (do NOT "unblock" it): the photos-before-nodes ordering is the load-bearing invariant that guarantees nodes point at real files. Upload failures in 8+ years of production are transient (network / temp 5xx) and self-resolve; the lane "wedge" is theoretical. See [[code-review-improvement-ledger]] (Round-3 "photo-upload incident loop" — examined and REJECTED for exactly this reason).
