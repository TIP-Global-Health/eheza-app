Two failures hit during the 2026-06-21 `develop` → `nutrition` multidev deploy (rwanda/ihangane). Both recur on any deploy, so fix them up front.

**1. Dirty-tree abort from lock-file churn.** Every `ddev restart` runs the `post-start` hook `ddev client-install`, which re-resolves deps and rewrites `client/package-lock.json` + `client/yarn.lock` (different npm/yarn version than what generated the committed locks). That dirties the tree, and `ddev robo deploy:pantheon` aborts with *"The GitHub working directory is dirty."* Discarding them fixes one run, not the next. **Durable fix:** `git update-index --skip-worktree client/package-lock.json client/yarn.lock` (local-only, reversible with `--no-skip-worktree`, verify with `git ls-files -v` → leading `S`). The locks aren't in the deploy payload anyway (only `client/dist/` is rsynced), so zero effect on what ships.

**2. Orphaned-module `cc all` crash (Exit 137) post-deploy.** The env's DB (cloned from prod) has modules enabled that newer code no longer ships, so post-deploy `cc all` hits *"module missing from the file system"* and gets SIGKILLed (137), leaving `updb`/`fra`/`uli` un-run — a half-deploy. Seen this run: `admin_views_system_display` (dropped by the `admin_views` 1.7 contrib build — only that submodule went; `admin_views`/`admin_menu` themselves stayed) and `hedley_pusher` (a long-removed module; `.ddev/config.local.yaml`'s `post-import-db` hook already deletes its row locally — same orphan, just on the remote env). **Fix (documented at drupal.org/node/2487215):** `terminus remote:drush <site>.<env> -- sql-query "DELETE FROM system WHERE name = '<module>'"` then re-run the stack `cc all` ×2, `updb -y`, `fra -y`, `cc all`, `uli`. DB writes work even though the env warns "read-only Git mode" (that only blocks codebase/SFTP writes, not the DB). When this reaches production the same orphan cleanup will be needed.

**2b. Exit 137 can ALSO be a transient OOM that FALSELY reports real modules "missing" — do NOT delete those rows.** On the 2026-06-21 `develop` → vhw `training` deploy (a large delta), the chained post-deploy `cc all && cc all && updb && fra && cc all && uli` ExecStack got SIGKILLed (137) mid-rebuild, drowning in thousands of stale `ctools` `include_once` failures (restful `.inc` plugins moved into subdirs) and flagging `hedley_group_education`/`hedley_hiv`/`hedley_reports`/`hedley_tuberculosis` as "missing from the file system." These are **real, present modules** (verified: they exist in `develop`'s `server/hedley`, the env's `system.filename` points at the correct path, and the files were tracked in the pushed clone) — the warning was just the half-cleared registry under memory pressure. **Before deleting any `system` row, verify the module is genuinely absent from `develop` (`find server/hedley/modules -name '<m>.info'`) and from the pushed clone (`git -C server/.pantheon-<name> ls-files .../<m>.module`).** Deleting a real module's row would disable live functionality. **Recovery for the OOM:** re-run each post-deploy step as its OWN command (`terminus remote:drush <site>.<env> -- cc all`, then `updb -y`, then `fra -y`, then `cc all`, then `uli`) — a single `cc all` in a fresh full-memory process succeeds where the chained stack OOMed. Genuine orphans (nutrition's `admin_views_system_display`/`hedley_pusher`) vs. false-positive OOM (training's hedley_* modules) are distinguished by that develop+clone existence check. ⚠ **The per-step re-run is now the tooling's own job** (PR #2130, branch `deploy-sync-step-retry`, targets `main`): `deployPantheonSync()` no longer chains the six steps in one `taskExecStack` — each runs through `drushOnPantheon()` with 3 attempts and a 15s/30s backoff, so one transient kill no longer abandons the rest. Once that is merged, a deploy that still reports a failed step has failed it 3 times; hand-running it a fourth time is unlikely to help. ⚠ **`updb -y` is the exception to the retry-is-safe rule** — verified at `includes/update.inc:1007-1010`: the schema version is written only when `$context['finished'] == 1 && empty($ret['#abort'])`, so a hook killed mid-execution is never recorded and any retry re-runs it from the top, on D7 hooks that are not idempotent. Check which updates ran before re-running `updb`. **Fastest triage: grep the deploy log for `missing from the file system` first.** If the chained ExecStack died 137 with *zero* such lines (seen 2026-08-22, `main` → ihangane `qa`), it is purely OOM — skip the existence checks and go straight to the per-step re-run; every step then passes (`cc all`, `updb -y` applying `hedley_update_7048`/`hedley_admin_update_7003`, `fra -y` "already matches defaults", `cc all`, `uli`).

**2c. The `updb` exit-137 seen all through the 2026-08-23 vhw deploys is safe to retry — those two hooks are effect-idempotent.** `hedley_update_7048` (`server/hedley/hedley.install`) is just `module_disable(['logs_rollbar'])`, `module_enable(['logs_glitchtip'])`, `variable_del('logs_rollbar_enabled')`, `variable_del('logs_rollbar_rollbar_access_token')`; `hedley_admin_update_7003` is `variable_del('hedley_admin_report_email')` + `menu_rebuild()`. Disabling an already-disabled module, enabling an already-enabled one, and deleting an absent variable are all no-ops, so a kill at any point followed by a retry converges. **The kill is caused by the `module_enable` of `logs_glitchtip`** — enabling a brand-new module forces a registry rebuild, which is the memory spike. Two shapes seen the same day: on vhw **dev** the kill landed *after* both `Performed update ... [ok]` lines (post-update cache flush) and the retry said "No database updates required"; on vhw **qa** it landed *before* any `Performed update` line and the retry ran both hooks from the top. Both ended correct — verified on qa: `logs_rollbar` status 0 / schema -1, `logs_glitchtip` status 1 / schema 0, `hedley` at 7048, `hedley_admin` at 7003, no `logs_rollbar%` variables left, `hedley_admin_report_email` gone. **Generalize the check, not the verdict:** read the hook bodies before accepting any retried `updb`, since the recorded-only-on-completion rule still holds for hooks that aren't idempotent.

**3. A `ddev restart` can drop the terminus session — the preflight auth check runs BEFORE it, so re-verify after.** Both deploy skills check `terminus auth:whoami` in preflight and *then* restart ddev, so a green check is stale by the time the deploy runs. The session does not always survive: on the 2026-08-23 vhw production release the post-restart `whoami` returned *"You are not logged in"*, while the vhw `qa` multidev deploy an hour later (same day, same containers) stayed logged in across its restart. `TERMINUS_MACHINE_TOKEN` in `.ddev/config.local.yaml` enables `ddev terminus-auth`; it does **not** auto-login on boot. So: after every restart run `ddev exec terminus auth:whoami`, and if it says not logged in, `ddev terminus-auth` (fixes it in seconds). Skipping this means the deploy pushes code and then fails every `remote:drush`, leaving the env on new code with a stale cache/registry.

**Root `/` returning 403 on a Pantheon env is normal, not a broken deploy.** The Elm client is rsynced to `<clone>/app`, so the app is at **`/app/`** — smoke-test that, not `/`. Good check: `curl -o /dev/null -w '%{http_code} %{size_download}'` on `/app/Main.js` and compare the byte size to the local `client/dist/Main.js`; identical sizes across dev/test/live prove the same build shipped everywhere.

**One-time clone if the site was never deployed locally.** vhw had no `server/.pantheon-vhw` clone. The host already has Pantheon SSH access (test: `git -C server/.pantheon-ihangane ls-remote origin`), so clone host-side from `server/` with the vhw URL in `_deploy-common/deploy-reference.md` (`-b master`), then `git fetch && git checkout <env-branch>`. Also remember to flip `.ddev/config.local.yaml` to the target site (`EHEZA_SITE`/`PANTHEON_NAME`) and `ddev restart` so the in-container `PANTHEON_NAME` matches (verify: `ddev exec bash -c 'echo $PANTHEON_NAME'`) — wrong value pushes to the wrong Pantheon site.

Also note (non-blocking): `fra` on a DB with data warns *"A list field (field_treatment_ongoing / field_prenatal_diagnoses) with existing data cannot have its keys changed"* — Features can't rekey a populated list field, so that one property stays; the rest reverts `[ok]`, and the overridden-feature count still ends at 0. Not a deploy failure.

The huge "deleted:" list in the deploy's `git status` was a **false alarm** — the commit summary showed them as 100% **renames** (hedley_restful plugin classes reorganized from `node/` into `node/{sync,reference,report,session,activity,encounter,misc,participant}/`). Read the commit-summary tail before panicking.
