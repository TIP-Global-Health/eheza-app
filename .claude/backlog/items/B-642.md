### B-642 — Acute Illness and every other encounter record: a change saved while a sync cycle is between its upload and its download is undone when the device downloads its own earlier upload; the next save of that record then erases the change on the server — a closed Acute Illness encounter can end up stored with no diagnosis — READY · CONFIRMED by reading (orchestrator read the download save, the revision hand-off, the encounter revision arm, the diagnosis writer, the close writer, the encoder and the diagnosis derivation; nothing run, the timing was not observed) · MED-LOW · tier 2, same as B-496 · ⚠ user to decide whether the tier-1 rule applies, as on B-496 · R71 unit 2 · DEPLOYED · all sites · expected rare, not sized
- **What it is.** The clinical-record half of B-634's "Wider, NOT traced" note. Same stored result as B-496 (a diagnosis the device showed is stored as none), by a different route that B-496's fix (#2377) does not touch.
- **Not B-496, not B-524.** B-496 was the device's own save not being assessed during a download; here the save is assessed and written, then undone. B-524 needs a second writer; this is one device.
- **Mechanism.** The Authority download writes each server row over the local row, with no check for a queued change of the same uuid:
  ```js
  // client/src/js/app.js:644-647, 665
      case 'Authority':
        table = dbSync.shards;
        break;
  ...
    table.bulkPut(entities)
  ```
  The same batch replaces the record in memory:
  ```elm
  -- client/src/elm/SyncManager/Update.elm:309-310
                              appMsgs =
                                  [ handleNewRevisionsMsg backendAuthorityEntityToRevision data.entities ]
  -- client/src/elm/Backend/Update.elm:5264-5269
          encounterActionConsideringDeletedField uuid data =
              if data.deleted then
                  Dict.remove uuid

              else
                  Dict.update uuid (Maybe.map (always (Success data)))
  ```
  The server returns every revision above the cursor, the device's own uploads included (`HedleyRestfulSync.class.php` `getForHealthCenter`, `node.vid > base`; scout-read, not re-read by the orchestrator). Every encounter change is a whole-record PATCH built from the copy in memory:
  ```elm
  -- client/src/elm/Backend/AcuteIllnessEncounter/Update.elm:28-32, 361-367
          CloseAcuteIllnessEncounter ->
              updateEncounter encounterId maybeEncounter (\encounter -> { encounter | endDate = Just currentDate }) model

          SetAcuteIllnessDiagnosis diagnosis ->
              updateEncounter encounterId maybeEncounter (\encounter -> { encounter | diagnosis = diagnosis }) model
  ...
                  , updateFunc encounter
                      |> sw.patchFull acuteIllnessEncounterEndpoint encounterId
  -- client/src/elm/Backend/AcuteIllnessEncounter/Encoder.elm:26
      , ( "acute_illness_diagnosis", encodeAcuteIllnessDiagnosis encounter.diagnosis )
  ```
- **Sequence, one device.** (1) A cycle uploads the encounter as created (no diagnosis). (2) After the upload lane's last empty read and before the download reaches that row, the nurse saves the measurement that decides the diagnosis; the diagnosis PATCH is queued. (3) The download hands back the encounter as created; row and memory lose the diagnosis. (4) The nurse ends the encounter; that PATCH is built from the reverted copy. The server applies both in order and keeps a closed encounter with no diagnosis.
- **Why nothing on the device repairs it.** The screen takes the diagnosis from the measurements, so it still shows; the writer fires only when the measurement-derived diagnosis *changes*, so later saves do not write it again:
  ```elm
  -- client/src/elm/Backend/Update.elm (generateSuspectedDiagnosisMsgsFirstEncounter)
      if diagnosisBeforeChange /= diagnosisAfterChange then
          case diagnosisAfterChange of
              Just newDiagnosis ->
                  updateAcuteIllnessDiagnosisMsg id newDiagnosis
  ```
  If no further save follows the revert, the queued PATCH restores the record on the next cycle.
- **Who reads the stored value.** A subsequent encounter (`getAcuteIllnessDiagnosisForEncounters previousEncounters`, `Pages/AcuteIllness/Encounter/Utils.elm:96-101`), and on the server `hedley_stats`, `hedley_reports`, `hedley_case_management` (all read `field_acute_illness_diagnosis`; readers listed by grep, not traced).
- **Other fields with the same exposure (scout-read, not re-read by the orchestrator).** Any encounter's end date; prenatal `indicators`, `pastDiagnoses`, `nextVisitDate`; well-child encounter note and warnings; the individual participant's EDD, newborn, outcome and dates; session close; person edit. Prenatal and NCD diagnoses are regenerated from measurements on every later save, so they recover. Multi-step forms saved from the stored value (NCDA steps, vaccination doses) were NOT traced.
- **Size.** The window is the WhatsApp read, the general download and the authority download up to the batch holding the echo — seconds on a good link, longer on a slow one or behind a long download. No measurement. Sizing query (not run — night round): closed `acute_illness_encounter` nodes whose current revision holds no diagnosis while an earlier revision by the same device user holds one. B-524's "same device" counts on ihangane (diagnosis set shrunk 2, end date lost 4) fit this trigger but are not tied to it.
- **Bearing on B-499.** The second restore pass may list encounters stored as none by devices already on the fixed build; this is one way that can happen.
- **Fix shape (first guess).** In the download save, leave alone any row whose uuid still has an unsynced `shardChanges` / `nodeChanges` entry, and keep it out of the revision broadcast. That would close B-634 too. B-524's field-level encoding narrows the server damage but not the on-device revert.
