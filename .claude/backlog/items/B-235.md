### B-235 — Prenatal nutrition (Healthy Start): the gestational weight-gain verdict is inverted, so a woman gaining too little is told "Adequate" and one gaining well is told "Inadequate" — ✅ IMPLEMENTED · CONFIRMED (anchors + git + chart oracle verified) · HIGH · tier 2 · R25 unit 1
- **Mechanism.** `Pages/Prenatal/Activity/Utils.elm:1850-1854` in `resolveGWGClassificationForHealthyStart`: `if actualWeightGain <= expectedWeightGain then GWGAdequate else GWGInadequate`. `expectedWeightGain` (:1810-1845) is the *target* gain for the interval, built from the per-day rates in `weightGainStandardsByPrePregnancyClassificationHealthyStart` (:1877-1883). Gaining **less** than target is therefore reported as adequate, and outright weight loss (negative `actualWeightGain`) is the most "adequate" result of all.
- **The two independent oracles both disagree with it.** (1) The non-Healthy-Start sibling `resolveGWGClassification` (:1776-1789) computes `relation = actual / expected` and grades `< 0.7` severely inadequate, `< 0.9` inadequate, `<= 1.25` adequate — less than expected = inadequate. (2) The chart `viewWeightGainForEGAHealthyStart` (`Pages/Prenatal/ProgressReport/Svg.elm:309-338`) draws `firstTrimesterRedPoints` / `remainingTrimestersRedPoints` as the polygons **below** the expected-gain line and the green ones above, from the same per-day pair. So the same patient can plot in the chart's red zone while the nutrition form calls her Adequate/green.
- **History — the flip was deliberate, which is why this needs a product answer and not just a patch.** `f68333fab` (2026-01-12) introduced the function as `if expectedWeightGain < actualWeightGain then GWGAdequate` — agreeing with both oracles. `45f215dbd` (2026-01-13, "Another round of fixes") inverted that single line. ⚠ Verified the rest of that commit: its only other content is a pure variable rename in `Svg.elm` (`bmi` → `weightGain`, 10 lines each side, no semantic change), so the chart was **not** re-pointed to match. `45f215dbd` is an ancestor of `origin/main` — **deployed**.
- **Reachability.** Nurse → Prenatal encounter → Examination → Nutrition Assessment, when `healthyStartEnabled features` (`Activity/View.elm:1005`, `Backend/Utils.elm:390`). `Activity/View.elm:3235-3251` colours the line red iff `GWGInadequate` and sets `isAdequateGWG = classification /= GWGInadequate`; that boolean rides `PreSaveNutritionAssessment` → `SaveNutritionAssessment` (`Activity/Update.elm:1091, 1182-1187`) → `Backend.PrenatalEncounter.Model.SetGWGIndicator` → `Backend/PrenatalEncounter/Update.elm:55-75`, which writes `IndicatorAdequateGWG` / `IndicatorInadequateGWG` onto the encounter.
- **Impact.** Two consumers, both inverted: the on-screen guidance the nurse acts on, and the persisted indicator, which `hedley_reports.module:999-1000` maps to report token `'gwg'` (`:2230`) — so the Healthy Start GWG statistic is inverted too.
- **Sizing — partly done, one query left for the user.** `hedley_admin_get_enabled_features_string()` reads `variable_get("hedley_admin_feature_<name>_enabled", FALSE)`, so an absent variable = off. Checked live: the variable **exists on `ihangane` only** and returns *No matching variable found* on `vhw`, `tip-somalia` and `uvl` — Rwanda-only at most. ⚠ Its **value** was blocked for me by the auto-mode classifier; run `terminus drush ihangane.live -- vget hedley_admin_feature_healthy_start_enabled`. If it is `1` this is live clinical guidance being given backwards; if `0`, the item is inert and drops to tier 4.
- **Fix shape (guess).** Restore `actualWeightGain >= expectedWeightGain → GWGAdequate` so verdict and chart agree. Because the inversion was deliberate, confirm the direction with the Healthy Start protocol owner first — and if the intent was a two-sided band (too little *and* too much are both inadequate), that is a third possibility neither oracle currently expresses.
- 📌 Adjacent, unverified, different unit: the Healthy Start baseline BMI comes from `resolveBookingWeight` in the activity (`Activity/View.elm:3195-3203`) but from `resolvePrePregnancyWeight` on the progress report (`ProgressReport/View.elm:1797-1808`), so the classification feeding the two can diverge for the same patient.

  ⚠ **And a revert would have been wrong**: the pre-flip line was `expectedWeightGain < actualWeightGain`
  (strict), so a gain exactly on target classified Inadequate. Fix is `actualWeightGain >= expectedWeightGain`.
  Verified: `elm make src/elm/Main.elm` 548 modules; elm-test 3020 pass; elm-review clean on the committed state.
  Discrimination-tested both ways — against the deployed `<=` four of the five new tests fail; against the

- 📌 **The adjacent note is now CONFIRMED as a second spec deviation, split out as B-268.** Issue #1604 Step 1
  classifies from the **booking** measurements. The activity does that (`resolveBookingWeight`, `Utils.elm:1576`),
  but the progress report uses `resolvePrePregnancyWeight` (`:1509`), which reads the self-reported

- 🔍 **Review (`/code-review medium`, 2026-08-25) found one real defect in the fix and it is now fixed** —
  commit `3623d79f5`, thread `#2150 (discussion_r3856245037)`. `>=` alone decided the spec's
  "equal to or greater than" by exact float comparison, and the two sides reach the same number by
  different routes: `expectedWeightGain` is `days * 0.06`, `actualWeightGain` is the difference of two
  entered weights. At 30 days, expected `1.7999999999999998` vs actual `61.8 - 60.0 = 1.7999999999999972`
  → a woman exactly on target read Inadequate. Reproduces at day 5, 15, 30, 40, 55, 65, 80, 85, 105 and
  110 — a monthly visit interval is in the set. Both sides now pass through `Round.roundNum 2`
  (decimal-string rounding, so equal values return the *same* Float, making it a real equality rather
  than a tolerance).
  ⭐ **The lesson: I had seen the float fragility and mis-scoped it.** While picking test values I found
  30 days fails and 25 days is exact, and chose 25 — treating it as a test-construction problem when it
  was a production one. **A boundary that is awkward to test exactly is evidence about the code, not
  about the test.** Now covered by a sweep over every five-day interval to 20 weeks, which names the
  failing intervals when it breaks.
