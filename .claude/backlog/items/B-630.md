### B-630 — Person registration: after the app restarts on a group-session child page, the address lists stay empty until the next sync starts — ten minutes or more — so a nurse cannot pick a province and a CHW's Save does nothing — ✅ IMPLEMENTED · CONFIRMED by reading, ⚠ start-up order NOT observed (orchestrator read every hop; nothing run) · LOW · tier 4 · R62 unit 2 · DEPLOYED · all sites · not sized
- **Mechanism.** The location tables start empty on every app start and are filled only by a sync step:
  ```elm
  -- client/src/elm/SyncManager/Model.elm:447-448
      , geoInfo = emptyGeoInfo
      , reverseGeoInfo = Dict.empty
  ```
  ```elm
  -- client/src/elm/SyncManager/Update.elm:1204-1227
          BackendPhotoUpload ->
              case model.syncStatus of
                  SyncUploadPhoto errorsCount webData ->
  ...
                              -- This is first step of sync.
                              -- When device is offline, we may not get any further,
                              -- therefore, we need to generate and store geo info data here.
                              geoInfo =
                                  getGeoInfo model.syncInfoGeneral.site
  ...
                                  , geoInfo = geoInfo
                                  , reverseGeoInfo = getReverseGeoInfo geoInfo
  ```
  The other writer is the general download's site change (`Update.elm:906-914`). The cycle leaves `SyncIdle` only through `determineSyncStatus`, which refuses on the two photo pages:
  ```elm
  -- client/src/elm/SyncManager/Utils.elm:115-128, 381-383
          photoPage =
              case activePage of
                  -- Activity page where pictures are taken in bulk.
                  UserPage (SessionPage _ (ActivityPage (ChildActivity ChildPicture))) ->
                      True

                  -- Participant page, where activities are taken for a child.
                  UserPage (SessionPage _ (ChildPage _)) ->
                      True
  ...
      if syncCycleOn && not photoPage then
  ...
      else
          -- No change.
          model
  ```
  The start-up kick is one `TrySyncing` (`App/Update.elm:1034-1043`, after `HandlePairedDevice`); it runs `BackendFetchMain`, which on a photo page changes nothing. The next attempt is the idle timer — `idle: 10 * 60 * 1000` in `app.js` (`Utils.elm:1189-1196`) — and that tick is refused too if the nurse is on a child page at that moment. During a group session she usually is.
- **Reachability.** The app restarts on the same URL (`Nav.pushUrl model.navigationKey (Url.toString model.url)` in init, `App/Update.elm:199`): a reload, a discarded tab restored, or "Version" pressed while on a session child page. The nurse then opens registration before a sync has started.
- **Impact.** `App/View.elm:425-431` hands these tables to the Person form. Nurse create: the province list holds only the blank option. CHW create: nothing resolves from the empty reverse table, the address inputs are hidden, all five levels are required, Save does nothing visible ([[B-389]]'s symptom, different cause). Edit is unaffected.
- ⚠ **Not observed.** That `UrlChanged` lands before `HandlePairedDevice` at start is read from the code (the URL push is immediate, the device lookup is a request to the service worker), not seen in a browser. If the order were the other way the page would still be the PIN page and the sync would start. Check in the browser before building.
- **Relation to the R33 ruling.** R33 ruled the start-up empty window "sub-second, do not re-chase"; that holds when the start-up `TrySyncing` advances the cycle. This is the start where it does not.
- **Not the declined class.** Sync stalls are declined; this is form data that happens to be loaded by a sync step. [[B-610]] and [[B-621]] concern the same photo-page hold with other effects.
- **Fix shape (guess).** Build both tables in `SyncManager.emptyModel` from the site already in the flags, keeping the two recalculations for a site change.
