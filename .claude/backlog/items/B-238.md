### B-238 — Prenatal ultrasound: opening the execution-date calendar and closing it without picking a day counts the form 6/6 and enables Save, but Save then does nothing — READY · CONFIRMED (anchors verified; not reproduced in a browser) · LOW · tier 4 · R25 unit 1
- **Mechanism.** `ultrasoundFormInputsAndTasks` (`Pages/Prenatal/Activity/Utils.elm:3866-3872`) counts six tasks: the three pregnancy-sign booleans, `executionDate`, `eddWeeks`, `eddDays`. `toUltrasoundValue` (:6969-6981) requires a **seventh** field the count ignores — `|> andMap form.eddDate`. `eddDate` is never typed in; it is derived in `Activity/Update.elm` by `SetExecutionDate` (:355-363), `SetEDDWeeks` (:410-418) and `SetEDDDays` (:449-457), each needing the other two values present. But `SetExecutionDateSelectorState` (:375-386) does `executionDate = Maybe.Extra.or form.executionDate (Maybe.andThen .dateDefault state)` — merely **opening** the calendar sets the date to today (`dateDefault`, :3787) **without** computing `eddDate` — and the popup's only button is `close` (`DateSelector/SelectorPopup.elm:16-20`), which never re-emits `select`.
- **Reachability.** Nurse → first prenatal encounter (Ultrasound is expected until one is recorded, :107-109) → fill EDD weeks and days first, then open the execution-date calendar and dismiss it without tapping a day. `executionDate = Just today`, `eddDate = Nothing`, tasks 6/6. `Activity/View.elm:4291-4296` enables Save on `tasksCompleted == totalTasks`; `SaveUltrasound` (`Update.elm:473-500`) wraps the message list in `unwrap [] (\value -> …)`, so a `Nothing` value yields **no** save message and **no** `SetActivePage`. The button is dead and silent. The natural top-to-bottom order (date, then weeks, then days) computes `eddDate` correctly, so the nurse has to skip the date field and come back to it.
- **Impact.** No data loss and no false navigation (unlike B-037) — the encounter simply cannot be saved until the nurse re-touches a weeks/days field, with no explanation on screen. Recorded because it is the same count-vs-save class and cheap to close. All sites.
- 📌 The same `value.eddDate` is what `SaveUltrasound` writes onto the pregnancy via `Backend.IndividualEncounterParticipant.Model.SetEddDate` (`Update.elm:494-497`) — the participant-EDD path that B-168, B-194 and B-196 all touch. A fix here should not change that write; it is only reached when the value exists at all.
- **Fix shape (guess).** Either count `maybeToBoolTask form.eddDate` as a seventh task, or have `SetExecutionDateSelectorState` recompute `eddDate` when it applies the default, as `SetExecutionDate` does. The second is preferable — it removes the inconsistent state instead of only refusing to save it.
