### B-634 — Resilience messages: a read / favourite / remind action made while a sync cycle is running is undone when the device downloads its own earlier upload; the next action then erases it on the server too — READY · CONFIRMED by reading (orchestrator read the download save, the revision hand-off to the logged-in nurse, the whole-blob write and the server general query; nothing run, the timing was not observed) · LOW · tier 4 · R65 unit 2 · DEPLOYED · ihangane only, usage-capped (about 20 nurses, programme idle since 2025-11) · not sized
- **Not B-167(a) and not B-550.** B-167(a) is two devices on one nurse; B-550 is a server-side edit reverted. This is one device. B-167(a)'s line "same-device races closed in ms via the revision broadcast" does not cover it.

- **Sequence.** (1) A cycle reads its upload batch, holding action A. (2) The nurse marks message B read: the local row is A+B and the change is queued. (3) The same cycle's General download returns the nurse at A; IndexedDB and the in-memory nurse go back to A, B shows unread again. (4) Without another action the next cycle uploads A+B and it heals. (5) An action C before that (idle gap is 10 minutes, `app.js:464`) is built from the reverted copy, so the queue holds A+B then A+C, the server stores each whole, and B's flag is lost for good.
- **Reachability.** Wellbeing › Resilience Message: collapse a message or use its options while a cycle is between reading the upload batch and saving the General download. The reminder OK on the main menu takes the same path (scout's reading).
- **Impact.** A read message returns to Unread and the counter rises; a favourite or "remind me" is dropped. No clinical data.
- ⚠ **Wider, NOT traced.** The `bulkPut` has no queued-change check for the Authority table either (`app.js:645-647`). Whether a clinical record edited twice inside one cycle shows the same revert — and whether anything then rewrites it whole from the reverted copy — was not followed. Worth one look before this is sized as a messaging-only item.
- **Fix shape (first guess).** Skip, or re-apply the queued change over, a downloaded row whose uuid still has an unsynced `nodeChanges` row; or merge message flags per message id on the server (B-167(a)'s shape), which removes the permanent half only.
