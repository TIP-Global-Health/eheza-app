### B-431 — Group enrolment: the automatic check-in after adding a child to a running session always creates a new attendance record, even when the adult is already checked in — READY · CONFIRMED (orchestrator read the handler, the save switch and the page that does it right; sized live) · LOW · tier 4 · R36 unit 4
- **Mechanism.**
  ```elm
  -- client/src/elm/Backend/Update.elm:4189-4200 (HandlePostedPmtctParticipant)
                        GroupEncounterOrigin sessionId ->
                            data |> RemoteData.map (Tuple.second >> .adult >> (\motherId ->
                                                  Measurement.Model.SaveAttendance Nothing True
                                                      |> Backend.Session.Model.MeasurementOutMsgMother motherId
  ```
  `Nothing` reaches `saveMeasurementCmd` (`Backend/Utils.elm:271-281`), which POSTs on `Nothing` and PATCHes on `Just id`. The Attendance page resolves the existing id first (`Pages/Attendance/View.elm:139-146`).
- **Reach.** Attendance → Add New Participant → register/search → add family member → Relationship page with `GroupEncounterOrigin` → Save. Duplicate whenever the adult was checked in first (the normal order) or a second child is enrolled under her in the same session.
- **Impact.** Two `attendance` nodes for one person-session; readers take `List.head` (`Backend/Measurement/Utils.elm:145-150`), so a check-out can be undone by the other record. The daily duplicate sweep soft-deletes one. Live ihangane (2026-09-22): 0 live duplicate pairs, 11 pairs counting soft-deleted ones, all in 2026 (latest 2026-09-19).
- **Production check 2026-11-08 (read-only, all four sites).** vhw, uvl and tip-somalia have no duplicate attendance. ihangane has 13 person-session groups, oldest 2026-04-21; 6 have enrolments of that adult next to the attendance nodes (3 devices, April to July 2026).
  - 2 of the 6: two different children under one adult. 4 of the 6: the SAME child enrolled 2–3 times in the same group within seconds (5 extra `pmtct_participant` rows, all still live, cause not traced).
  - The "adult checked in first" order appears in none of the 6: the first attendance follows the first enrolment. The other 7 groups have no nearby enrolment, so another cause. Every one of the 6 keeps exactly one live attendance after the sweep.
  - Not measured: how often this path runs without a duplicate.
- **Presented 2026-11-08; I withdrew the recommendation to build it** (only 2 cases match the defect). No decision from the user yet.
- **Fix shape (first guess):** resolve the adult's current attendance id for the session before dispatching, as the Attendance page does, and pass it as the `Maybe AttendanceId`.
- **Correction to the production check above (2026-11-08).** Until `aace4a2e0` (shipped in v1.15.0, 2026-01-22) the nightly sweep hard-deleted duplicates, so "oldest 2026-04-21" is only the start of the surviving evidence. Six is a count since then, not a lifetime count.
