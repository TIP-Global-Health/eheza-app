- **Mechanism.**
  ```php
  // server/hedley/modules/custom/hedley_case_management/hedley_case_management.module:328-338
  function hedley_case_management_resolve_immunization_follow_ups($person_id, $to_nid, $limit = 200) {
    $query = hedley_general_create_entity_field_query_excluding_deleted();
    $result = $query
      ->entityCondition('entity_type', 'node')
      ->entityCondition('bundle', 'well_child_next_visit')
      ->propertyCondition('nid', $to_nid, '<')
  ```
  The nutrition, prenatal, TB and HIV resolvers use the same `nid <` rule (scout: `:127`, `:274`, `:388`, `:470`). `resolve_follow_up` sets `field_date_concluded = time()`; the client's `filterResolvedFollowUps` then drops the row on every device.
- **Reachability.** Device A offline for weeks with an old encounter; device B already uploaded a newer next-visit / follow-up for the same person; A syncs → `hedley_case_management_node_insert` → the insert trigger → the newer follow-up closes, while the follow-ups A's old visit created get higher nids and stay open. `generateImmunizationFollowUps` then shows the older due date or drops the child.
- **Evidence.** Scout (unit 5) matched each closure to the node whose upload time equals its `date_concluded`: device 3834 uploaded encounters dated 2025-09-30/10-01 on 2025-11-26, closing next-visits 2025-11-05..11-25 recorded by device 3836; device 3829 uploaded a 2025-03-20 encounter on 2025-11-11, closing a 2025-10-27 next-visit. Unit 7 independently measured the client-vs-server order disagreement since 2025 at 3/1,391 nutrition and 11/7,343 next visits. Not shown: whether each child actually dropped off the list (none of the 18 has an open next-visit today; later visits could explain that).
