### B-277 — Well Child immunisation (Burundi): the DTP-booster Save handler reads the DTP primary-series form, so what the nurse entered for the 18-month booster is never stored — READY · CONFIRMED (anchors verified; live-measured 2/2 records wiped) · MED · tier 3 · R26 unit 2 · ⭐ DEPLOYED (identical line on `origin/main`)
- **Mechanism.** `Pages/WellChild/Activity/Update.elm:1009-1013`: `SaveDTPStandaloneImmunisation personId saved nextTask -> ... saveMeasurementMsgs toVaccinationValueWithDefault model.immunisationData.dtpForm saved (Backend.WellChildEncounter.Model.SaveDTPStandaloneImmunisation personId)`. Every input on the DTP-standalone task writes to `dtpStandaloneForm` — `updateVaccinationFormByVaccineType VaccineDTPStandalone` (`Utils.elm:941-942, :972-973`) — and the View (`View.elm:1070`) and the task counter (`Utils.elm:1684`) read `dtpStandaloneForm`. Only the Save handler reads `dtpForm`. The eight sibling handlers (`:987-1084`) each read their own form; this one was copy-adapted from the DTP arm and **born this way** in `b52857711` (2023-10-29, "Introduce DTPS tandalone task"). `toVaccinationValue` (`Measurement/Utils.elm:1255-1267`) always returns `Just`, so the save never short-circuits.
- **Three traced outcomes.** (1) DTP task untouched this session (the usual case — primary series at 6/10/14 weeks, booster at 18 months): `dtpForm` is empty and not dirty → a `VaccinationValue EverySet.empty EverySet.empty AdministeredPreviously` is stored as the DTP-standalone measurement; the nurse's "given today" / "not given, reason" is discarded. `immunisationTaskCompleted TaskDTPStandalone` (`Utils.elm:863-864`) is `isJust measurements.dtpStandaloneImmunisation`, so task, activity and encounter all read complete, while `vaccinationProgress` keeps the child "behind" on the booster and the next visit keeps demanding it. (2) DTP task filled in the same session (catch-up child): the DTP doses/dates are stored under the DTP-standalone measurement — e.g. `VaccineDoseThird` today — which `latestVaccinationDataForVaccine` then reads as the booster given. (3) Re-edit of a saved record: `vaccinationFormWithDefault dtpForm saved` refills from the saved value → no-op write.
- **Twin.** `Pages/ChildScoreboard/Activity/Update.elm:516-522` — same commit, same `dtpForm` read. Fix both.
- **Reachability / site.** Burundi only: `allVaccineTypes` (`Measurement/Utils.elm:9942-9948`) adds `VaccineDTPStandalone` for `SiteBurundi` and HPV elsewhere. Nurse Pediatric Care → Immunisation → DTP-standalone → Save; CHW "administered previously" reaches the same handler.
- **Live measurement (`vhw.live`, 2026-08-30).** `well_child_dtp_sa_immunisation`: **2 nodes total, 2 with zero `field_administered_doses` rows, both `administered-previously`** (created 2025-04-04 and 2025-10-31) — the exact signature of outcome (1). For scale: `well_child_dtp_immunisation` has 361 nodes, `child_scoreboard_dtp_sa_immunisation` 0. So the task is rarely reached on Burundi but has lost data every time it was.
- **Fix shape (guess).** `dtpForm` → `dtpStandaloneForm` in both handlers (one word each). Pin with a test in the style of `nutritionAssessmentGateTests` (`Pages/WellChild/Activity/Test.elm:48-106`): a model whose `dtpStandaloneForm` holds a dose, `update` with `SaveDTPStandaloneImmunisation`, assert the emitted backend value carries it. The two live records cannot be repaired from data (the entry was never stored); the affected children just need the booster re-recorded.
