### B-028 — `IndexDbQueryGetShardsEntityByUuid` crashes on not-found — its PRIMARY use case → sync-incident diagnostics never sent — ✅ IMPLEMENTED 2026-08-13 via PR #2077 (shipped as B-159 item (a); verified on origin/develop `app.js:1193`) · CONFIRMED
- JS: `app.js` branch does `let entities = [result[0]];` then `entities[0].type` — TypeError when uuid absent from `shards`. It's queried exactly when an upload failed with "Could not find UUID X" (`SyncManager/Utils.elm` `resolveIncidentDetailsMsg`) — where X is typically a local not-yet-uploaded entity, i.e. NOT in `shards` → crash is the expected path.
- Elm: reply feeds `BackendReportIncidentDetails` (`Update.elm:901-907`) — fire-and-forget POST (`send (always NoOp)`), so nothing wedges; the diagnostic report is just silently lost.
- Fix: `if (!result[0]) { return sendIndexedDbFetchResult(queryType, JSON.stringify([])); }`. Severity LOW-MED (debuggability of exactly the FK incidents the backend team investigates).
- ⛔ **DUPLICATE — the same defect was recorded twice and found independently by two rounds** (B-028, and B-159 item (a) "no-reply crash on unknown-uuid incident lookup"). Fixed once, in #2077, with `if (!result.length) { return sendIndexedDbFetchResult(queryType, JSON.stringify([])); }`. 📌 Lesson: before starting any Tier-4 item, grep the backlog for the SYMPTOM and the FUNCTION NAME, not just the item id — a long queue re-finds its own entries, and the second recording never links back to the first.
