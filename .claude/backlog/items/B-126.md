### B-126 (original entry) — Client v5 UUID generation can mint the SAME UUID for two nodes created within ~100µs (silent record loss) — PLAUSIBLE (trigger frequency unquantified; mechanism CONFIRMED empirically) · MED · fix S
- `makeUuid()` (`client/src/js/nodes.js:1304`) = `v5(String(performance.timeOrigin + performance.now()), deviceUuid)` — **deterministic**: same clamped timestamp + same device ⇒ identical UUID. Sole call site: `postNode` (nodes.js:333), i.e. every client-created entity.
- **Empirical (Chrome, this machine, 2026-08-03):** `performance.timeOrigin + performance.now()` yields **39 distinct values in 10,000 tight-loop reads** (runs of 484 identical), string resolution 0.1ms; **996/1000 microtask-adjacent capture pairs identical**. Browser clamping (Spectre mitigations) makes the timestamp a ~100µs bucket, jittered — collision whenever two `makeUuid()` entries land in one bucket.
- **Concrete same-cycle double-create exists:** `PostRelationship` (Backend/Update.elm ~4320) dispatches `PostPmtctParticipant` via `sequenceExtra` in the SAME update cycle — pmtct `sw.post` fires immediately, relationship POST after two Dexie selects, so typically >100µs apart but not guaranteed (sub-100µs IDB resolution is possible on fast devices). No *guaranteed* same-bucket pair found; the scheme's collision resistance rests entirely on inter-POST latency nobody designed for.
- **Impact when it fires:** both entities land in the `shards` Dexie table keyed by uuid → second `table.put` silently OVERWRITES the first (client-side loss BEFORE upload); both change rows still upload with the same uuid → server-side duplicate-uuid node or upsert-clobber (backend behavior for a POSTed duplicate uuid unverified).
- **Outstanding verification (blocked this session — permission classifier stopped the terminus query):** duplicate `field_uuid` check on ihangane.live (`GROUP BY field_uuid_value HAVING COUNT(*)>1` joined to node) would show whether it has EVER fired server-side; note client-side overwrite may leave no server trace if the backend upserts.
- **Fix (tiny, no design change):** salt the name string — `timestamp + ':' + (++counter)` (module-level monotonic counter) — or simply use `v4()` for client-created nodes (crypto RNG, collision-proof; the v5-mimics-backend scheme has no functional dependency — makeUuid is used once at creation, nothing re-derives it). Keep it to a few lines in nodes.js.
- Context: this came out of the R17 uuid.js micro-audit; uuid.js itself (vendored kelektiv roll-up) is otherwise sound — crypto.getRandomValues used when available; the Math.random fallback is unreachable on the Chrome fleet.
