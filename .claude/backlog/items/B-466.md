### B-466 — Reporting e2e: the postpartum fixture records the outcome on the participant page first, so its postpartum visit lands in a second pregnancy, and its comment calls that step required — READY · CONFIRMED (spec + participant page read, 2026-10-13, while reproducing B-373) · LOW · tier 4 · test-only
- **Mechanism.** `client/e2e/reporting.spec.ts` "Backdate and create postpartum prenatal encounter":
  ```ts
  // client/e2e/reporting.spec.ts:1028-1041
        // Record pregnancy outcome from participant page first —
        // required before the Postpartum encounter button becomes active.
        ...
        await recordPregnancyOutcome(page, { preTerm: true });
        ...
        await startPrenatalEncounter(page, 'postpartum');
  ```
  The first visit is backdated 7 days, so Postpartum is already enabled (`postpartumEncounterButtonEnabled`: last visit not postpartum, none completed today). Recording the outcome closes the pregnancy, the participant page then sees no active pregnancy, and Postpartum creates a NEW pregnancy (`createNewSessionMsg … NursePostpartumEncounter`). The helper's doc comment (`client/e2e/helpers/prenatal.ts` `recordPregnancyOutcome`, "This is required before starting a Postpartum encounter") repeats the claim.
- **Impact.** Test-only: the Peripartum / ANC report assertions are built on a woman with two pregnancies, one holding the outcome and one holding the postpartum visit — the B-373 shape, not the clinical one. A fix to B-373 does not change this path (no postpartum visit in the concluded pregnancy).
- **Fix shape (guess).** Start Postpartum first and record the outcome through the visit's Pregnancy Outcome activity (`completePregnancyOutcome`), or drop the comment's claim; re-check the report counts the spec expects.
