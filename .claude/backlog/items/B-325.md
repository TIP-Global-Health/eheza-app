### B-325 — Sync download: the revision cursor advances past an upload whose transaction has not committed yet, so a second device at the same health centre never receives those records — silent, permanent, no error on either side — READY · CONFIRMED (both server queries, the client cursor rule, the upload transaction and the concurrent background writer read by the orchestrator; live DB settings checked) · MED-HIGH · tier 2 · R29 unit 2 · ⭐ DEPLOYED (all sites, both lanes)
- **Mechanism.** The GET handler pages by the node table's current `vid`: `node.vid > base` … `orderBy('node.vid')` … `range(0, 500)` (`server/hedley/modules/custom/hedley_restful/plugins/restful/node/sync/HedleyRestfulSync.class.php:239-265`; general lane `:140-155`), and the client sets its cursor to the highest `vid` in the batch (`client/src/elm/SyncManager/Update.elm:286-292`, general twin `:818-824`). That contract assumes vids become visible in vid order. They do not: a vid is an InnoDB auto-increment allocated at INSERT, but the upload wraps the whole batch in one `db_transaction()` (`HedleyRestfulSync.class.php:427-433`), so its rows become visible only at commit. Any other writer committing a same-shard node during that window gets a vid inside the upload's range and is visible first — a device that downloads in the window sets its cursor above the upload's vids; when the upload commits, its nodes sit *below* the cursor and `node.vid > base` never selects them again. `revision_count` uses the same predicate, so it reads 0 and the lane reports `Success`. Live ihangane: `innodb_autoinc_lock_mode = 1`, `tx_isolation = READ-COMMITTED` (checked from this seat). A second, narrower window in the same request: the batch query and the per-type render are separate queries, and the render selects the *current* `vid` (`HedleyRestfulSyncBase.class.php:76-79`) — a batch member re-saved between them is served at its new higher vid, and the client's cursor jumps over everything committed in between; the comment at `:267-272` ("represent the specific revision, rather than the current revision") describes what the code does not do.
- **The concurrent writer exists in production and is not another device.** The AQ workers re-save persons of the HC whose measurements were just uploaded, each in its own short transaction: `hedley_ncda.module:1049` and `hedley_reports.module:1343` (`node_save($person)`). Scout-measured on ihangane.live (7 days): uid-0 person revisions 495 vs 24 for the busiest device; **7 of 102 multi-row uploads** had a uid-0 person revision with a vid strictly inside the upload's `MIN(vid)..MAX(vid)` and a `node_revision.timestamp` 1–7 min before the upload start, all on the same shard. That is the precondition at ~7% of uploads; whether a second device issued its GET inside the 0–5 s window is not recoverable after the fact — a device that lost nodes this way shows no symptom.
- **Reachability.** Automatic: every device's `BackendAuthorityFetch` / `BackendGeneralFetch` (`Update.elm:161-169`, `:706-714`). Nothing on the client (`app.js:625-667` `bulkPut`) or server reconciles; only a from-zero re-sync (the debug "reset revision") recovers.
- **Impact.** Every *other* device at the HC silently lacks the uploaded measurements/encounters/participants (and, on the general lane, nurse/village/HC edits); the server and the uploading tablet hold the data. Case management, dashboards, growth charts and later edits on those devices diverge. All sites, no `EHEZA_SITE` split. ⚠ The parked per-record-commit design brief (`design-brief-backend-per-record-commit`) would *widen* this window by committing items one by one — read this first if that brief is revived. Related but distinct: B-317 (client applies a late response under the wrong HC), B-192 (inner-join drops).
- **Evidence.** Both handlers, `HedleyRestfulSyncBase`, the upload transaction, the client cursor rule and both worker `node_save` sites read by scout and orchestrator at `62b029b9d`; DB settings and the 7-day census run on ihangane.live. Not executed as a race.
- **Fix shape (guess).** Never hand out the head of the vid sequence while a transaction may still be open behind it: exclude `node.changed >= REQUEST_TIME - lag` (uploads take ≤ 5 s; `changed` is the upload's REQUEST_TIME) from both the batch and the count; or return a server-computed safe cursor (max vid below any open transaction) and have the client use it instead of the batch max. Close the render window by emitting the batch query's vid rather than re-reading `node.vid`. If a lag is introduced the client must not treat `revision_count == 0` alone as completion.
