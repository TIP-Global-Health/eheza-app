### B-419 — Photo download: a failed IndexedDB read of deferred photos never answers Elm, so photo downloads stop until reload — READY · CONFIRMED-mechanism (orchestrator read both JS branches, the catch set and the Elm Loading guard) · LOW · tier 4 · hardening · R35 unit 3 · latent
- **Mechanism.** B-025 put a `.catch` on the five upload branches of `askFromIndexDb`, and `GetShardsEntityByUuid` has one too. The two deferred-photo branches do not:
  ```js
  // client/src/js/app.js:1070-1128
      case 'IndexDbQueryDeferredPhoto':
        (async () => {
          let result = await dbSync.deferredPhotos.where('attempts').belowOrEqual(2).limit(1).sortBy('attempts');
          ...
        })();
  ...
      case 'IndexDbQueryDeferredPhotoBatch':
        ...   // try/catch covers only JSON.parse(data), not the Dexie reads
        })();
  ```
  Elm sets the lane to Loading before asking and ignores later requests while Loading:
  ```elm
  -- client/src/elm/SyncManager/Update.elm:1008-1017
                  DownloadPhotosInProcess (DownloadPhotosBatch record) ->
                      if isRecordLoading record then
                          noChange
                      else
                          ... { record | indexDbRemoteData = RemoteData.Loading ... }
  ```
  Only the reply handlers move it out of Loading. The lane has no timeout.
- **Impact.** Needs a rejected Dexie read (e.g. Chrome backing-store "UnknownError" under disk pressure). Photo downloads then stop for the session; main sync is a separate status and continues. The app's frequent self-reloads limit the duration.
- **Related:** B-318 is the same symptom from the photo GET having no timeout. B-026 fixed `bulkPhotos.js`, not this read.
- **Fix shape (first guess):** add `.catch` to both branches sending `[]`; `SyncManager/Decoder.elm:76-101` already reads that as "no rows", which moves the lane to Idle so it retries next cycle.
