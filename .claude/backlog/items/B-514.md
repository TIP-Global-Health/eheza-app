### B-514 — Sync-incident re-creation + nightly measurement dedup: a re-created measurement for an encounter that already holds one of that bundle wins the dedup by its newer revision, so the device's record is soft-deleted and replaced — on ihangane a CHW-recorded prenatal "fever" danger sign became "none" on deploy night — MONITORING until 2026-11-19 · MED-LOW · tier 3 · CONFIRMED (code + both ihangane copies, 2026-10-26) · DEPLOYED (all sites; one instance on ihangane, none on vhw)
- **Mechanism.** `hedley_user_create_entity_by_sync_incident_data()` (`hedley_user.module:231-`, origin/main) builds the node from the incident payload with no check that the encounter already holds a measurement of that bundle for the person. `delete-duplicate-measurements.php` (`hedley_admin/scripts`, nightly Jenkins H 23) then keeps the first node in `orderBy('n.vid', 'DESC')` (`:84`) and soft-deletes the rest — and the re-created node always has the newest `vid`, so it wins regardless of content or author.
- **Live instance.** Post-deploy run of `recreate-sync-incident-entities.php` on 2026-10-25 09:14:47 UTC created `danger_signs` 5627713 (uuid 2ff41f27, signs `none`, uid 0, vid 10800758) for prenatal encounter 5386411 (person 5062392), which already held `danger_signs` 5386418 (uuid 726ba7f8, signs `fever`, uploaded by robot 3925 on 2025-12-12, vid 9833073 on the pre copy). At 23:53:32 the dedup soft-deleted 5386418 (`field_deleted` 1, new vid 10812054) — the only soft-delete of the first night on new code. Devices on that shard download the deletion and the `none` record; the person's reports data was recalculated.
- **Impact.** A clinical record changed by two maintenance paths with no human decision: the CHW's danger sign is gone from the encounter, the antenatal progress report and the Case Management history. One instance so far; the class recurs whenever a re-created entity has a live sibling (vhw's two re-creations had none).
- **Fix shape (first guess).** The re-creation path should skip or flag a measurement whose encounter already holds that bundle for the person (and say so in watchdog), and the dedup should prefer the device-authored node over a uid-0 copy, not the newest revision. Restoring 5386418 is a repair, which is the user's call (declined class) — recorded here for the decision, not proposed as a script.
