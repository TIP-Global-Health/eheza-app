### B-433 — Prenatal labs: a repeated tap on "known as positive" for a test reopened from the record still clears it — the repeat-tap guard added by PR #2212 compares against the empty form in the model, not the form on screen — ✅ IMPLEMENTED 2026-09-22 (issue #2278, PR #2279) · CONFIRMED (handler, view merge and guard read on `develop` 2026-09-22; same mechanism fixed for NCD in PR #2275, review round 2) · LOW · tier 4 (form UX; nothing is saved wrong, the nurse has to re-enter) · filed at the user's request out of B-421's review
- **Mechanism.** PR #2212 (B-320, commit `60c281b9d`) made the universal known-as-positive updates leave the form alone when a tap repeats the answer shown:
  ```elm
  -- client/src/elm/Measurement/Utils.elm:6526-6528 (knownAsPositiveUpdate)
  knownAsPositiveUpdate knownAsPositive form =
      if knownAsPositiveUnchanged knownAsPositive form then
          form
  ```
  `knownAsPositiveUpdateHIVTest` and `knownAsPositiveUpdatePartnerHIVTest` go through the same guard. But the Prenatal handlers apply the update to the form held in the model, which is still empty for a test loaded from the record:
  ```elm
  -- client/src/elm/Pages/Prenatal/Activity/Update.elm:2278-2284
          SetHIVTestFormBoolInput formUpdateFunc value ->
              let
                  form =
                      model.laboratoryData.hivTestForm      -- knownAsPositive = Nothing on a reopened test

                  updatedForm =
                      formUpdateFunc value form
  ```
  while the view shows the form merged with the saved value:
  ```elm
  -- client/src/elm/Pages/Prenatal/Activity/View.elm:1586
                                  |> hivTestUniversalFormWithDefault data.hivTestForm
  ```
  and the bool input's label fires on every tap, checked or not (`Pages/Utils.elm` `viewCustomBoolInput`: `label [ onClick <| setMsg value ]`).
- **Reach.** Three universal known-as-positive tasks, all raw-form handlers: HIV (`:2278`), Partner HIV (`:3134`), Hepatitis B (`:2440`, uses plain `knownAsPositiveUpdate`).
- **Harm.** Nurse reopens a saved HIV test (run today, Negative, partner answers given) and taps the already-shown "No" on "known as positive": the guard misses, and the update clears performed, note, date, the result and the four partner/programme answers. Nothing wrong is saved — the task goes incomplete and she must re-enter the whole test. PR #2212's intent (commit message: *"Leave the entry alone when the answer repeats what is on screen"*) holds only for a form touched in the same session.
- **Not in scope here:** the universal "performed" updaters carry no repeat-tap guard at all, in any module; a repeat Yes there resets the run by design of the older code. Decide separately whether to guard them.
- **Fix shape (first guess):** as PR #2275 did for NCD — in the three handlers, apply `formUpdateFunc` to the form merged with the saved record (`hivTestUniversalFormWithDefault` / `partnerHIVTestFormWithDefault` / the Hepatitis B one over `getMeasurementValueFunc` of the encounter's measurement), the pattern Prenatal's `update` already uses for `medicalHistoryForm` at the top of the function. Test through the real `update` with a saved test in the db, as `Pages/NCD/Test.elm` `repeatedTapOnSavedTest` does. ⚠ `elm-test-cannot-import-backend-update` in memory: Prenatal `Activity.Update` is not `Backend.Update`, and NCD's equivalent test compiles in CI's budget, but check.
