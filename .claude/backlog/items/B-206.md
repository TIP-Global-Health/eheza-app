### B-206 — Child wellness dashboard: the "# of Children Seen" card counts visits, not children — ✅ IMPLEMENTED 2026-08-24 (issue #2137, PR #2138) · CONFIRMED · tier 4 · found by `/code-review medium` on PR #2136
- `numberOfChildrenSeen` was `getEncountersForSelectedMonth … |> List.filter isSPVNurseEncounter |> List.length`, and `getEncountersForSelectedMonth` is `List.concatMap .encounters >> List.filter (withinSelectedMonth …)`. So it counted nurse well-child ENCOUNTERS in the selected month while the card reads **"# of Children Seen"** (`Translate.elm:30072`). A child seen twice that month added two. The error is always upward.
- **Live measurement, ihangane.live 2026-08-24** (nurse `pediatric-care` encounters vs distinct participants, by month): 2025-09 1,427/1,407 (+1.4%) · 2025-10 1,739/1,706 (+1.9%) · 2025-11 1,690/1,664 (+1.6%) · **2025-12 1,467/1,377 (+6.5%)** · 2026-01 1,631/1,577 (+3.4%) · 2026-06 589/569 (+3.5%) · **2026-07 634/590 (+7.5%)**. Typically 1.5-3.5%; the 16.5% seen in 2026-03 is an artefact of that month holding only 106 encounters.
- ⭐ **Scope checked, and it is a lone site, not a family.** `getEncountersForSelectedMonth` has four other callers in `Pages/Dashboard/View.elm` (:260, :836, :852, :3042) and every one feeds something labelled as encounters or cases — diagnosed cases, total assessments, percent of good nutrition encounters — where counting encounters is correct. This card was the only place the flattened count was presented as a count of people.

- 📋 **Review outcome (`/code-review medium children-seen-counts-children`, 2026-08-24) — 2 findings on this item, BOTH real, both fixed in `4c76eb5`:**
  1. **The first fix was incomplete.** `countChildrenSeenForSelectedMonth` counted `SPVDataItem`s, and an item is an **individual participant**, not a child: `hedley_stats_get_spv_data()` keys `$items` by participant nid while setting `'id' => $row->field_person` (`hedley_stats.module:1598`), so one child holding two well-child participants yields two items sharing an `identifier`. I deduped visits and left participants duplicated — the same defect class the item exists to remove. Now `>> List.map .identifier >> EverySet.fromList >> EverySet.size`, matching `spvDataDict` and `immunizationDataItems`. **Live residual measured before fixing: nil in 9 of 12 months, max +0.35% (2 children, 2026-06)** — negligible in impact, but it is a shared `Utils` helper named for children and the next caller will trust the name. The duplicate participants are the well-child face of the create-race tracked as [[B-195]] (56 persons on ihangane.live hold >1 `well-child` participant).
  2. **The test asserted the wrong thing and would have BLOCKED the correct fix.** `childSeenAt` hard-coded `identifier = 1`, so "each child seen counts once" asserted that two items sharing one identifier count as 2. Deduping by identifier turns it red. ⛔ **A test that must be deleted to allow a bug fix is worse than no test.** `childSeenAt` now takes a `PersonIdentifier`; the distinct-children case is real and the shared-identifier case is pinned.
- ⛔ **PROCESS TRAP, cost a wrong conclusion AND a wrong diagnosis of that conclusion (2026-08-24):** the first discrimination run reported the new test PASSING with the dedupe removed — i.e. that it tested nothing. I first blamed a Python write that never reached disk. **That was wrong.** The real cause: `>> List.map .identifier >> EverySet.fromList >> EverySet.size` **occurs TWICE in `Pages/Dashboard/Utils.elm`** — `countTotalNumberOfPatientsWithGestationalDiabetes` already used the identical idiom, with a comment giving the same reasoning (*"Since one woman may have multiple pregnancies, we make sure that patient identifier is unique before we count the total"*). My revert replaced the FIRST occurrence, so it reverted the gestational-diabetes counter and left `countChildrenSeenForSelectedMonth` intact; the suite passed because the fix under test was never removed. The same slip later put `Set.fromList` into that unrelated function while applying the O(n²) fix.
  ⭐ **The runbook's `hedley_reports.module` rule generalises: in any file with near-identical pipelines, edit BY LINE NUMBER with the target line asserted first.** Re-run that way, exactly `one child holding two participants counts once` fails and the other four pass. 📌 And: a "no discrimination" verdict is itself a claim that needs verifying before it is reported — I posted the wrong explanation to PR #2138 before checking, and had to correct it there.
  📌 **Second lesson: the precedent already existed.** Had I grepped for the dedupe idiom before writing it, `countTotalNumberOfPatientsWithGestationalDiabetes` would have shown both the pattern AND the reason, 240 lines above my own function in the same file.
