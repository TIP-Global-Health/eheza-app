### B-543 — Photos (group Child Picture, Family Nutrition, person registration): the Dropzone completion event is delivered to whichever person's form is on screen when the upload finishes, so a photo taken for child A lands in child B's form if the nurse switches cards before it completes — READY · LOW · tier 4 · TRACED, NOT REPRODUCED (window = client-side resize + cache write) · DEPLOYED · R49 unit 2
- **Mechanism.** One global Dropzone is bound to `#dropzone`; completion is a DOM event dispatched on that element, and the Elm handler is whatever the CURRENT view attached to the reused node:
  ```js

      var event = makeCustomEvent("dropzonecomplete", { file: file });
  ```

  In the group activity-first flow the message is wrapped as `MsgChildActivity ChildPicture selectedParticipant (MsgMeasurement …)` with `selectedParticipant` computed by the view AT EVENT TIME (`Pages/Activity/View.elm:112-135, 232`), and `Pages/Session/Update.elm` inserts the url into `childForms[selectedParticipant]`. Same shape in `Pages/FamilyNutrition/Encounter/Update.elm` (`DropZoneComplete` writes `photoData` of the currently selected member) and `Pages/Person/View.elm:973`.
- **Reachability.** Group session → Activities → Child Picture → tap child A → take photo → while Dropzone is still resizing (600×800) and POSTing to `cache-upload/images`, tap child B's card. B's thumbnail shows A's picture; Save stores it as B's `photo`. Family Nutrition: switch member before completion. The nurse normally sees the wrong thumbnail first; the window is a second or two on the tablets in use.
- **Fix shape (first guess).** Make the completion carry who it was taken for (render the person id on the dropzone host and read it from `event.target` in the decoder; drop a completion whose person differs from the current selection), or bind one Dropzone per person id. The signature pad (`signaturecomplete` on `#signature-pad`, `Pages/StockManagement/View.elm:832`) has the same shape but its page is a singleton that cannot change person mid-upload.
