### B-369 — Prenatal participant (mixed fleet, release #2128): once a new device opens a fresh pregnancy over an expired undated one, every v1.18 device sees TWO active pregnancies and picks one arbitrarily — encounters and the outcome can land on the years-old shell — READY · CONFIRMED (both `isPregnancyActive` versions, `viewActions` pick and the nurse first-visit action read by the orchestrator; order trace from B-254) · LOW · tier 4 · R32 unit 2 · introduced by #2134 (B-194), un-deployed; bites only during the device adoption window
- **Mechanism.** #2134 lets an undated pregnancy expire 372 days after registration on new clients:
  ```elm
  -- client/src/elm/Pages/Prenatal/Participant/Utils.elm:24-28 (develop)
          let
              eddDate =
                  Maybe.withDefault (lmpToEDDDate session.startDate) session.eddDate
          in
          diffDays eddDate currentDate < 92
  ```
  Deployed clients (`git show origin/main:client/src/elm/Pages/Prenatal/Participant/Utils.elm`, `v1.18.2`) keep it active forever:
  ```elm
          session.eddDate
              |> Maybe.map
                  (\eddDate -> diffDays eddDate currentDate < 92)
              |> Maybe.withDefault True
  ```
  On a new device the expired shell drops out of `activePregnancyData`, so `maybeSessionId` is `Nothing` and the first-visit button creates a second participant:
  ```elm
  -- client/src/elm/Pages/Prenatal/Participant/View.elm:~277 (viewActionsForNurse)
                          maybeSessionId
                          |> Maybe.withDefault (createNewSessionMsg currentDate selectedHealthCenter id NurseEncounter)
  ```
  An old device then holds two active antenatal participants for the woman and takes `List.head` of an unsorted filter (`View.elm:~84-92`, same on main) — participant-UUID order per B-254's trace.
- **Reachability.** Nurse/CHW participant page for a woman whose undated shell is past 372 days, opened on an updated device; the same woman then opened on a not-yet-updated device at the same HC.
- **Impact.** On the old device: a visit can resume the shell's years-old open encounter or start a subsequent visit on it; "Record Pregnancy Outcome" can conclude the wrong one; an LMP recorded into the shell gives it an EDD, which then makes it active on new devices too (B-254 for good). All sites. Scout live rate of the trigger (encounters created >372 days after registration into an EDD-null pregnancy, 2026-03-15 → now): ~2 participants on ihangane, 3 on vhw — so a handful at most across an adoption window of weeks.
- **Backlog de-dup.** B-254 (arbitrary pick — the selection defect itself, needs two active pregnancies; previously only reachable via B-195's race), B-194 (the #2134 change; its entry discusses the outcome-button trade, not the mixed fleet).
- **Fix shape (guess).** Nothing can change deployed clients. Landing B-254's sort (newest `startDate` first) in the same release shrinks the tail; the release note could tell HCs to update every device together.
