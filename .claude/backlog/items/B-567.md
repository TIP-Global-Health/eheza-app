### B-567 — Acute Illness subsequent visit: the page's diagnosis is computed as if the visit were the first one, so a positive malaria RDT on a follow-up never reaches the Next Steps gate, the medication form, the saved follow-up or the header — Coartem is never offered, complicated malaria and infants are not referred, and Case Management keeps the old diagnosis — READY · MED-HIGH · **tier 1 (standing rule: care-pathway determination)** · CONFIRMED by running (orchestrator's scratch elm-test in a scratch worktree, 2026-11-09, 7 pass / the 2 design assertions fail / both controls pass) · DEPLOYED, both sites, CHW and nurse · in the code since the 2020-21 original (`git blame` `03e288ff4c` / `57fd1968f6`), not introduced by B-525 / B-280 · R52 unit 3
- **Mechanism.** `generateAssembledData` builds the record with placeholders and runs the diagnosis resolver on THAT record, before the real `initialEncounter` flag is set:
  ```elm
  -- client/src/elm/Pages/AcuteIllness/Encounter/Utils.elm:61-71, 96-105
          assembled =
              RemoteData.map AssembledData (Success id)
                  ...
                  |> RemoteData.andMap (Success previousEncountersData)
                  |> RemoteData.andMap (Success [])
                  |> RemoteData.andMap (Success [])
                  |> RemoteData.andMap (Success True)      -- initialEncounter placeholder
                  |> RemoteData.andMap (Success Nothing)   -- diagnosis placeholder
      ...
                  currentDiagnosis =
                      if initialEncounter || isJust diagnosisByCurrentEncounterMeasurements then
                          diagnosisByCurrentEncounterMeasurements

                      else
                          getAcuteIllnessDiagnosisForEncounters previousEncounters

                  diagnosisByCurrentEncounterMeasurements =
                      resolveAcuteIllnessDiagnosis currentDate features isChw data   -- data.initialEncounter == True here
  ```
  The resolver branches on that flag — the subsequent-visit branch (RDT ± danger signs) is only reached when it is `False`:
  ```elm
  -- client/src/elm/Pages/AcuteIllness/Activity/Utils.elm:2472-2507
  resolveAcuteIllnessDiagnosis currentDate features isChw assembled =
      if assembled.initialEncounter then
          ... covid19DiagnosisPath ... nonCovid19DiagnosisPath ...
      else
          malariaRapidTestResult assembled.measurements
              |> Maybe.andThen (\testResult -> case testResult of RapidTestPositive -> if dangerSignPresentOnSubsequentVisit ... then Just DiagnosisMalariaComplicated else Just DiagnosisMalariaUncomplicated ...)
  ```
  Both initial paths need the three symptom records (`nonCovid19DiagnosisPath` gates on `mandatoryActivitiesCompletedFirstEncounter`, `:2386-2398`; `covid19SuspectDiagnosed` counts symptoms, `:2510-2535`), and Symptoms is offered only on an initial encounter (`expectActivity`: `AcuteIllnessSymptoms -> assembled.initialEncounter`, `:64-65`). So on EVERY subsequent encounter `diagnosisByCurrentEncounterMeasurements` is `Nothing` and `assembled.diagnosis` is the carried-over one — the `isJust` clause of `currentDiagnosis` is dead by construction. The STORED diagnosis is right: `generateSuspectedDiagnosisMsgsSubsequentEncounter` (`Backend/Update.elm:9856-9895`) calls `subsequentEncounterDiagnosisUpdate` on the finished record (`initialEncounter = False`), but `previousEncounters` excludes the current encounter (`Encounter/Utils.elm:47-54`), so the stored value never flows back into `assembled.diagnosis`, and nothing on the page reads `assembled.encounter.diagnosis`.
- **Consumers of the wrong value on a subsequent visit** (every reader of `assembled.diagnosis`): (a) `expectNextStepsTask` → `expectNextStepsTaskSubsequentEncounter currentDate person diagnosis` (`:2113-2123`, `:2192-2228`): `sendToHCByMalariaTesting ageMonths0To6 diagnosis` (`:2282-2286`, True for Complicated / Pregnant / Uncomplicated under 6 months) is evaluated with the OLD diagnosis, so with a positive RDT plus a danger sign, or a positive RDT in a child under 6 months, the task set is `[MedicationDistribution, FollowUp]` instead of `[SendToHC, FollowUp]`; (b) `viewMedicationDistributionForm … diagnosis` (`Activity/View.elm:1152, 1237-1240` → `medicationDistributionFormInutsAndTasks`, `Utils.elm:890-1095`): the medicine list is the OLD diagnosis's — lemon juice / honey for cold-and-cough, ORS + zinc for GI, and for fever-of-unknown-origin / undetermined the `_ -> ( emptyNode, ( [], [] ) )` arm (0/0 tasks, Save enabled on an empty form) — never Coartem for the malaria the encounter now carries; (c) `SaveFollowUp personId (Maybe.map Tuple.second assembled.diagnosis)` (`View.elm:1355-1358`) stores the old diagnosis on the follow-up, and Case Management prefers `item.value.diagnosis` (`GlobalCaseManagement/View.elm:649-658`); (d) the encounter header "Subsequent visit: <old>" (`Encounter/View.elm:190-203`), the activity header (`Activity/View.elm:102`), the person-details label (`Encounter/View.elm:231`) and the post-save popup (`Backend/Update.elm:9884`) — while the progress report's Assessment pane (stored, B-220) says malaria.
- **Reachability.** CHW or nurse subsequent encounter of an illness whose earlier encounters had no positive RDT (cold and cough, respiratory infection, GI infection, fever of unknown origin after a negative RDT, undetermined). Vitals with temperature ≥ 37.5 → the Laboratory task's subsequent branch (`:2033-2055`: fever recorded, no earlier positive) → RDT saved Positive → `MalariaTestingRevision` → the writer stores malaria, the page keeps the old illness. A follow-up of an illness that already had a positive RDT is NOT affected (the RDT task is not offered). No `EHEZA_SITE` split.
