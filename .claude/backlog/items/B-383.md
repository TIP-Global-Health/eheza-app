### B-383 — Resilience survey cap counts duplicate saves, so a nurse who saved one sitting twice is permanently denied the programme's final survey — READY · CONFIRMED (orchestrator read both functions and re-ran the live duplicate query) · LOW · tier 4 · R33 unit 5 · DEPLOYED, ihangane only, usage-capped
- **Mechanism.** The gate counts nodes:
  ```elm
  -- client/src/elm/Pages/MessagingCenter/View.elm:81-93
                                  surveyCount =
                                      List.length filteredSurveys

                                  filterCondition survey =
                                      if surveyCount == 0 then
                                          -- We need to have at least one survey completed.
                                          True

                                      else if surveyCount >= 3 then
                                          -- There can be up to 3 surveys during program which lasts
                                          -- 6 months. At the begining, after 3 months and at the end.
                                          -- So, if we have 3 surveys already, there's no need to another one,
                                          False
  ```
  Its sibling in the same feature deduplicates for exactly this reason, and says so:
  ```elm
  -- client/src/elm/Pages/MessagingCenter/Utils.elm:155-165
                  uniqueSortedSurveys =
                      -- In our system, sometimes we see that measurements are saved more than once.
                      -- Therefore, we make sure taht take surveys we take got a unique dateMeasured.
                      -- Use List.foldl.
                      List.foldl
                          (\survey acc ->
                              Dict.insert survey.dateMeasured survey acc
                          )
                          Dict.empty
                          surveys
  ```
  So the score dialog treats a double-save as one sitting and the gate treats it as two — the copy-adapted sibling that did not get the dedup.
- **Reachability.** Wellbeing → Resilience Message (`UserPage MessagingCenterPage`); `view` computes the gate before anything else, and `False` means the survey is never offered again for the rest of the programme.
- **Evidence (orchestrator live queries, ihangane.live).** Exactly one duplicate group exists in production: nurse 1627758, `quarterly`, `date_measured` 2024-08-29, 2 nodes — nids 4204941 (created 10:10:52) and 4205311 (10:17:31), seven minutes apart, so a second sitting or second device rather than a double-tap. Her full quarterly set is 3 nodes over 2 distinct dates (2024-08-29 ×2, 2024-12-11). `surveyCount = 3` → blocked; with the dedup it would be 2 and the third survey would be presented.
- **Impact.** One nurse of 20 on the only live site loses the programme's final outcome measurement; the resilience-survey report and CSV are short one row. No clinical or patient data.
- **Usage cap (orchestrator-relevant).** Gating is per-nurse (`field_resilience_program`), not a feature flag and not site-split. 87 `resilience_survey` nodes on ihangane, first 2024-08-26, last 2025-11-06, **zero in 2026**; 20 enrolled nurses, all with a start date; vhw/uvl/tip-somalia have none. Programme length is 221 days, so every enrolled nurse's programme ended Apr 2025 (18) or Aug 2025 (2). Tier everything in this program as usage-capped.
- **Fix shape (guess).** Count distinct `dateMeasured` rather than `List.length`. Per the repo's duplication rule the existing fold in `resolveSurveyScoreDialogState` should become one shared helper used by both, not a second copy.
