### B-245 — Statistical Queries: 15 prenatal diagnoses are missing from the report mapping, so encounters carrying only those are counted as "No Prenatal Diagnosis" — ✅ IMPLEMENTED 2026-09-16 (issue #2258, PR #2259, branch `B-245-prenatal-report-diagnosis-mapping`, base develop @8b37e326e, commits 97afbfcb5 + 0bf1c0911 + a144c374b) · CONFIRMED (mapping diffed independently; consumer chain verified) · MED-HIGH · tier 3 · R25 unit 7
- **Mechanism.** `hedley_reports_prenatal_diagnosis_mapping()` (`hedley_reports.module:2128`) maps only 82 of the 97 real allowed values of `field_prenatal_diagnoses`. The producer drops anything unmapped without a trace (`:980-992`, `if (!empty($prenatal_diagnosis_mapping[$diagnosis['value']]))`), then joins what is left into the wire (`$encounter_data = "$encounter_date|$encounter_type|$mapped_diagnoses|$mapped_indicators"`).
- **It is worse than an undercount.** When *all* of an encounter's diagnoses are unmapped, `$mapped_diagnoses` is `""`; `server/elm/src/Backend/Reports/Decoder.elm:253-260` turns that into `[]`; and `generatePrenatalDiagnosesReportData` (`server/elm/src/Pages/Reports/View.elm:2628-2635`) maps an empty list to `[ NoPrenatalDiagnosis ]`. A diagnosed encounter is therefore actively counted as **undiagnosed**.
- **The 15 values, verified by diffing the Features allowed-values list against the mapping keys myself** (8 structural array keys and `none` excluded): `malaria-continued`, `malaria-continued-recurrent`, `malaria-anemia-continued`, `malaria-anemia-continued-recurrent`, `hyperemesis-gravidum-by-symptoms`, `severe-vomiting-by-symptoms`, `heartburn-persistent`, `pelvic-pain-continued`, `urinary-tract-infection-continued`, `candidiasis-continued`, `gonorrhea-continued`, `trichomonas-or-bv-continued`, `high-risk-of-preeclampsia-initial`, `high-risk-of-preeclampsia-recurrent`, `moderate-risk-of-preeclampsia`.
- **All 15 are producible today.** `resolveSymptomsDiagnoses` (`client/src/elm/Pages/Prenatal/Activity/Utils.elm:3552-3570`) emits the `*Continued`, `*BySymptoms` and `HeartburnPersistent` values on every non-postpartum nurse encounter; `resolveLabResultsAndExaminationDiagnoses` (`:3470-3484`) emits the three preeclampsia-risk values from EGA week 12 for any pregnancy with a known LMP.
- **Two sub-cases with different fixes.** 12 have an obvious base code already in the map (`malaria`→`o`, `malaria-anemia`→`p`, `hyperemesis-gravidum`→`e1`, `severe-vomiting`→`f1`, `heartburn`→`k1`, `pelvic-pain-intense`→`m1`, `urinary-tract-infection`→`n1`, `candidiasis`→`p1`, `gonorrhea`→`q1`, `trichomonas-or-bv`→`r1`), and the map already collapses initial/recurrent pairs onto one code — so collapsing these too is the established convention. The 3 preeclampsia-risk values have no base code and no `PrenatalDiagnosis` constructor in `server/elm/src/Backend/Reports/Model.elm:126-190`, so surfacing them needs a code + constructor + `Translate` row: a product call.
- **Provenance.** The map was written 2025-04-20 (`ce5a984a0`); the `-continued` family predates it (2022-05-22, `e8b22dbbc`) so it was missed at authoring, and the preeclampsia-risk values arrived 2025-07-09 (`f3b8c6437`) after it and were never added.
- ⚠ **The map is baked into the stored `field_reports_data` blob**, so fixing it changes nothing on live until every person is recalculated.
- **Sizing query for the user:** `SELECT field_prenatal_diagnoses_value, COUNT(*) FROM field_data_field_prenatal_diagnoses WHERE field_prenatal_diagnoses_value IN (<the 15>) GROUP BY 1`, per site.
- **Fix shape (guess).** Add the 12 collapsible values pointing at their existing codes; decide the preeclampsia trio separately. ⭐ Worth a guard asserting every allowed value except `none` has a mapping entry — that class check would have caught both misses, and it is the same shape as B-230's encoder⊄decoder round-trip test.

## ✅ Implemented 2026-09-16 — issue #2258, PR #2259

⛔ **The entry's "15 missing values" framing was WRONG, and so was its fix shape.** The user gave the
requirement (2026-09-16): the server app counts *how many different diagnoses were made* during a
pregnancy. Under that rule the 15 split three ways, and **10 of them are correct behaviour today**:

- **10 omitted, not a defect.** Every `-continued` / `-persistent` value is a *reconfirmation* —
  the derivations are literally `<base>Diagnosed && diagnosedPreviously <base>` (and
  `symptomRecorded && symptomRecordedPreviously` for `pelvic-pain-continued`). Giving them a code,
  the base's or their own, would count one condition twice in a pregnancy. Left unmapped, with a
  comment in the mapping function so the next reader does not "fix" it.
- **2 collapsed** onto codes they already share a condition with: `hyperemesis-gravidum-by-symptoms`
  → `e1`, `severe-vomiting-by-symptoms` → `f1`. Neither carries a `diagnosedPreviously` clause; they
  are a first diagnosis by a different route, under an identical EGA gate.
- **3 → 2 new codes** (`m2`, `n2`): high risk of preeclampsia (initial + recurrent collapse, as the
  client's own Translate already does) and moderate risk. Two new report rows, so constructor +
  decoder case + `allPrenatalDiagnoses` + CSS class + Translate + rebuilt bundle.

**Live (2026-09-16, ihangane only — vhw / tip-somalia / uvl all return zero):** the 5 now-mapped
values are 78 records (`hyperemesis-gravidum-by-symptoms` 54, `moderate-risk-of-preeclampsia` 17,
`severe-vomiting-by-symptoms` 7); the 10 correctly-omitted ones are 8 records. Of the 51 encounters
counted as "No Prenatal Diagnosis", **6 carry only reconfirmations** and still will — judged
defensible (no new diagnosis was made there), left alone.

### Repair script added 2026-09-16 (`a144c374b`) — user asked for it rather than a full sweep

`hedley_reports/scripts/recalculate-newly-mapped-prenatal-diagnoses.php` resolves the people carrying
one of the five newly-coded diagnoses (encounter → `field_individual_participant` → participant →
`field_person`) and queues one `HEDLEY_REPORTS_CALCULATE_AGGREGATED_DATA` item each;
`--dry_run` prints the count only. The queue helper dedupes, so a re-run cannot flood it.

**Live sizing (ihangane, 2026-09-16): 78 diagnosis records on 78 encounters, 77 distinct patients,
out of 232,265 published persons — 0.03%.** The other three sites have none of the five.
`generate-data-for-all.php` walks every person; this walks 77, which matters because production
AdvancedQueue is Jenkins-serialised to one worker per site DB ([[prod-advancedqueue-jenkins-serialized]]).

⛔ **Trap found while writing it: `hedley_general_apply_exclude_deleted()` CANNOT be called twice on
one query.** It hardcodes the alias `fd` in both its ON clause and its WHERE conditions, so a second
call gets a Drupal-renamed join (`fd_2`) whose ON clause still points at `fd`, leaving the second
node unfiltered and the first condition duplicated. The script joins `field_data_field_deleted`
itself, once per node alias. ⭐ The script's query was then run as raw SQL against ihangane.live and
returns **77**, matching the independent measurement — the deleted/published filters change nothing
here, but they make the queued set exactly the set the producer would rebuild.

📌 Two caveats recorded for whoever runs it: between deploy and the recalculation the two new rows
read **0** rather than 17, and the worker rewrites a person's whole report blob, not just the
prenatal diagnoses.
