### B-448 — Statistical Queries and Completion apps: a failed data batch is dropped without trace, so the page shows the "in process" placeholder forever — READY · VERIFIED in code (orchestrator read the response handler) · LOW · tier 4 · DEPLOYED · not reproduced
- **Found R38 unit 4.**
- **Mechanism.** The shared sync handler in the server Elm apps maps only the success case; a `Failure` (HTTP error, timeout, decode error) falls through to "do nothing", leaving `remainingForDownload` unchanged:
```elm
-- server/elm/src/Backend/Components/Sync.elm:92-113
handleSyncResponse config data model =
    RemoteData.toMaybe data
        |> Maybe.map
            (\response -> ... if config.getRemaining response == 0 then BackendReturn modelUpdated Cmd.none noError [] else handleSendRequest config (config.getLastIdSynced response) modelUpdated)
        |> Maybe.withDefault (BackendReturn model Cmd.none noError [])
```
  `isSyncComplete` (`server/elm/src/Pages/Components/Utils.elm`) gates every input on `Just 0`, so nothing on the page changes and no retry is offered. Batches are 50,000 JSON blobs each (`HedleyRestfulReportsData.class.php:13`), so a timeout on a large scope is the realistic trigger; request sizes were not measured and no failing request was observed.
- **Reachability.** Any Statistical Queries or Completion results page.
- **Impact.** The operator waits on a page that will never finish and has no way to tell it from a slow one. All sites.
- **Fix shape (guess).** Surface the `Failure` (the `BackendReturn` already carries an `error` slot) and offer a retry of the failed batch.
