### B-405 — The production build runs image optimisation and then throws the result away: all 302 deployed images are byte-identical to source — READY · CONFIRMED (orchestrator byte-compared the whole directory against the deployed artifact) · LOW · tier 4 · R34 unit 4
- **Mechanism.** Two tasks in the same `gulp.parallel` write the same destination paths:
  ```js
  -- client/gulpfile.js:166-179
  gulp.task("images", function() {
    return gulp.src("src/assets/images/**")
      .pipe($.changed("dist/assets/images"))
      .pipe($.imagemin({ progressive: true, interlaced: true }))
      .pipe(gulp.dest("dist/assets/images"))
  ```
  `minify`'s own stream (`gulp.src("serve/**/*.*") … .pipe(gulp.dest("dist"))`) carries `serve/assets/images/*` — the plain copies made by `copy:images` — into the same `dist/assets/images/*`, and `gulp.parallel("minify", "cname", "images")` (`client/gulpfile.js:535`) runs them concurrently with no ordering.
- **Evidence (orchestrator).** Compared every file in `client/src/assets/images/` with `server/.pantheon-ihangane/app/assets/images/`: **302 identical, 0 differing, 0 missing.** imagemin/svgo cannot produce byte-identical output for 302 files, so its result never reaches the artifact — either overwritten by `minify`, or skipped because `gulp.dest` preserves source mtimes and `$.changed`'s `compareLastModifiedTime` then sees no change.
- **Impact.** The production bundle ships unoptimised images to devices that are offline-first and bandwidth-constrained. Secondary: two vinyl-fs write streams on the same path is a genuine (unobserved) interleave hazard.
- **Fix shape (guess).** Either sequence `images` after `minify`, or drop `images` from `publish` and let `copy:images`/`minify` be the only path — the current arrangement claims an optimisation step that does nothing.
