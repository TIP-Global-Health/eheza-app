### B-259 — A freshly opened person form greets the nurse with "Person has been saved" — READY · CONFIRMED (anchors verified) · LOW · tier 4 · R25 unit 5
- **Mechanism.** `Pages/Person/View.elm:547-548` reads `request = db.postPerson`; `:803-812` renders the green success banner when it is `Success _` **and** `Set.isEmpty (Form.getChangedFields personForm)` — the comment says *"We only show the success message until you make changes"*. But `postPerson` is one `WebData PersonId` for the whole app (`Backend/Model.elm:200`), set to `NotAsked` only at model init (`:304`); neither `HandlePostedPerson` nor `HandlePatchedPerson` resets it. Entering the create page fires `ResetCreateForm` (`App/Update.elm:1211`), which empties the form — producing exactly the banner's condition.
- **Reachability.** Register person A → back to the directory → "add person": the empty form opens already showing "Person has been saved", with the semantic `success` class. Same on any edit form opened after any successful save or patch anywhere in the app, including the WhatsApp dialog's patch.
- **Impact.** A misleading confirmation that a registration succeeded when nothing was submitted. All sites.
- **Fix shape (guess).** Reset `postPerson` to `NotAsked` on entry to the create/edit page, beside the existing form reset.
- 📌 Related and traced but not reproduced: `Backend/Update.elm:4431` refuses a `PostPerson` while `postPerson` is `Loading`, and `PatchPerson` also sets `Loading` — so an unrelated in-flight patch can in principle swallow a Save tap. No realistic timing was found with the local service worker.
