### B-625 — Dashboard statistics: the device records the new statistics hash before the statistics are saved, so a failed save leaves stale figures the server does not resend — READY · CONFIRMED by reading (orchestrator read all four hops; nothing run) · LOW · tier 4 · R60 unit 1 · not sized

- **Reachability.** Every sync cycle ends in this lane. The defect needs `table.bulkPut` on `statistics` to fail (`client/src/js/app.js:665-676`) — in practice a full device (`QuotaExceededError`), which the two download lanes already handle by not moving their cursor.
- **Impact.** In memory the new statistics are applied, so the dashboard is right until the page reloads. After a reload the device shows the previously saved statistics (or none, if no save ever succeeded) and keeps sending the new hash, so nothing is resent until the server recalculates that health centre's statistics. All sites. Display staleness only; no uploaded data is touched; it ends at the next recalculation.
- **Not measured.** How often the statistics write is the one that fails, and how long a health centre's hash stays unchanged on a live site. If recalculation is frequent the window is short — check before sizing.
- **Sibling, not filed.** The `DeferredPhotos` save (`Update.elm:308`) is fired by the handler that moves the revision cursor, so a failed save loses that batch's photo rows; on a full device the photo cache writes fail too.
- **Fix shape (first guess):** persist the hash when the `AuthorityStats` save reports success, or blank that authority's hash on `IndexDbSaveFailure` for the table.
