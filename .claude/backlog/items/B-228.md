### B-228 — Acute illness: closing an illness never sets the participant's `dateConcluded`, so Case Management keeps showing the concluded illness until the server-side resolution syncs back — READY · CONFIRMED (anchors verified) · LOW · tier 4 · R24 unit 2
- **Mechanism.** `Backend/IndividualEncounterParticipant/Update.elm:41-47` `CloseAcuteIllnessSession` sets `endDate` + `outcome` only; the TB (:49-61) and HIV (:63-75) siblings also set `dateConcluded = Just currentDate`, prenatal sets it from the user date. Server never sets `field_date_concluded` on an acute-illness participant either (B-174's live census: 23,639 AI participants, ALL empty). The one client consumer is `Pages/GlobalCaseManagement/View.elm:579-587` `generateAcuteIllnessFollowUpEntryData`, which drops the follow-up entry when `dateConcluded < limitDate` — a dead guard, since the field is always Nothing.
- **Reachability.** CHW records the illness outcome (`Pages/AcuteIllness/Outcome/Update.elm` → `CloseAcuteIllnessSession`); the follow-up entry stays listed until `hedley_case_management_handle_update_trigger` resolves the follow-up node server-side and that resolution downloads. Offline devices carry the stale entry for the whole round-trip. Dashboard unaffected (`hedley_stats` derives AI date_concluded from `field_expected` value2 = endDate, post-#2122).
- **Impact.** Stale follow-up rows in Case Management for concluded illnesses between outcome entry and the next full sync; no data loss. All sites.
- **Fix shape (guess).** Set `dateConcluded = Just currentDate` in `CloseAcuteIllnessSession` like TB/HIV (encoder already sends `date_concluded`; sync handler treats it as a date at `HedleyRestfulSync.class.php:~373`). Historical rows stay null and are covered by the server path.
