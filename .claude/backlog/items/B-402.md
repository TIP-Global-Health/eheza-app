### B-402 — A test comment records a "FINDING" that is false — the Labs tab's glucose ranges are not swapped — and two test cases are named after it — READY · CONFIRMED by refutation (orchestrator read the actual strings and the range predicate) · LOW · tier 4 · R34 unit 2
- **The claim.** `client/src/elm/Backend/Measurement/Test.elm:119-121` asserts, in a comment marked FINDING:
  ```elm
  -- client/src/elm/Backend/Measurement/Test.elm:118-121
      -- FINDING: the Labs tab has the fasting/non-fasting thresholds SWAPPED
      -- (it lists non-fasting normal up to 126 and fasting up to 200). The code
      -- matches the clinical convention; the last two cases pin that.
  ```
  and two cases carry it in their titles: `"fasting 150 -> diabetes [Labs tab's >200 fasting would wrongly miss this]"` and `"non-fasting 150 -> not diabetes [Labs tab's >126 non-fasting would wrongly flag this]"`.
- **It is not true.** The displayed ranges match the code arm for arm:
  ```elm
  -- client/src/elm/Translate.elm:20159-20172
          RandomBloodSugarResultNormalRange type_ ->
              case type_ of
                  TestRunBeforeMeal _ ->
                      { english = "74-126 mg/dL (F)"
                  …
                  TestRunAfterMeal _ ->
                      { english = "74-200 mg/dL (NF)"
  ```
  `TestRunBeforeMeal` is selected exactly when `PrerequisiteFastFor12h` is present (`Pages/Report/Utils.elm:301-305`), i.e. it *is* the fasting arm — so the tab shows fasting normal up to 126 and non-fasting up to 200, not the reverse. The predicate agrees:
  ```elm
  -- client/src/elm/Pages/Report/Utils.elm:141-148
  randomBloodSugarResultNormal : RandomBloodSugarResult -> Bool
  randomBloodSugarResultNormal result =
      case result of
          TestRunBeforeMeal value ->
              value >= 74 && value <= 126

          TestRunAfterMeal value ->
              value >= 74 && value < 200
  ```
  which is the exact complement of `diabetesBySugarCount`'s `> 126` / `>= 200`.
- **Impact.** No runtime effect — the two cases test real behaviour and pass. The cost is that the repo carries a false finding in a place a future session will read as evidence, and it was believed once already: the R34 unit-2 scout reported it as a live documentation defect, and only re-reading the strings refuted it. Repo policy (`CLAUDE.md`, "Code Comments") is that comments describe current behaviour.
- **Fix shape (guess).** Delete the FINDING paragraph and rename the two cases after what they actually pin (the fasting/non-fasting split). ⚠ The same comment block also records the `> 126` vs ADA `>= 126` question — that half is a clinical boundary convention, which is a **declined class** ("need a clinician, not a PR"); see the R34 round notes.
