### B-244 — Person edit: saving a person whose photo was not re-taken sends `"photo": null`, and the backend deletes the stored photo — READY · CONFIRMED (full chain traced, both ends verified) · HIGH · tier 2 · R25 unit 5
- **The exact shape B-150 fixed for GPS coordinates, on a key that fix did not cover.**
- **Mechanism, in five verified hops.** (1) The edit form re-seeds the photo from the stored person — `Backend/Person/Form.elm:341` `applyDefaultTextInput photo defaultAvatarUrl identity` — so `avatarUrl = Just "<remote url>"`. (2) `Backend/Person/Encoder.elm:28` emits `( "photo", maybe string person.avatarUrl )`. (3) `PatchPerson` uses `sw.patchFull` (`Backend/Update.elm:4657`), whose full-value encoder puts **every** key in the change row — not just changed ones. (4) `SyncManager/Encoder.elm:112-120` then overwrites that key unconditionally whenever `isJust identifier_.entity.avatarUrl`: `replacePhotoWithFileId` (:85-97) resolves `Dict.get localId record.uploadPhotos |> Maybe.map (…fileId) |> Maybe.withDefault null`, and the upload row exists only if the service worker made one — which it refuses to do for a non-local URL (`client/src/js/nodes.js:1330`, `photosUploadUrlRegex = /\/cache-upload\/images/`, `sw.js:21`). A photo that came *down* from Drupal is a `/sites/default/files/styles/…` URL, so no row → **`"photo": null`**. (5) Server-side, `photo` is **not** in `$ignoredFields` (`HedleyRestfulSync.class.php:400-424`) and B-150's PATCH guard at `:455-459` covers only `latitude` and `longitude`, so the null reaches `setPropertyValues` and empties the image field.
- ⚠ This mechanism is already documented in [[photo-upload-fileid-encoder-wiring]] — *"a missing fileId encodes the image field as null (orphaned photo)"*. What is new is that a plain **edit** reaches it, because `patchFull` re-sends a photo key the user never touched.
- **Reachability.** Nurse → person page → edit → Save (`Pages/Person/Update.elm` `generateMsgsForPersonEdit` → `PatchPerson InitiatorEditForm`). Also every *secondary* patch carrying a DB-loaded person: the child-address propagation in the same function (so a parent's address edit can wipe the **children's** photos) and the WhatsApp/progress-report `PatchPerson` calls. Creation is unaffected — the photo-upload stage runs before entity upload (`SyncManager/Utils.elm:117-129`), so a freshly captured photo does have its row.
- **Impact.** Silent loss of patient identification photos on the backend, then on every device once the null syncs back down. The editing device keeps showing the photo until then (`nodes.js patchNode` writes the URL into local IDB), which is why this can run unnoticed. All sites, no feature flag.
- **Sizing query for the user (read-only, per site):** compare distinct `entity_id` in `field_revision_field_photo` against `field_data_field_photo` for `person` nodes, restricted to nodes whose `changed > created`.
- **Fix shape (guess).** Rewrite the `photo` key only when the change row actually has an upload row, and otherwise drop the key entirely so PATCH leaves the stored file alone. ⭐ A backend null-photo guard for person PATCH — mirroring the coordinates guard right beside it — should go in too: B-150's lesson is that old client builds keep sending the bad payload long after the client fix ships.
- 📌 Untraced tail, same shape: `doEncode` is unconditional for `Photo`, `NutritionPhoto`, `PrenatalPhoto`, `WellChildPhoto`, `FamilyNutritionPhoto` and StockUpdate `signature` (`SyncManager/Encoder.elm:128-162`), so any **re-save** of one of those measurements without retaking the image may null its image too. Only the person path was traced end to end.
