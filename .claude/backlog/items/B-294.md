### B-294 — Nutrition (individual): the assessment stored on the `nutrition_nutrition` measurement goes stale when signs are saved before the last mandatory measurement — the recompute gate compares computed-before vs computed-after, never stored vs computed — READY · CONFIRMED (gate + save source + card order + all consumers re-verified; **269 live divergent encounters on ihangane**, 2026-09-01) · MED · tier 3 · R27 unit 3
- **Mechanism, two halves.** (1) At save time the assessment stamped onto the signs value is computed from SAVED measurements only: `viewNutritionContent` (`Pages/Nutrition/Activity/View.elm:306-331`) computes `assessment = generateNutritionAssessment currentDate zscores db assembled |> nutritionAssessmentForBackend` — the just-ticked signs live only in the form, and a not-yet-saved weight is absent — and `SaveNutrition` persists it. (2) The compensating recompute `generateNutritionAssessmentIndividualMsgs` (`Backend/Update.elm:9491-9587`, fired per measurement revision) does nothing while any mandatory activity is missing, and afterwards rewrites the stored fields only when `assessmentChanged = not (everySetsEqual assessmentBefore assessmentForBackend)` — computed-from-db-BEFORE-this-revision vs computed-AFTER, never stored-vs-computed. In the encounter page's own card order — `allActivities = [ Height, Muac, Nutrition, Weight, … ]` (`Backend/NutritionActivity/Utils.elm:104`) — the signs save while Weight is missing (no recompute), and when Weight lands last, `assessmentBefore` already contains the signs/MUAC-driven assessments, so a normal weight makes before == after → no rewrite. The stored `field_nutrition_assesment` on `nutrition_nutrition` keeps whatever was computable at signs-save time — typically `none`.
- **Unaffected surfaces.** The warning popup and Next Steps use the freshly computed `assessmentAfter`; the FollowUp measurement gets a correct assessment at `SaveFollowUp` (computed at click time). That divergence between the two stored copies is the live signature: **269 encounters** on `ihangane.live` where `nutrition_nutrition`'s stored assessment ≠ `nutrition_follow_up`'s (SQL in this entry's sizing note).
- **Consumers of the stale field.** (a) Completion report: `hedley_reports.module:3449-3468` prefers `nutrition_nutrition`'s value and falls back to follow-up only when the nutrition measurement is ABSENT — a stale `none` there means "no next-steps expected", so an assessed encounter reads complete without next steps. (b) Child scorecard: `hedley_ncda.module:928-947` matches `malnutrition-moderate/severe` against this field for the "malnourished referred to HC" row. (c) Client: `filterNutritionAssessmentsFromNutritionValue` (`Measurement/Utils.elm:10053-10075`) feeds progress-report nutrition-assessment entries. Corroboration the field is known-unreliable in production: `hedley_admin/scripts/populate-nutrition-assessment.php` exists solely to copy the FollowUp assessment onto the Nutrition measurement (group + individual) — and it is not one of the two daily Jenkins scripts, so the client keeps re-creating what it backfills.
- **Untraced sibling.** The GROUP flow shares the identical gate (`Backend/Update.elm:9651-9652`, `:9726-9727`); whether its save path stamps a fresher value was not traced.
- **Fix shape (guess).** Gate the rewrite on stored-vs-computed (`measurement.value.assesment /= assessmentForBackend`), or include the form's signs in the value `SaveNutrition` stamps. One test with the Height→Muac→Nutrition→Weight order discriminates.
- **Sizing (run 2026-09-01, ihangane: 269).** `SELECT COUNT(*) FROM (SELECT ne.field_nutrition_encounter_target_id AS enc, GROUP_CONCAT(DISTINCT CASE WHEN n.type='nutrition_nutrition' THEN na.field_nutrition_assesment_value END) AS on_nutrition, GROUP_CONCAT(DISTINCT CASE WHEN n.type='nutrition_follow_up' THEN na.field_nutrition_assesment_value END) AS on_follow_up FROM node n JOIN field_data_field_nutrition_encounter ne ON ne.entity_id=n.nid JOIN field_data_field_nutrition_assesment na ON na.entity_id=n.nid LEFT JOIN field_data_field_deleted d ON d.entity_id=n.nid WHERE n.type IN ('nutrition_nutrition','nutrition_follow_up') AND COALESCE(d.field_deleted_value,0)=0 GROUP BY enc HAVING on_nutrition IS NOT NULL AND on_follow_up IS NOT NULL AND on_nutrition <> on_follow_up) x;` — vhw/uvl not yet run.
