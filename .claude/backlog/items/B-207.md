### B-207 — Dashboard donut charts: a period with no children renders every slice as "NaN%" — ✅ IMPLEMENTED 2026-08-24 (issue #2139, PR #2140) · CONFIRMED · tier 4 · found by `/code-review medium` on PR #2136
- `viewDonutChart` (`Pages/Dashboard/View.elm`) guarded with `if List.isEmpty data`, which tests whether the chart has ROWS, not whether those rows hold anything. With every slice at 0, `viewPieChartLegend` computes `round (100 * toFloat usage / totalSigns)` with `totalSigns = 0`; `0 / 0` is NaN and `String.fromInt` renders it literally, so the legend reads "On Track (NaN%) / Behind (NaN%)". `Shape.pie` over all-zero values also yields NaN arc angles, so the ring does not draw.
- ⭐ **Consumer sweep done before choosing where to fix — only ONE path was vulnerable:**
  - **Fevers by Cause** builds `chartData` with `List.filter (Tuple.second >> (/=) 0)` applied first, so its list genuinely IS empty when there is no data and the original guard fired correctly. That filter is also the evidence the guard was written expecting zero-filtered input.
  - **ECD and Immunization** (Child Wellness) pass a fixed slice per category, so they reach the guard with a non-empty list of zeros. These are the defect.
  - **Family planning** calls `viewPieChartLegend` DIRECTLY, bypassing the donut guard, but builds its rows from `getFamilyPlanningSignsCounter` — a counter, so counts are never 0 — and `Dict.isEmpty dict` guards the empty case, where `List.map` over `[]` renders no rows rather than NaN. Not vulnerable, so the legend's arithmetic was left alone.
- **Fix:** `if List.all (Tuple.second >> (==) 0) data`. `List.all` on an empty list is `True`, so the previous empty-list behaviour is preserved exactly; a chart with any non-zero slice still draws, including its zero-valued slices.
- **Verified:** `elm make` 548 modules · `elm-test` 2,986 pass · `elm-format --validate` clean · elm-review on the committed state in a fresh clone, 0 errors.
- 📌 **No unit test, deliberately.** `viewDonutChart` is not in `Pages.Dashboard.View`'s exposing list (`exposing (chwCard, view)`), and the runbook's R5-1/R6-1 precedent is explicit: do not expose view helpers purely to unit-test a trivial change. Compile plus suite regression is the gate here.
- 📋 **Review outcome (`/code-review medium donut-no-data-guard`, 2026-08-24): clean on the diff.** The reviewer independently checked that `List.all (Tuple.second >> (==) 0) []` is `True` so the empty case is unchanged, and that all three callers derive counts from `List.length`, so no mixed-sign path can sum to zero and still divide by zero in the legend.
- ❌ **One adjacent finding REFUTED as filed** — `viewFamilyPlanningDonutChart:2224` guards on `Dict.isEmpty dict` while drawing `signs`, which filters `NoFamilyPlanning` out, so an all-`none` period renders a blank ring past the guard. **Mechanism verified; the proposed remedy is wrong.** In that case there IS data: the chart centre correctly reads `0%` and "0 out of N women", computed from `totalWomen`/`totalNoFamilyPlanning`, which the `signs` filter does not touch. Showing "No data for period" would be FALSE and would replace a real clinical signal (nobody reported using family planning) with an absence of one. ⭐ **The distinction that matters: the ECD donut fabricated a number (`NaN%`) where it had nothing to say; the family-planning donut shows correct numbers beside an empty ring.** What remains is cosmetic, and the fix would be a design decision about drawing an all-zero-usage state, not a guard change. Live: `none` is 31,248 of 231,479 family-planning rows (13.5%), so an all-`none` period is reachable only in the small-N tail. Filed at file level on PR #2140 (line not in the diff).
