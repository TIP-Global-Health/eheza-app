### B-407 — `.ddev/config.local.yaml.example` is not in the "default state" both deploy skills tell the operator to expect, so a station built from it reinstalls and wipes its local DB on every `ddev restart` — READY · CONFIRMED (orchestrator read both the example and both skills) · LOW · tier 4 · R34 unit 4
- **The contradiction.** Both skills say:
  > **No (default):** ensure the `post-start` hook in `.ddev/config.local.yaml` is in its default state (only `- exec-host: ddev client-install` active; everything below commented). No reinstall.
  (`deploy-release/SKILL.md:72`, `deploy-multidev/SKILL.md:75`, echoed in `_deploy-common/deploy-reference.md:71-84`.)
  The shipped example has **32 uncommented `- exec` lines** in that block, including the full reinstall:
  ```yaml
  -- .ddev/config.local.yaml.example:28-40
    post-start:
      - exec-host: ddev client-install
      - exec: "cd .. && chmod +x ./scripts/build && ./scripts/build"
      …
      - exec: drush site-install -y hedley install_configure_form.update_status_module='array(FALSE,FALSE)' …
  ```
  It has to stay that way, because CI builds its config by concatenating the example verbatim (`ci-scripts/install_drupal.sh:9-11`).
- **Impact.** A station set up by following CLAUDE.md's Local Setup (`cp .ddev/config.local.yaml.example .ddev/config.local.yaml`) has a config in which **every `ddev restart` reinstalls and wipes the local DB** — including the mandatory restart in Step 2 of both deploy skills, whose "default No" branch the operator believes is a no-op. Site-specific: the reinstall re-migrates for whatever `EHEZA_SITE` is set, so the developer silently loses their current site's local data. Dev-only; no patient data.
- **Fix shape (guess).** Either ship the example commented and have CI uncomment what it needs, or change the skills and CLAUDE.md to describe the state the file is actually in. The two must stop disagreeing; which one moves is the user's call.
