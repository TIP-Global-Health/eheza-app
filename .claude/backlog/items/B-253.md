### B-253 — Pregnancy Outcome page reads an arbitrary encounter instead of the latest, so Gravida and Para can render as `----` — ✅ IMPLEMENTED · CONFIRMED (anchors verified; B-214's helper) · LOW · tier 4 · R25 unit 3
- **Mechanism.** `Pages/Prenatal/Outcome/View.elm:31-34` and the identical block in `Outcome/Fetch.elm:20-24` call `Backend.NutritionEncounter.Utils.getPrenatalEncountersForParticipant` — a plain `Dict.toList` (`:350-360`, **B-214's anchor**) — then `List.reverse |> List.head`. The prenatal-specific wrapper `Pages/Prenatal/Encounter/Utils.elm:277-280` exists precisely to add `List.sortWith sortEncounterTuplesDesc`, and every other prenatal "latest" consumer uses it (`Participant/View.elm:103`, `PatientRecord/View.elm:548`, `GlobalCaseManagement/View.elm:728`). The Outcome page is the copy that was not updated, so it yields the UUID-last encounter, not the most recent.
- **Traced consequence.** EDD/EGA survive, because `resolveGlobalLmpValue` (`Encounter/Utils.elm:222-235`) chains `orElse` down to the CHW value and `generatePreviousMeasurements` filters on id, not date. Gravida/Para do not: `resolveGlobalObstetricHistory` (`:261-274`) has **no** such fallback and reads only `List.head nursePreviousMeasurements`. When the arbitrarily-picked encounter happens to be the earliest nurse encounter, that head is a later encounter — and a later encounter can never hold obstetric history, because `expectHistoryTask` (`Pages/Prenatal/Activity/Utils.elm:903-922`) gates `Obstetric` on the first encounter. - **Impact.** Two clinical summary fields blank on the outcome form. The save itself is keyed on the participant id (`Outcome/Update.elm`, `ClosePrenatalSession`), so **no wrong data is written**.
