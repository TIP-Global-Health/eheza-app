### B-406 — Every precache revision in the shipped service worker is the hash of the file *before* minification, so a minifier-only change is invisible to installed devices — READY · CONFIRMED (orchestrator verified against the deployed artifact, with a clean control) · LOW · tier 4 · R34 unit 4
- **Mechanism.** `pwa:dev` generates the service worker from `serve/` (`client/gulpfile.js:465-491`, `globDirectory: 'serve'`), and `minify` only afterwards rewrites those files into `dist/`. So every revision in `precacheAndRoute` describes bytes that never ship.
- **Evidence (orchestrator, deployed ihangane artifact).** `service-worker.js` says `url:"Main.js",revision:"005e20ccc272dd8641bad06378921357"` while `md5sum app/Main.js` is `532c5160254a37e6b8218ca9d138a02d`. ⭐ The control is exact: `app.js` is on the uglify exclusion list, and its manifest revision `c70d744ce690efdaa5804280b0c82a08` **equals** its deployed md5 — so the divergence is minification, not the hashing.
- **Impact.** Low and not user-visible today: workbox uses the revision only as a change token and does not verify integrity, and the token still changes whenever the source changes. The narrow exposure is a change confined to the *minifier* — a config change or a gulp-uglify bump — which produces different shipped bytes under an unchanged revision, so every already-installed device keeps the stale precached copy indefinitely. That is the one failure mode an offline-first PWA cannot recover from without a manual cache bust, and nothing forces a PWA update ([[B-168]]).
- **Fix shape (guess).** Generate the service worker from `dist/` after `minify`, or accept it and record the constraint where the next person will read it.
