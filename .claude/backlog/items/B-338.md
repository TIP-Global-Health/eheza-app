### B-338 — Prenatal labs (lab technician): a blood smear declined and then corrected is recorded as a RAPID TEST, so a positive answer diagnoses malaria from a test nobody ran — ✅ IMPLEMENTED 2026-09-10 (issue #2226, PR #2228, branch `B-338-smear-order-memory`, base develop; merged `91386895c`) · CONFIRMED (form hydration → view branch → save → diagnosis predicate read; live-counted, and the signature is already present 9 times on ihangane) · MED-HIGH · tier 1 · issue #2226 · found by B-319's review round 3, 2026-09-09
- **Mechanism.** The record keeps no memory that a blood smear was ordered once someone declines it. `bloodSmearTaken` is derived from the SAVED value alone, and `BloodSmearNotTaken` is not in the list that makes it true (`Measurement/Utils.elm:7595-7603`, and `:7626` `bloodSmearTaken = bloodSmearTakenByValue`). A decline writes `BloodSmearNotTaken` (`toMalariaResultValue:7658`, `Maybe.withDefault BloodSmearNotTaken form.bloodSmearResult`), so on reopen `bloodSmearTaken` is False and `malariaResultFormAndTasks:4518-4527` renders `standardTestResultInputsAndTasks` — the RAPID TEST's result list — instead of the smear's. Saving stores that answer as `testResult` under `TestNoteRunConfirmedByLabTech` (`:7647`), which `testPerformedByExecutionNote` accepts, so branch 1 of `positiveMalariaTest` (`Pages/Prenatal/Activity/Utils.elm:2177-2195`) reads it as a genuine RDT ⇒ a Positive answer diagnoses malaria from a rapid test the nurse never ran.
- **Reachability is unambiguous.** A nurse who declines the RDT and takes NO smear never reaches this form: `testPrerequisites` stays `Nothing`, so `expectUniversalTestResultTask` is False. Arriving here with `bloodSmearTaken = False` and a why-not note therefore means one thing only — a smear order that was declined. A genuine RDT sent to the lab arrives with note `run-today`, which is the case that must keep the RDT select.
- **Live (all four sites, 2026-09-09).** `prenatal_malaria_test` where note = `run-confirmed-by-lab-tech`: ihangane has **9 records with smear `not-taken` AND `field_test_result = negative`** — the signature exactly, a rapid-test result stored for a test never run — plus 1 with both fields set. **vhw, tip-somalia and uvl have zero**; only Rwanda's lab technicians work this flow. All ten are negative, so nothing has been misdiagnosed yet; what exists is ten false "rapid test was run" records.
- ⭐ **B-319 produced the first step of every one of them.** Until PR #2224 lands, the lab technician's tab opens pre-answered "No" with the nurse's reason ticked, so the decline happened by ACCIDENT; this defect then turned each correction into a false rapid-test record. The two are one chain, and #2224 removes the accident but not this.
- **Fix shape (guess).** One line, no schema change: treat a test whose note says the RDT was not performed as a smear —
  `bloodSmearTakenByValue = (not <| testPerformedByExecutionNote value.executionNote) || List.member value.bloodSmearResult [ ...the five... ]`.
  Checked against every state that reaches this form: RDT genuinely at the lab (`run-today`/`not-taken`) keeps the RDT select; declined order (why-not/`not-taken`) switches to the smear select; pending order and read smear are unchanged. The alternative — a new `BloodSmearResult` variant meaning "ordered, then declined" — costs an Elm type, decoder, encoder, the PHP allowed-values list and a migration, and buys nothing this does not.
- ⛔ **Stacks on B-319 / PR #2224** — both edit `malariaResultFormWithDefault`, and the accident that starts this is only removed once #2224 merges.
- ⚠ **Ten existing ihangane records carry a false `field_test_result`.** After the fix they reopen showing the smear select while that stale RDT result stays in the record. All are `negative`, so no diagnosis is affected; whether to clean them up is a separate decision for the user.
