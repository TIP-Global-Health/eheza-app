### B-478 — Service worker: a change is stored on the device before its upload row, so when the row fails the device keeps a change the server never receives — READY · VERIFIED (code read + Node harness; raised as finding 2 in the medium review of PR #2345) · tier 3 · DEPLOYED · ⚠ gated on PR #2345's field reports
- **Found 2026-10-13** in the review of #2345 (B-168), round 1, finding 2.
- **Mechanism.** `patchNode` / `postNode` (`client/src/js/nodes.js`) run `table.update` / `table.put` and `sendRevisedNode` BEFORE the `db.transaction` that adds the `shardChanges` / `nodeChanges` row. When that add fails twice, the inner `catch` builds a 400 and the following `.then` replaces it with the 200 — so the page and the device show the change, and nothing uploads. A missing node rejects with a non-Response → `Http.NetworkError` at the page.
- **Impact.** Unknown in the field; #2345 makes it measurable (`Dropped <method> <type> <uuid>: upload row not stored` in Rollbar). Leading suspect for B-168's EDD drops.
- **Fix shape (built once on the branch as `9210e8361`, then pulled out — user 2026-10-13 agreed it was too risky for a diagnostic):** one `saveChange` writing the node and the upload row in ONE transaction, sending the node to the page after commit, answering 400 with `String(err)` on any failure (retry dropped). Changes EVERY local save; needs a real-browser failure test (inject a failing `shardChanges` creating hook in DevTools) and a look at how each Save screen handles a 400 (Person form keeps the form → retry must not duplicate, which the rollback guarantees).
- **Gate:** build only if #2345's reports show upload-row failures in the field.
