### B-318 — Sync: the dashboard-statistics download has no timeout and no elapsed-time guard, so one stalled request wedges uploads and downloads until the app is reloaded — ✅ IMPLEMENTED 2026-09-24 (issue #2290, PR #2291, branch `B-318-stats-download-timeout`, base `d7a357439`) · CONFIRMED (guard + GET read against the three sibling lanes) · MED · tier 2 (⬆ from 3, 2026-09-24) · R28 unit 1 · ⭐ DEPLOYED (all sites)
- ⬆ **Re-tiered 3 → 2 by the user, 2026-09-24** ("Move all t2 candidates to t2"): the same upload/download wedge class as B-025, which was tier 1.
- **Mechanism.** `client/src/elm/SyncManager/Update.elm:328-333` `BackendAuthorityDashboardStatsFetch`: `if RemoteData.isLoading webData then noChange`. The two other download lanes guard with `isLoading webData && (elapsed < downloadRequestTimeout)` (`:120-123`, `:682-685`); the three upload POSTs carry `HttpBuilder.withTimeout uploadRequestTimeout` (`:1266`, `:1459`, `:1611` — added by `e1026cbdb` for exactly this wedge, B-025). The stats GET (`:364-373`, `/api/sync/<hc>?statistics=1`, a multi-hundred-KB payload) has neither; elm/http's default timeout is none. `determineSyncStatus` (`Utils.elm:316-343`) leaves this status unchanged unless `Success`, and `TrySyncing`/`BackendFetchMain` re-enter only through this branch, which returns `noChange` while Loading.
- **Same gap, lower impact:** `BackendDeferredPhotoFetch` GET (`:1785-1788`) has no timeout and `FetchFromIndexDbDeferredPhoto` returns `noChange` while `isRecordLoading` — only the photo lane stalls.
- **Reachability / impact.** Every sync cycle ends with this GET per authority (`Utils.elm:305`). A stalled mobile link during it: no uploads (measurements stay on the device), no downloads, Device page shows "Downloading" forever, until reload. Same class and same accepted remedy as B-025.
- **Fix shape (guess).** Mirror the siblings — `withTimeout` on the stats GET (and the single-photo GET) and/or the `downloadRequestTime` elapsed check on its `isLoading` guard.
- ✅ **IMPLEMENTED 2026-09-24 (issue #2290, PR #2291).** Stats GET gets `HttpBuilder.withTimeout`; `uploadRequestTimeout` renamed `transferRequestTimeout` (60 s, shared). Chose timeout over the elapsed-time guard: the stats handler carries no `requestTime`, so a late reply from an abandoned request would be accepted; a timed-out XHR is cancelled. `Failure Timeout` is left in place by `determineSyncStatus`, and the next tick re-issues. Verified: elm-format, elm make (548), elm-review, comment check. Not browser-run (shared app). Photo GET deliberately left out → [[B-435]].
- 🔁 **Review round 1 (medium, 2026-09-24): 1 finding, fixed in `2562c87a1`.** A 60 s whole-transfer timeout would fail a slow link's several-MB stats download on every cycle, and `determineSyncStatus` left this step only on `Success`, so uploads never restarted. Live size (ihangane.live, serialized cache, 14 HCs): avg 2.9 MB, p90 7.4 MB, max 9.3 MB. Fix: a stats `Failure` marks the authority `Error` and advances like `Success` (this also ends the pre-existing wedge on a stats 500/`BadBody`); own `statisticsRequestTimeout` = 5 min; rename reverted. 2 new `SyncManager/Test.elm` cases fail on the pre-fix code. 📌 Not changed: a failure that ends the cycle after >45 s still schedules the page refresh (pre-login pages only), as a slow success already did.
