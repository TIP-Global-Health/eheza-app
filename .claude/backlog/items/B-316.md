### B-316 — Z-score tables: a failed table download on first load is never retried and never shown, so growth charts render without curves and nutrition assessments run without z-scores until the app is reloaded — READY · CONFIRMED (fetch guard + consumers read; frequency unknown) · LOW · tier 4 · R28 unit 6
- **Mechanism.** `client/src/elm/ZScore/Update.elm:78-84` (and siblings) fetch a table only `if isNotAsked model.<table>`; a `Failure` is sticky until reload. Every chart renders with `RemoteData.withDefault []` reference data (`ZScore/View.elm:799` etc.) and every `zScore…` helper returns `Nothing` via `RemoteData.toMaybe`. No view reads the load status (nothing outside `ZScore/` inspects `zscores.*`).
- **Reachability.** `App/Update.elm:224` issues `FetchAllTables` at configuration time; the six JSON files are precached by the service worker (`gulpfile.js:445-452`), so this needs a network failure on FIRST load before precache completes. Not sized — a traced error path, not an observed problem.
- **Impact.** Silent for the session: charts without curves, and the stored nutrition assessment (B-294's field) computed without the underweight/stunting/wasting z-verdicts. **Fix shape (guess).** Also fetch when `RemoteData.isFailure`, or surface the state.
- 📌 **Live check 2026-10-13 (orchestrator, ihangane, user asked "does it really happen on live").** Signature searched: an assessment stored WITHOUT `underweight-severe` while the server's own `field_zscore_age` on the same encounter's weight is ≤ −3 (the client rule is unconditional at that point) and the weight node precedes the assessment node. Individual nutrition: 13 of 204 such pairs, 6 pre-2021 with an empty assessment (field not yet written then), 2 disproved (the same nurse stored underweight verdicts on other children that day, so the tables were loaded), 5 undecidable (2022-09, 2022-10, 2024-01, 2024-10, 2025-12: each the only severe-z child of its session, one with the weight edited after the assessment). Well Child: 0 of 10. The 5 are equally explained by [[B-294]]'s broken recompute gate, which is the simpler cause. No telemetry exists for a failed table fetch (`ZScore/` never reports to Rollbar), so the question cannot be settled from live data; kept at tier 4. A Rollbar report on table-fetch `Failure` is the cheap way to find out.
