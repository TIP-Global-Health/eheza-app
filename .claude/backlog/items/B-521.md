### B-521 — Patient search by National ID: spaces and separators must be typed exactly as stored, so a Rwanda ID typed with the card's spaces, or a Burundi ID typed with "-" for "/", finds nobody — READY · PLAUSIBLE (code read; no live count of stored spacing/leading spaces) · LOW · tier 4 · side finding of B-382 (PR #2450, review round 1, findings 1–3)
- **Found 2026-11-01** in round 1 of PR #2450, which lets the National ID search take any character.
- **Mechanism.** The device matches the start of the stored value, ignoring case only:
  ```js
  -- client/src/js/nodes.js (PR #2450)
                              return table.where('national_id_number').startsWithIgnoreCase(nationalIdContains).distinct().and(function (person) {
  ```
  The `national_id_number` index holds the value as stored. Rwanda stores 16 digits (validated), but its card prints them with spaces; Burundi and Somalia store free text, untrimmed (`nullable string`), with `/`, `-` and spaces (B-382's uvl counts: `/` 2,355, `-` 351, spaces 13). The query is trimmed (`FetchPeopleByNationalId trimmed`), so a stored leading space never matches either.
- **Before PR #2450** none of these could be typed at all (the field froze on the first non-digit), so this is not a regression; it is what remains after it.
- **Impact.** A nurse who types an ID with different spacing or separators sees "no results" and may register a duplicate. Not measured.
- **Fix shape (guess).** Index a normalised key — lowercased, with whitespace and separators removed — the way `name_search` is built by `gatherWords`, and normalise the query the same way. Needs a Dexie schema version bump, so its own PR.
