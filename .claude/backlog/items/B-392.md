### B-392 — The duplicate-referral guard now reads a history that cannot contain the encounter it reports to, so a rhesus-negative or diabetes result entered late sends the nurse to refer a patient to hospital a second time — ✅ IMPLEMENTED (issue #2272, PR #2273, branch `B-392-report-back-guard-asks-origin`) · CONFIRMED (orchestrator traced all five links in source; the changed input is scout-run-verified via the shipped test harness) · MED · **tier 1** (care pathway) · R33 unit 1 · **introduced by the B-364 merge, NOT yet deployed** (origin/main is v1.18.2, release #2128 open)
- **Mechanism.** When a lab result is entered for an older encounter A through a later encounter C's labs-history page, the result is saved onto **A** with `originatingEncounter = Just C`, and the assessment reports the added diagnosis back to **C** as a past diagnosis. Two guards exist to suppress that report when the diagnosis is already known, and their comments say exactly why:
  ```elm
  -- client/src/elm/Backend/Update.elm:8865-8887
                                  if
                                      (-- Reporting back about previous diagnosis results in hospital referral
                                       -- at Next steps. For Diabetes, we have logic saying that when it's first
                                       -- diagnosed, the patient is referred to hospital.
                                       -- On next occasions, no next steps are required.
                                       -- Therefore, if we know that Diabetes was already diagnosed, we will not
                                       -- report back about this diagnosis, to prevent unnecessary referral to the hospital.
                                       diabetesDiagnosed
                                          && Pages.Prenatal.Utils.diagnosedPreviouslyAnyOf Pages.Prenatal.Utils.diabetesDiagnoses assembledAfter
                                      )
                                          || (rhNegativeDiagnosis
                                                  && Pages.Prenatal.Utils.diagnosedPreviouslyAnyOf
                                                      [ DiagnosisRhesusNegativeInitialPhase
                                                      , DiagnosisRhesusNegativeRecurrentPhase
                                                      ]
                                                      assembledAfter
                                             )
                                  then
                                      []
  ```
- **The five links, each verified in source by the orchestrator.**
  1. `assembledAfter` is the assembly of **A**, not of the originating encounter — `generatePrenatalAssessmentMsgs ... id` (`Backend/Update.elm:8739`) is called as `processRevisionAndAssessPrenatalWithReportToOrigin data.encounterId False (Just (originatingEncounterId, ...))` (`:3247`), so `id = data.encounterId` = the encounter the measurement belongs to.
  2. `diagnosedPreviouslyAnyOf` reads **only** `nursePreviousEncountersData`:
     ```elm
     -- client/src/elm/Pages/Prenatal/Utils.elm:89-97
     diagnosedPreviouslyAnyOf diagnoses assembled =
         assembled.nursePreviousEncountersData
             |> List.filter
                 (\data ->
                     List.any (\diagnosis -> EverySet.member diagnosis data.diagnoses) diagnoses
                 )
     ```
  3. Since the merge that list holds only encounters that started on an **earlier day**:
     ```elm
     -- client/src/elm/Pages/Prenatal/Encounter/Utils.elm:291-300
     generatePreviousMeasurements currentEncounter db =
         getPrenatalEncountersForParticipantDesc db currentEncounter.participant
             |> List.filter
                 (\( _, encounter ) ->
                     -- Only encounters that started on an earlier day are history.
                     -- This leaves out the current encounter, and any later encounter
                     -- (a lab result can be entered after the next visit has started).
                     Date.compare encounter.startDate currentEncounter.startDate == LT
                 )
     ```
     So a diagnosis made at a **later** encounter B is invisible to A — and B is precisely where it was made. Before PR #2243 the list held every *other* encounter of the pregnancy, so the guard saw it.
  4. The guard therefore does not fire, and `SetPastPrenatalDiagnoses reportedDiagnoses` is sent to the originating encounter (`Backend/Update.elm:8890-8893`).
  5. `assembled.encounter.pastDiagnoses` drives the initial-phase hospital referral:
     ```elm
     -- client/src/elm/Pages/Prenatal/Utils.elm:2069-2078
     diagnosesCausingHospitalReferralByPastDiagnoses assembled =
         let
             allowedPastDiagnoses =
                 syphilisDiagnosesIncludingNeurosyphilis
                     ++ diabetesDiagnoses
                     ++ [ DiagnosisHepatitisBRecurrentPhase, DiagnosisRhesusNegativeRecurrentPhase ]
         in
         EverySet.toList assembled.encounter.pastDiagnoses
             |> List.filter (\diagnosis -> List.member diagnosis allowedPastDiagnoses)
     ```
     consumed at `Pages/Prenatal/Utils.elm:133` as `byPastDiagnoses`, inside `diagnosesCausingHospitalReferralByPhase PrenatalEncounterPhaseInitial`.
- **Reachability.** A orders a blood-group/rhesus (or random-blood-sugar) test that is never completed → B runs it again, the result is entered at B's own recurrent phase, `DiagnosisRhesusNegativeRecurrentPhase` lands in B's diagnoses and B refers to hospital → at C the nurse's Laboratory activity offers "complete previous tests" for A (`Pages/Prenatal/Activity/View.elm:3885`), she enters A's pending result, `SaveBloodGpRsResult` / `SaveRandomBloodSugarResult` set `originatingEncounter = Just C` (`Pages/Prenatal/RecurrentActivity/Update.elm:1410`, `:1654`) → the guard consults A's history, which no longer contains B → C's Next Steps demands a second hospital referral for a condition already diagnosed and referred. The rhesus comment names this scenario itself ("it's possible to have multiple tests pending, and results can be entered multiple times").
- **Why the two diagnoses differ.** For **diabetes**, pre-merge the matcher's own `(not <| diagnosedPreviouslyAnyOf diabetesDiagnoses assembled)` guard (`Activity/Utils.elm:2871`, `:2879`, `:2886`, `:2894`) also saw B and suppressed the diagnosis on A entirely, so nothing was reported. Post-merge A correctly gets its own diabetes diagnosis — that is B-364's point — **and** the report guard no longer fires. For **rhesus negative** there is no matcher guard, so this was the only thing preventing the duplicate.
- **Evidence.** Scout added cases to the shipped `assembledFromDb` harness in `Pages/Prenatal/Activity/Test.elm` and they passed at `3eef4b666`: a diabetes diagnosis at a **later** encounter gives `diagnosedPreviouslyAnyOf diabetesDiagnoses = False` on A's assembly; same for the rhesus pair; control — the same diagnosis at an **earlier** encounter gives `True`. The shipped `historyBeforeEncounterTest` pins the exclusion independently. The `Backend/Update` path itself was not run (see [[elm-test-cannot-import-backend-update]]).
- **Impact / sizing (orchestrator-relevant).** Both sites, no `EHEZA_SITE` split. **Very rare**: 222 ihangane lab records carry `field_originating_encounter` (69 blood-group, 48 RBS, 81 syphilis, 24 hepatitis B), and in five years `field_data_field_past_prenatal_diagnoses` holds `none` ×42,586 plus exactly one row each of `diabetes`, `rhesus-negative`, `hepatitis-b`, `syphilis`. So the report-back path fires a handful of times ever and the guard has probably never yet been the deciding factor. **Tier 1 on the standing rule — a care pathway determined wrongly — not on population.** It is a documented guard that has silently stopped working, and it is catchable before the release ships.
- **Related, same machinery (recorded, not a separate item).** `updateLabsHistory` sets `originatingEncounter` for only four of ten saves — `SaveSyphilisResult` (`:1317`), `SaveHepatitisBResult` (`:1357`), `SaveBloodGpRsResult` (`:1410`), `SaveRandomBloodSugarResult` (`:1654`); the other six save with no origin and take a different branch. The scary-sounding consequence does not occur: the navigate-to-Next-Steps arm filters on `emergencyReferralDiagnosesInitial`, which holds only `*InitialPhase` variants while a lab result produces `*RecurrentPhase` ones, so the nurse is not thrown into an old encounter's Next Steps.
- **Fix shape (guess, not a spec).** The guard's question is "does the encounter we are reporting **to** already know this?", so ask it of the originating encounter's data rather than of A's history — e.g. assemble `originatingEncounterId` and test its `diagnoses` ∪ `pastDiagnoses` ∪ its own history. Note `diagnosedPreviouslyAnyOf` deliberately ignores `pastDiagnoses`, which is a second reason the guard under-detects: a diagnosis reported to an encounter is invisible to the next report.
- **✅ IMPLEMENTED 2026-09-22 (issue #2272, PR #2273, commit `a70ab257f`).** New `Pages.Prenatal.Utils.diagnosisKnownAnyOf` = history ∪ own diagnoses ∪ `pastDiagnoses`; the two report-back guards in `Backend/Update.elm` call it on the ORIGINATING encounter's assembly (`knownAtOrigin`, built once from `after`), no longer on A's. Five elm-tests via the `assembledFromDb` harness (gained a `pastDiagnoses` field): C sees B's rhesus; A's history cannot (pins the defect); own-diagnosis and past-diagnosis legs; control. Reducing the reader to history-only fails exactly the two new legs. elm make 548, suite 3237/0, elm-review clean. The `Backend/Update` call site is compile-verified only (elm-test cannot import it).
- **Review round 1 (2026-09-22, medium): 1 finding, fixed in `6e85fff17`.** The reader read only previous visits' `diagnoses`, so a diagnosis that entered the pregnancy as a PREVIOUS visit's `pastDiagnoses` (two pending tests of one kind: visit 1's result entered at 2, visit 2's at 3) was still reported and referred again. `diagnosisKnownAnyOf` now applies `knownTo` (own ∪ `pastDiagnoses`) to the encounter and to every `nursePreviousEncountersData` entry; the sixth test case fails on the previous reader.
