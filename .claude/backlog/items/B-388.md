- **Mechanism — optional on the backend, strictly required by the client.** All five geo instances on the `village` bundle are optional:
  ```php
  // server/hedley/modules/custom/hedley_chw/hedley_chw.features.field_instance.inc:36-38
      'field_name' => 'field_cell',
      'label' => 'Cell',
      'required' => 0,
  ```
  (same for `field_province`, `field_district`, `field_sector`, `field_village`; only `field_health_center` is `'required' => 1`). The client decoder admits no null:
  ```elm
  -- client/src/elm/Backend/Village/Decoder.elm:11-19
  decodeVillage =
      succeed Village
          |> required "health_center" decodeEntityUuid
          |> required "label" string
          |> required "province" decodeGeoField
          |> required "district" decodeGeoField
          |> required "sector" decodeGeoField
          |> required "cell" decodeGeoField
          |> required "village" decodeGeoField
  ```
  `decodeGeoField = string |> map (String.toLower >> toTitleCase)` — `null` fails it.
- **The value arrives as an explicit `null`, not as a missing key.** `HedleyRestfulVillages::alterQueryForViewWithDbSelect` LEFT-JOINs each field via `hedley_general_join_field_to_query(..., FALSE)`, which unconditionally adds the column; `HedleyRestfulSyncBase::postExecuteQueryForViewWithDbSelect` then tests `property_exists(...)`, which is true with value NULL. So the JSON carries `"cell": null`. ⚠ This matters because `optional` would tolerate a present null too — only `required` fails on it.
- **One bad entity fails the whole batch** (`client/src/elm/SyncManager/Decoder.elm:350`, `required "batch" (list <| decodeBackendGeneralEntity ...)`). The general lane carries health centres, nurses and villages and runs before the authority lanes, so a jam there stops **all** sync for every device on the site.
- **Reachability.** Any admin creating or editing a village node in the Drupal form and leaving one geo text field blank; also `hedley_migrate/scripts/migrate-villages.php`, which writes `$row[0]`..`$row[4]` verbatim with no trim and no validation.
- **The sibling guard is 400 lines away in the same module**, and its comment spells out the sync consequence it exists to prevent:
  ```php
  // server/hedley/modules/custom/hedley_chw/hedley_chw.module:24-33
  function hedley_chw_node_presave($node) {
    if ($node->type != 'village') {
      return;
    }

    $items = field_get_items('node', $node, 'field_health_center');
    if (empty($items) || empty($items[0]['target_id'])) {
      throw new Exception('A village must be assigned a health center.');
    }
  }
  ```
  The geo fields have no such guard, and their failure mode is strictly worse: a missing health centre makes an INNER JOIN drop the row silently; a missing geo field makes the batch undecodable.
- **Evidence (orchestrator live queries, all four sites).** Zero villages hold a NULL geo field today — ihangane 370, uvl 22, vhw 18, tip-somalia 5, all zero for cell, sector and village. Latent, not firing.
- **This is the recorded "tolerated blank server-side = poison record client-side" shape** (B-108's durable lesson). It is NOT the declined poison-batch class: the proposal is a presave guard that stops the bad record being written, not client-side skip or quarantine.
- **Fix shape (guess).** Extend `hedley_chw_node_presave()` to require the five geo fields the way it already requires the health centre. Making `decodeVillage` tolerate null is the alternative, but `Village` types them as non-optional `String`, so the presave guard is the smaller change. A check that the five names resolve as a chain would also catch [[B-389]].
