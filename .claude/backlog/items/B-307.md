### B-307 — Case Management follow-up entries: tapping one always creates a NEW encounter, so a second encounter can be opened the same day the follow-up was scheduled — ✅ IMPLEMENTED 2026-09-02 (issue #2192, PR #2193, branch `B-307-followup-encounter-same-day-guard`, base develop @db06c9942) · CONFIRMED (traced 2026-09-02 while shipping B-232) · MED · tier 3 · split out of B-232
- **Mechanism.** `StartFollowUpEncounter` (`Pages/GlobalCaseManagement/Update.elm:45-80`) dispatches to five per-program helpers, and every one of them posts a new encounter unconditionally — none checks whether the patient already has an encounter of that type today.

  ```elm
  -- client/src/elm/Pages/GlobalCaseManagement/Update.elm:141-150
  startFollowUpEncounterWellChild currentDate selectedHealthCenter db data =
      resolveIndividualParticipantForPerson data.personId WellChildEncounter db
          |> Maybe.map
              -- If well child participant exists, create new encounter for it.
              (\sessionId ->
                  [ emptyWellChildEncounter sessionId currentDate PediatricCareChw (Just selectedHealthCenter)
                      |> Backend.Model.PostWellChildEncounter
                      |> App.Model.MsgIndexedDb
                  ]
              )
  ```

  The participant pages refuse exactly this. `Pages/WellChild/Participant/View.elm` navigates into today's open encounter instead of creating one, and disables the button outright when one was completed today:

  ```elm
  -- client/src/elm/Pages/WellChild/Participant/View.elm:120-124, 179-181
                              -- Resolve active encounter for person. There should not be more than one.
                              resolveActiveEncounter encounters =
                                  List.filter (Tuple.second >> isDailyEncounterActive currentDate) encounters
                                      |> List.head
                                      |> Maybe.map Tuple.first
  ...
          action =
              maybeActiveEncounterId
                  |> Maybe.map navigateToEncounterAction

  -- client/src/elm/Pages/WellChild/Participant/View.elm:131-140
                              , -- We will not allow create new / edit existing action, if
                                -- there was CHW pediatric care encounter completed today.
                                List.filter
                                  (\( _, encounter ) ->
                                      encounter.startDate == currentDate && encounter.endDate == Just currentDate
                                  )
                                  chwPediatricCareEncounters
                                  |> List.isEmpty
                                  |> not
  ```

  ```elm
  -- client/src/elm/Backend/IndividualEncounterParticipant/Utils.elm:75-77
  isDailyEncounterActive : NominalDate -> { a | startDate : NominalDate, endDate : Maybe NominalDate } -> Bool
  isDailyEncounterActive currentDate encounter =
      encounter.startDate == currentDate && isNothing encounter.endDate
  ```

  So the Case Management tap is the ONLY client path that can mint a second same-day encounter of these types.
- **Reachability.** CHW → Case Management, any of the five panes (nutrition/home-visit, immunization/well-child, acute illness, tuberculosis, HIV). Both sites, no flag.
- **Impact.** Duplicate same-day encounters, and each one is a real encounter carrying its own measurements. Concretely on the immunization pane after B-232 (#2191): the entry is visible on the day it was scheduled, tapping it opens a second Well Child encounter that same day, and because resolution is day-granular that second encounter's `startDate` equals `item.dateMeasured`, so `== GT` is false and **the entry is never cleared** — the child stays on the pane until some unrelated later encounter happens. Raised as a low finding on #2191 and left there by user decision 2026-09-02; the guard is the proportionate fix and it closes that case too.
- **The fetch question is ANSWERED — no new fetch is needed.** `Pages/GlobalCaseManagement/Fetch.elm:190-206` already returns `fetchHomeVisitEncountersMsg`, `fetchWellChildEncountersMsg`, `fetchAcuteIllnessEncountersForParticipantMsg`, `fetchTuberculosisEncountersForParticipantMsg` and `fetchHIVEncountersForParticipantMsg`, so all five `db.*EncountersByParticipant` dicts are populated, and `Backend/NutritionEncounter/Utils.elm:305-345` already exports a `get<Type>EncountersForParticipant` for each.
- **Fix shape (guess).** Give the tap the participant page's rule: if an encounter of that type is active today, navigate into it; if one was completed today, do nothing (or keep the dialog closed). ⚠ Two wrinkles found while tracing: (1) only `startFollowUpEncounterHomeVisit` and `...WellChild` take `db` today — `...AcuteIllness` (`:133`), `...Tuberculosis` (`:157`) and `...HIV` (`:175`) do not, and need it threaded in; the call site at `:52-65` already has `db` in scope, so it is mechanical. (2) TB and HIV have a second branch that CREATES the participant when `data.participantId` is `Nothing` — a new participant has no encounters, so the guard belongs only on the existing-participant arm.
- 📌 Adjacent, not folded in: whether resolution should compare encounter IDENTITY rather than dates is a separate design question, and it applies equally to the nutrition pane that immunization was copied from. With this guard in place it stops being reachable from the client.
