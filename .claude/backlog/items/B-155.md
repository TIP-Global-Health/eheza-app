### B-155 — Retire the phpcs advisory workaround: upgrade the sniffer, and move its configuration into the repo — READY · CONFIRMED (measured 2026-08-06) · MED · release-prep-adjacent, do AFTER the September release
- **Why it exists:** on 2026-08-06 an advisory (PKSA-rdkp-vv9z-mjkg, OS command injection, covers everything `< 3.13.6`) went live on Packagist and composer stopped installing the pinned `squizlabs/php_codesniffer:3.5.6` — `lint_phpcs` died on EVERY branch and on develop, before linting anything. PR #2053 (issue #2052) unblocked it with `--no-security-blocking` on both installs. **That is a deliberate deferral, not a fix.**
- **Risk of leaving it, assessed 2026-08-06 — LOW and bounded, which is why deferring is defensible:** the job runs `cimg/php:7.4.30` over our own source; **no CircleCI contexts are used at all**, and there is no `add_ssh_keys`, terminus, Pantheon credential or deploy step anywhere in `.circleci/config.yml` or `ci-scripts/` — deployment is the local `robo` path. A successful injection lands in a throwaway container with nothing to steal. Residual: developers run the flagged version locally, and `composer audit` will always report it.
- ⚠ **The forcing function is PHP, not security.** 3.5.6 is from 2020 and CI/production are on PHP 7.4 (long EOL). When Pantheon pushes PHP 8, that phpcs will not cope, and this upgrade lands on top of a PHP migration under deadline instead of on its own terms.
- **The upgrade is NOT a one-line bump — measured, not guessed:**
  1. `phpcs 3.13.6` **refuses to load `drupal/coder:8.3.9` at all** (rejects `DrupalPractice\Sniffs\CodeAnalysis\ScopeInfo` as a malformed sniff, aborts per module). Both must move: coder **8.3.31** is the first requiring `^3.13`.
  2. Coder 8.3.31 pulls in `dealerdirect/phpcodesniffer-composer-installer`, a composer plugin that must be explicitly allowed (`composer global config --no-plugins allow-plugins.dealerdirect/phpcodesniffer-composer-installer true`) or the install dies.
  3. With both bumped: **349 findings under `Drupal`, 236 under `DrupalPractice`** over `server/hedley/modules/custom`. Breakdown: **283** "class short comment should describe what the class does" (`hedley_migrate/handlers` + RESTful plugin classes — real doc debt, 283 hand-written sentences); **225** "Unused variable `$plugin`" (**ALL FALSE POSITIVES** — every one is in `hedley_restful/plugins/…` where `$plugin = array(…)` at file scope IS the ctools plugin contract); ~77 real others, 13 files auto-fixable by `phpcbf`.
- ⭐ **The durable half: move the phpcs configuration out of bash arguments into a committed `phpcs.xml.dist`.** Standards, extensions and ignore patterns currently live in `ci-scripts/test_coder.sh`'s CLI, duplicated by every local invocation — which is why the 225 ctools false positives have nowhere to be excluded, and why a local run can silently differ from CI. One ruleset used by both; `VariableAnalysis` excluded for `plugins/*` with the reason.
- **Shape:** one PR for packages + `phpcs.xml.dist` (the upgrade is only safe once the ruleset can absorb the false positives), then `phpcbf` + the ~77 by hand. The 283 class comments are a **product decision**: write them, or exclude that sniff deliberately.
- 📌 **Verification lesson from getting here (cost two wrong answers):** I reported "0 errors, 0 warnings" for the bump when the coder install had SILENTLY FAILED (composer printed its usage banner) and phpcs was linting with no standard loaded — because I counted violation-format lines instead of checking the exit code. **Check `$?`, and beware `cmd | tail` — the pipeline status is `tail`'s, not the command's.**
