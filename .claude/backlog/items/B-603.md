### B-603 — Prenatal › Next Steps › Enrol newborn: if the registration form stays open more than five minutes (or the app reloads on it), the baby is created but never linked to the pregnancy — no error, no report, and the task still reads "not done" — READY · CONFIRMED by reading (orchestrator read the handler, the create page's fetch list, the forget arm and the five-minute loop; not run, not sized) · MED-LOW · tier 3 · DEPLOYED all sites · R56 unit 3
- **Mechanism.** After the person POST succeeds, the newborn link is sent only if the prenatal encounter is still in memory; otherwise the message list is silently empty:
  ```elm
  -- client/src/elm/Backend/Update.elm:4531-4546 (HandlePostedPerson)
                                    PrenatalNextStepsNewbornEnrolmentOrigin _ encounterId ->
                                        let
                                            ...
                                            updateNewbornEnroledMsg =
                                                Dict.get encounterId model.prenatalEncounters
                                                    |> Maybe.andThen RemoteData.toMaybe
                                                    |> Maybe.map
                                                        (\encounter ->
                                                            [ Backend.IndividualEncounterParticipant.Model.SetNewborn personId
                                                                |> MsgIndividualEncounterParticipant encounter.participant
                                                            ]
                                                        )
                                                    |> Maybe.withDefault []
  ```
  The create page never asks for that encounter, so the data-wanted loop forgets it after five minutes:
  ```elm
  -- client/src/elm/Pages/Person/Fetch.elm:45-66
  fetchForCreateOrEdit related initiator db =
      [ FetchHealthCenters, FetchVillages, FetchClinics ]
          ++ (related |> Maybe.map (\id -> FetchPerson id :: fetchFamilyMembers id db) |> Maybe.withDefault [])
          ++ fetchSessionForInitiator initiator
  ...
  fetchSessionForInitiator initiator =
      case initiator of
          GroupEncounterOrigin sessionId ->
              [ FetchSession sessionId ]

          _ ->
              []

  -- client/src/elm/Backend/Fetch.elm:594-595 (forget)
          FetchPrenatalEncounter id ->
              { model | prenatalEncounters = Dict.remove id model.prenatalEncounters }
  ```
- **Reachability.** Prenatal encounter → Next Steps → "Enrol newborn" (`Pages/Prenatal/Activity/View.elm:3772`, opens `CreatePersonPage (Just mother) (PrenatalNextStepsNewbornEnrolmentOrigin birthDate encounterId)`) → fill the form → Save, more than five minutes after leaving the activity page, or after a reload on the form (new version, self-refresh).
- **Impact.** The child and the mother→child relationship are created and the app returns to Next Steps, but `participant.newborn` stays empty. The button is enabled by `isNothing assembled.participant.newborn`, so the task invites a second registration of the same baby (a newborn has no national ID, so no duplicate warning). Server-side, everything keyed on `field_newborn` misses the child (NCDA scoreboard newborn rows — B-313; the Healthy Start dashboards' cohort newborns). How often a registration takes over five minutes is not measured; a data count (pregnancies with a postpartum newborn-enrolment task and a same-day child of the mother but an empty `field_newborn`) would size it.
- **Not B-168.** B-168's diagnostic sits inside `updateIndividualEncounterParticipant` (`set-newborn`); here the message is never dispatched, so it cannot fire. This is B-074's shape (initiator ignored at fetch) for the prenatal initiator, and R52's "fetched for one page, kept for another" lens.
- **Fix shape (guess).** Have the create page keep `FetchPrenatalEncounter encounterId` wanted for this initiator (beside `fetchSessionForInitiator`), or carry the participant id in the initiator so the link does not depend on the cache.
