### B-382 — National-ID patient search accepts only digits, so on Burundi and Somalia it cannot type 99.8% of the IDs that are stored: the field freezes and the search silently runs on the prefix — READY · CONFIRMED (orchestrator read the branch and the validator; live counts on uvl / tip-somalia / ihangane) · MED on uvl, LOW on tip-somalia, none on Rwanda · tier 3 · R33 unit 6 · DEPLOYED
- **Mechanism.** The shared search widget drops any input that does not parse as an `Int`, returning the model untouched:
  ```elm
  -- client/src/elm/Components/PatientsSearchForm/Update.elm:89-97
                      else if isJust (String.toInt input) then
                          ( { model | input = input }
                          , Cmd.none
                          )
                              |> sequence update
                                  [ MsgDebouncer <| provideInput <| SetSearch input ]

                      else
                          ( model, Cmd.none )
  ```
  The digits-only assumption is Rwanda's, and the person form says so out loud:
  ```elm
  -- client/src/elm/Backend/Person/Form.elm:419-429
  nationalIdNumberValidator =
      case site of
          SiteBurundi ->
              nullable string

          -- @todo - needs validation?
          SiteSomalia ->
              nullable string

          _ ->
              validateNationalIdNumber
  ```
  So those two sites store alphanumeric IDs that the search cannot accept. The mode toggle is not site-gated (`Components/PatientsSearchForm/View.elm:23-27`).
- **Two user-visible consequences.** (1) The field freezes: Elm re-renders identical vdom, so the rejected character stays visible in the box while `model.input` keeps only the prefix, and every later keystroke is rejected too because the echoed DOM value still contains it. (2) The search silently runs on the prefix — `Backend/Update.elm:1620-1630` → `ParamsNationalIdContains trimmed` → `nodes.js:974` `startsWith(...)`, capped at 500 results, with no way for the nurse to narrow it.
- **Sizing (orchestrator live queries).** `uvl.live` `field_data_field_national_id_number`, non-empty: **2,434 total, 5 all-digits, 2,429 (99.8%) containing a non-digit** (`/` in 2,355, `-` in 351, letters in 41, spaces in 13 per the scout). `tip-somalia.live`: 3 total, 0 all-digits. Contrast `ihangane.live`: 67,318 total, **2** non-digit — Rwanda is unaffected, which is why this has never been noticed.
- **Relation to B-165.** B-165(b) named this exact desync and its fix line was "echo rejected input back into the model without searching". What shipped (issues #2080/#2082, PR #2085) fixed the empty case and the numeric case; the `else -> ( model, Cmd.none )` branch is still there. So part of B-165(b) is residue — but the Burundi/Somalia angle, which is what turns a typo-recovery nit into a mode that cannot be used at all, is not in B-165 and B-165 is closed at tier 4.
- **Fix shape (guess).** Two separable pieces: always store the typed `input` so the box and the model cannot diverge, gating only whether the debounced `SetSearch` is emitted; and make the plausibility test site-aware by reusing the site's own `nationalIdNumberValidator` instead of `String.toInt`. Whether non-Rwanda sites should simply accept any non-blank string is a decision for the implementing session.
