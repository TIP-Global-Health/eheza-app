- **Reachability — two routes.**
  - **Any photo-bearing type** (person registration photo, the five photo measurements, stock-update signature): the nurse saves between the photo lane's "none" and the authority lane's last empty query for that shard. The lane loops until the shard is empty (`SyncManager/Utils.elm:249-273`), so it picks up rows added meanwhile. Window ≈ the time the pending changes take to upload, once per cycle.
  - **Group-session child pages — the window stays open for the whole visit to the page.** `determineSyncStatus` freezes the status there:

    If the page is opened while the status is `SyncUploadAuthority`, it stays there; the tick still dispatches `FetchFromIndexDbUploadAuthority` (`Update.elm:592-598`), which only checks `isRecordLoading` (`Update.elm:1166-1199`), so `shardChanges` is re-queried every tick and a photo saved on that page is POSTed before any photo lane can run. On the bulk `ChildPicture` page that is every photo taken until the nurse leaves. The comment says the halt protects photo saving; entered in this state it does the opposite. Entering needs the cycle to be in the authority upload lane at the moment of navigation — seconds per cycle, so not common, but nurses navigate to child pages constantly during a session.
  - Sub-window: the photo row is added in the change row's `onsuccess` (`client/src/js/nodes.js:1365-1366`), so a query between the two sees no photo row at all — same loss.
- **Impact.** Silent, permanent loss of the photo on the server and then on every device; for the four copying plugins, loss of the child's existing avatar too. No error, no incident.
