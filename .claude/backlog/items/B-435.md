### B-435 — Photo download: the single-photo GET has no timeout, and an offline failure leaves it loading, so the photo lane can stall until reload — READY · PLAUSIBLE (read while building [[B-318]]; recovery paths not traced) · LOW · tier 4
- **Found while building [[B-318]] 2026-09-24**, deliberately kept out of PR #2291.
- **Mechanism.** `SyncManager/Update.elm` `BackendDeferredPhotoFetch`: `HttpBuilder.get (result.photo ++ "&access_token=" ...) |> HttpBuilder.send ...` has no `withTimeout`, and the branch returns `noChange` while `backendRemoteData` is `Loading`. `BackendDeferredPhotoFetchHandle` answers a `NetworkError` with `noChange` ("We're offline, so this doesn't qualify as an attempt"), which also leaves `backendRemoteData` at `Loading`.
- **Impact.** Only photo downloads stall; the main sync lanes are unaffected. ⚠ Not traced: whether `SchedulePhotosDownload` / `determineDownloadPhotosStatus` resets the record — re-verify before coding.
- **Trap for the fix.** A `Timeout` is not a `NetworkError`, so adding a timeout makes a slow large photo count as a failed attempt toward the retry limit.
- **Fix shape (guess).** On `NetworkError` / `Timeout`, reset `backendRemoteData` to `NotAsked` without counting an attempt; add a generous `withTimeout`.
