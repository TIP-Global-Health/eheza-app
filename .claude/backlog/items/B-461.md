### B-461 — Client build: `client/yarn.lock` is a second lockfile nothing reads, and it has drifted from `package.json` · CONFIRMED · tooling cleanup, no runtime effect
- **Found 2026-10-11**, out of PR #2323's review (finding on `client/package.json:20`). Not found by a discovery round.
- **The state.** `client/` carries both `package-lock.json` and `yarn.lock`. Nothing uses yarn: no mention in `ci-scripts/`, `.circleci/` or `.ddev/commands/`, and yarn is not installed on the host. CI installs with plain `npm install`:
```sh
# ci-scripts/install_client.sh:20
npm install
```
- **The drift.** On `develop` `yarn.lock` locks elm-test 0.19.1-revision6 while `package.json` asks for `^0.19.2-0` (`^0.19.3-0` after #2323). It was last touched 2026-02-27 (`0270bd3e2`).
- **Why not regenerate it.** `yarn@1.22.22 install --mode update-lockfile` on #2323's files rewrites +458 / −1018 lines, mostly reordering and merged ranges, not elm-test. Every future `package.json` change would need the same churn.
- **Proposed fix.** Delete `client/yarn.lock` in its own PR. `package-lock.json` stays the only lockfile; #2323 regenerates it so `npm ci` works.
- ⚠ In the main tree both lockfiles are `skip-worktree` with local edits (the deploy workaround in [[deploy-multidev-recurring-gotchas]]). Read the committed file with `git show origin/develop:client/yarn.lock`, not `grep` on disk. Deleting a skip-worktree file needs `git update-index --no-skip-worktree` first.
