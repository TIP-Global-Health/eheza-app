### B-247 — Nutrition report: the Elm half throws away edema on well-child encounters, so the same child is SAM at district scope and not-SAM at sector scope — READY · CONFIRMED (both decoders + the wire emitter verified) · MED-HIGH · tier 3 · R25 unit 7
- **Mechanism.** `hedley_reports_nutrition_metrics_to_string` (`hedley_reports.module:1452-1471`) emits edema as the 5th CSV token for **all three** encounter families, well-child included. The PHP report consumes it for all three (`:2447` `'edema' => (isset($encounter_fields[4]) && $encounter_fields[4] === '1')`) and `hedley_reports_categorize_acute_malnutrition` (`:3117-3131`) classifies SAM on `muac < 11.5 || $has_edema`. The Elm report consumes it for group and individual-nutrition encounters but **discards it for well-child**, in two places: `server/elm/src/Backend/Reports/Decoder.elm:790` destructures `[ stunting, underweight, wasting, muac, _ ]`, and `server/elm/src/Pages/Reports/Update.elm:150-156` hard-codes `hasEdema = False` under a comment claiming *"well-child wire doesn't carry edema"* — which is false. `WellChildEncounterData` (`Model.elm:230-235`) has no `hasEdema` field, unlike `NutritionEncounterData`.
- **Why the scope matters.** `hedley_reports_build_statistical_queries_results_app` (`:1741-1745`) attaches the PHP-precomputed `nutrition_report_data` only for `global / province / district / health-center`; for **sector, cell and village** the Elm app computes the report itself (`Pages/Reports/Update.elm:31-40`). So the same child in the same month is SAM in the district table and MAM-or-normal in the sector table.
- **Impact.** SAM undercount, with a matching MAM/normal overcount, at the three narrow scopes, for any child whose bilateral oedema was recorded at a well-child/SPV encounter with MUAC ≥ 11.5 cm. Oedema is a stand-alone SAM criterion, so the error runs in the clinically dangerous direction. All sites; hits the `acute_malnutrition_sam` prevalence and incidence rows.
- ✅ **`familyNutritionEncounterToMetrics` passing `False` is correct** — family nutrition records MUAC only and the PHP sets `'edema' => FALSE` at `:2482`. Well-child is the only mismatched path.
- 📌 **Adversarially checked and CLEAN, recorded so nobody re-chases it:** the wire looks like it swaps positions 2 and 3 (PHP emits `"$stunting,$wasting,$underweight,…"` while Elm reads `[stunting, underweight, wasting, …]`), but the PHP **local variable names are historically misnamed after the measurement rather than the indicator** — `$values['w']` is weight-for-age = underweight and `$values['u']` is weight-for-length = wasting. The docblock at `:1424-1434` states this explicitly. Wire order and both decoders agree.
- **Fix shape (guess).** Give `WellChildEncounterData` a `hasEdema` field, return the 5th token instead of `_`, and drop the hard-coded default. No PHP change and **no data regeneration** — the token is already on the wire and in the stored blobs.
