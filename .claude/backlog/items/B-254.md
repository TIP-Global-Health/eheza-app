### B-254 — Prenatal participant page picks an arbitrary pregnancy when a person has two active ones, so encounters can land on the wrong pregnancy — READY · CONFIRMED (anchors + fetch path + Dexie query verified) · LOW-MED · tier 4 · R25 unit 3
- **Mechanism.** `Pages/Prenatal/Participant/View.elm` `viewActions` filters `prenatalSessions` to active antenatal participants and takes `List.head` with **no sort**. The vendored `AssocList.update` appends new keys (`client/src/elm/AssocList.elm:235`), so `toList` preserves build order; the dict is `Dict.fromList` over the Dexie result (`Backend/Update.elm:564-575`), and that query (`client/src/js/nodes.js:~1050`) is `table.where('[type+person]').anyOf(tuples)` with no `sortBy` — i.e. participant-UUID order. Same shape as B-214, one layer up.
- **Everything on the page keys off that pick:** `maybeSessionId` (which pregnancy a new encounter is created under), `allEncounters` → `nurseEncounters`/`chwEncounters` (which buttons are enabled, whether an open encounter is resumable), `completedEncounts`, and the "Record Pregnancy Outcome" target.
- **Reachability.** Needs ≥2 simultaneously-active antenatal participants for one person. ⚠ **That state exists in production** — B-168 recorded participants 5604393 and 5604395 for person 5528577, created by device 4556 in one upload batch, each with an empty auto-encounter; B-195 and B-199 document the race that mints them. The app's own UI never *offers* a second pregnancy while one is active, so this is anomaly-triggered rather than routine — the finding is about the selection, not a daily occurrence.
- **Impact.** Encounters land on the wrong pregnancy, the other pregnancy's encounters become unreachable from this page, and the outcome form concludes the wrong one. All sites.
- **Fix shape (guess).** Sort the filtered list by `startDate` descending before `List.head`. ⚠ This is a *mitigation* — B-195's duplicate-pregnancy race is the cause, and fixing the selection does not stop the duplicates being created.
