### B-350 — Rollbar (client): sync errors raised before Rollbar is initialised are recorded as "already sent" and never reported — and a device jammed before the General download finishes never initialises Rollbar at all, so the devices Rollbar exists to catch are silent for good — READY · CONFIRMED (JS port branch, the single `rollbar.init` caller, the Elm token gate and the localStorage token restore read by the orchestrator; scout ran the shipped rollbar.umd 2.26.2 in node) · LOW-MED · tier 3 · R30 unit 6 · DEPLOYED, all sites — a monitoring gap of the B-331 class, client side
- **Mechanism.**
  ```js
  // client/src/js/app.js:1822-1841 (logByRollbar port)
          case 'sw':
          case 'sync':
              let result = await dbSync.errorsHash.where('hash').equals(data.md5).limit(1).toArray();
              if (result[0]) {
                // Hash exists, indicating that this message was sent already.
                return;
              }
              rollbar.log(data.message);
              await dbSync.errorsHash.add({ hash: data.md5 });
  // :1843-1847 — the 'db' source queues instead, and init drains the queue
          case 'db':
              await dbSync.dbErrors.add({ error: data.message, version: data.version, isSynced: 0 });
  ```
  `rollbar.init` has one caller (`app.js:1754-1776`, the `initRollbar` port), fired only on the LAST page of the General download:
  ```elm
  -- client/src/elm/SyncManager/Update.elm:751-758
                                  initRollbarCmd =
                                      if List.length data.entities < 500 && (not <| String.isEmpty data.rollbarToken) then
                                          initRollbar { ... }
  ```
  while Elm's gate is only a non-empty token (`App/Update.elm:1548-1553`), and the token is restored from localStorage at boot (`app.js:401`). Before init, `rollbar.log` on the UMD global only writes "Rollbar is not initialized" to the console (scout: returns `undefined`, `node_modules/rollbar/src/browser/core.js:64-70`) — but the hash is stored, and `errorsHash` is never cleared, so the same message is suppressed after init and in every later session. The message carries no location (`App/Utils.elm:72` passes `.error` only), so its md5 is stable.
- **Reachability.** Sync cycle order is UploadPhoto → Screenshot → General → Authority → WhatsApp → DownloadGeneral (`SyncManager/Utils.elm:116-276`), so every upload error in the first cycle after a launch precedes init. A stuck Authority upload stays in `SyncUploadAuthority` and never reaches DownloadGeneral; a General-download decode failure (the B-338 "new enum value jams old devices" class) never reaches the last page. Neither device ever initialises Rollbar.
- **Impact.** The jammed-lane devices are exactly the ones whose errors never arrive. Consistent with what July's triage saw (only post-init download-Authority errors). Scout's other SW note: SW-side rejections that are not `Response` objects reach Elm as `Http.NetworkError`, which Rollbar deliberately ignores — same visibility gap next to B-158.
- **Backlog de-dup.** B-331 (server Sentry SDK absent), B-168 (update visibility), B-158; memory `rollbar-postdeploy-triage-2026-07`. Not recorded.
- **Fix shape (guess).** Queue `sync`/`sw` messages like `db` until init, or store the hash only when a JS-side initialised flag is set; consider initialising from the stored token at boot.
