### B-143 — RoboFile deploy chain swallows its own failures (3 defects, one PR) — ✅ IMPLEMENTED 2026-08-09 (issue #2054, PR #2055, MERGED) · **HIGH · release-prep**
- (a) `server/RoboFile.php:139-141` (verified 2026-08-04): `$push_status = $this->_exec("cd ... && git pull && git add . && git commit ... && git push")->getExitCode(); if ($client_sync_result != 0)` — tests the WRONG variable (already known 0), so a failed pull/commit/push is ignored and `deployPantheonSync()` runs cc/updb/fra against an environment that never got the code. Compounding: NO `git pull` before the rsync (checkout :71, rsync :96/:108, pull only :139 on an already-dirty tree) — two-machine deploys make the pull fail exactly where the failure is swallowed.
- (b) `deployPantheonSync` (:169-186) discards the taskExecStack Result and returns void → `ddev robo deploy:pantheon:sync live` exits 0 even when terminus/updb/fra failed (shell `&&` stops later steps, but the failure is invisible). Fix: `return $task->run();`.
- (c) `:17` + `:160-165`: with `PANTHEON_NAME` unset, sync silently targets `eheza-app.<env>` (not a real site); terminus errors are then hidden by (b). `deployPantheon` hard-requires the var (:32-35); sync should too.
