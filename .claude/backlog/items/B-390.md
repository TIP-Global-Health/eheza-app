### B-390 — A failed GPS capture sends no reply and never clears the last reading, so one household's coordinates are shown and saved as the next person's — READY · CONFIRMED (orchestrator read the port handler, the sole writer and the init value) · MED · tier 3 · R33 unit 4 · DEPLOYED on the three `gps_coordinates` sites
- ⬖ **SPLIT out of [[B-150]], not a new find.** B-150's tail recorded this twice and marked it "STILL OPEN … deliberately left out of #2059" — but B-150 is `IMPLEMENTED`, so the queue never surfaces it. Re-verified at `3eef4b666` and given its own entry so the backlog seat can see it. B-150's own three parts remain fixed.
- **Mechanism — the failure path replies with nothing.**
  ```js
  // client/src/js/app.js:533-553
  elmApp.ports.getCoordinates.subscribe(function() {
    if (!("geolocation" in navigator)) {
      return;
    }
    ...
    navigator.geolocation.getCurrentPosition(
        (position) => { ... elmApp.ports.coordinates.send(result); },
        // Failure is expected (denied / hardware unavailable / timeout); Elm uses Maybe GPSCoordinates.
        () => {},
        options
    );
  });
  ```
  Both the unsupported-API early return and the error callback send nothing back.
- **And the model is never cleared.** `model.coordinates` is initialised `Nothing` (`App/Model.elm:231`) and has exactly **one** writer in the whole app:
  ```elm
  -- client/src/elm/App/Update.elm:1263-1266
          SetGPSCoordinates coordinates ->
              ( { model | coordinates = Just coordinates }
              , Cmd.none
              )
  ```
  Orchestrator grepped every assignment to `coordinates` across `App/Update.elm` and `App/Model.elm`: those two lines are all of them. The two request sites (UrlChanged → `CreatePersonPage`, `EditPersonPage`) call `getCoordinates ()` without clearing first, and `Pages/Person/View.elm` `gpsInfoSection` renders whatever is in `model.coordinates` as the current reading, next to a "save GPS location" checkbox, with no indication of age.
- **Reachability.** Nurse registers person A outdoors (fix arrives) → opens registration for person B in another household → permission denied, 15 s timeout, or no fix → no reply → A's coordinates display as B's and are saved if the box is ticked. `maximumAge: 600000` independently lets a 10-minute-old fix through the success path.
- **Impact.** Wrong household coordinates recorded for exactly the patients the feature exists to map. `hedley_admin_feature_gps_coordinates_enabled = 1` on **vhw, uvl and tip-somalia**; off on ihangane (re-checked live this round).
- ⚠ **Live data is consistent with this but does NOT discriminate it.** vhw has 10,686 persons with coordinates; six coordinate pairs are shared across different cells, covering 158 records — the largest is 96 persons at exactly `-4.0504328 / 29.5432139` across 7 cells. But those 96 were created between 2025-03-06 and 2026-06-25 by 12 different users, which an in-memory per-session stale value cannot explain; a device repeatedly returning the same network-derived position fits better. Real coordinate-quality problem, separate question.
- **Fix shape (guess).** Clear `model.coordinates` when the request is issued, and give the port a tagged failure reply so "failed" is distinguishable from "still waiting". Lowering `maximumAge` is a separate judgement call.
