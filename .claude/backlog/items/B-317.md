### B-317 — Sync download: a response arriving after its 30-second timeout is applied under whichever health centre is current by then, so a device syncing two HCs can write HC-A's revision cursor onto HC-B and never download HC-B's older records — ✅ IMPLEMENTED 2026-09-17 (issue #2265, PR #2266, branch `B-317-sync-download-late-response`, base develop @332874f44, commit cd329d387; each authority/general download carries its issue time and a reply whose time is not the current request's is ignored; a reply or IndexedDB save ack for an HC that is no longer current is dropped and the current HC is refetched next tick (covers the R29 add/remove-HC amendment); the stats reply updates the model's list instead of writing back its request-time copy; both download GETs get `withTimeout` 30 s. 6 elm-tests in `SyncManager/Test.elm`, 5 of them fail with the guards stubbed out; elm-review clean on a fresh elm-stuff; full suite 3223 green locally). **Review round 1 (medium, 2026-09-17): 2 findings, both fixed in f2dd38662 — (1) the 30 s `withTimeout` plus drop-by-issue-time meant a batch that always takes >30 s could never land (silent stall on slow links); (2) the UUID-only identity let a removed-and-re-added HC (cursor reset to 0) accept the in-flight batch and jump its cursor. Fix: a reply is identified by its authority AND the base revision the request was issued from (`isCurrentAuthorityRequest`), applied however late it arrives; a non-matching reply from the in-flight request refetches now, from a superseded one is ignored; the general lane carries its base the same way; the HTTP timeout is gone. Model field is now `downloadAuthorityAtRequest : SyncInfoAuthority`. 9 elm-tests, 6 fail with the guards stubbed; threads answered and resolved. ✅ CI fully green on f2dd38662, all 11 checks incl. simpletest + 3 e2e.** ⭐ **Verified on the real local stack 2026-09-17 (user-approved borrow of the main tree, build f2dd38662, single HC):** (1) fresh pairing → general 697/36 records and Nyange 491 records to cursor 5532, both equal to the server; (2) first batch delayed 70 s server-side → the 30 s re-issue produced a duplicate, the first reply landed at 70 s (cursor 5532), the duplicate (90 s) was discarded with no extra request, lane went Success → stats → idle; (3) reload mid-download → resumed from the persisted cursor 0, same outcome on Muhondo (cursor 693 = server max). The first PR version would have aborted the 70 s batch at 30 s. - **Mechanism.** `client/src/elm/SyncManager/Update.elm`. (1) `BackendAuthorityFetch` (`:117-183`) re-issues the GET after `downloadRequestTimeout` (30 s) while the previous `HttpBuilder.get` — no `withTimeout` — is still alive; elm/http delivers its result whenever it arrives. (2) `BackendAuthorityFetchHandle zipper webData` (`:184-224`) saves the batch under the REQUEST's authority (`shard = currentZipper.uuid`, correct) but stamps it with `timestamp = requestTimestamp`, which is `model.downloadRequestTime` read at HANDLER time (`:76-78`), i.e. the NEWEST request's time — the "request identification" guard from `6393fae16` never bound the stamp to the request; it also overwrites `downloadAuthorityResponse` with the late data. (3) `BackendAuthorityFetchedDataSavedHandle timestamp` (`:232-326`) compares against the same model value (only a request issued in the ~3 s save window can differ), then `Maybe.map2 … model.syncInfoAuthorities (RemoteData.toMaybe model.downloadAuthorityResponse)` writes `lastFetchedRevisionId = max vid of the late batch` into the CURRENT zipper element — whichever authority is current now.
- **Sequence that misfires** (rural link; first 500-row batch for HC-A > 30 s): R1(A, base a0) → 30 s → R2(A, base a0) re-issued → R1 returns, A's cursor = max(R1) → R3(A, base advanced) returns empty fast → A `Success`, `determineSyncStatus` rotates to HC-B → R5(B, base b0) issued → R2 (A's 500 rows) finally returns: rows saved under shard A (harmless), but the cursor write lands on **HC-B** = max vid of A's rows. Next tick issues R6(B, `base_revision` = A's max vid) before R5 lands; R5's own write later sets B's cursor to its batch max, but R6 has already skipped every HC-B node with a `vid` between the two (`node.vid` is global) — never downloaded. A second variant (R2 empty) marks HC-B `Success` with `remainingToDownload = 0`, lifting the `viewBySyncStatus` gate (`Pages/Utils.elm:1479-1524`) early — self-healing next cycle.
- **Impact.** Silent, persistent gap on the device for the second authority — people/measurements missing, no error, nurse re-registers → duplicates (B-195 class). Repaired only by the debug-only "Reset revision ID to 0" or re-adding the HC. The General lane has the same non-binding stamp but a single cursor, so its worst case is re-downloading.
- **Evidence.** Scout's scratch elm-test (model with zipper on HC-B, request in flight at t=5000; deliver `BackendAuthorityFetchHandle zipperAtRequestA (Success {one person, vid 900})`, then the IndexedDB ack `{Authority, Success, "5000"}`) → `[("hc-A",100,Success),("hc-B",900,Downloading)]`. Existing `SyncManager/Test.elm:280-303` pins only the mismatch branch. Orchestrator re-read all four handlers and re-derived the sequence. Not sized: needs field conditions, not row counts; how many devices hold ≥2 authorities is a live question (`hedley_device` HC assignment).
- **Not a declined-class item:** no poison/stall/back-off — a correctness race in cursor bookkeeping.
- **Fix shape (guess).** Bind identity to the request: tag `BackendAuthorityFetchHandle` (and the General twin) with the request time captured at issue, drop a response whose stamp ≠ `model.downloadRequestTime`; also drop an authority response whose `Zipper.current zipper |> .uuid` is not the current authority; key the save-completion write off the same captured identity. `withTimeout downloadRequestTimeout` on the download GETs would stop the orphan from ever delivering.
- **R29 unit 3 amendment (2026-09-07) — a DETERMINISTIC trigger and a stats-lane inverse, same write sites; fold into this item's fix.** (a) `RevisionIdAuthorityAdd` / `RevisionIdAuthorityRemove` (`client/src/elm/SyncManager/Update.elm:618-674`) rebuild the zipper with `Zipper.fromList`, which always refocuses on the head, and neither checks that a download is in flight — `TrySyncing` is a no-op unless `SyncIdle` (`:2504-2516`), so the in-flight `SyncDownloadAuthority` request keeps running. (b) `BackendAuthorityFetchedDataSavedHandle` (`:232-326`) `mapCurrent`s **`model.syncInfoAuthorities`** — whatever is current *now* — and `downloadRequestTime` was not changed by the click, so this item's timestamp guard passes. Sequence: nurse adds HC-A; while A's batches download she adds HC-B → zipper `[B*, A]` → A's response saves under shard A (correct) → the save ack writes `B.lastFetchedRevisionId = max vid of A's batch` (and `B.status = Success` on A's last batch) → B's whole history is never downloaded; the Device page shows B synced with 0 remaining. Most likely on first setup when two HCs are added in a row; needs no slow network. (c) The stats handler (`BackendAuthorityDashboardStatsFetchHandle`, `:434-466`) does the opposite — writes the **request-time closure zipper** back over the model and persists it — so an add during the stats fetch silently drops the new HC, and a remove resurrects the removed one. Scout reproduced all three with scratch elm-tests (`[A*]` + add B + A's ack ⇒ `("hc-B",900,Success),("hc-A",0,Downloading)`; stats lane ⇒ B dropped; `[A,B*,C]` + remove C + B's ack ⇒ written onto A). Device page buttons render regardless of `syncStatus` (`Pages/Device/View.elm:211-234`), and navigating to that page itself triggers `TrySyncing` (`App/Update.elm:1165-1166`). Fix-shape addition: in add/remove preserve the current focus (rebuild then `Zipper.findFirst` the previously current uuid) or defer edits until `SyncIdle`; in the ack AND stats handlers locate the target by the request's uuid, never by focus — the "drop a response whose request authority is not current" check must cover the saved-ack path too.
