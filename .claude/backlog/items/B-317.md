### B-317 — Sync download: a response arriving after its 30-second timeout is applied under whichever health centre is current by then, so a device syncing two HCs can write HC-A's revision cursor onto HC-B and never download HC-B's older records — READY · CONFIRMED (all four handlers read; scout reproduced with a scratch elm-test) · MED-HIGH · tier 2 · R28 unit 1 · ⭐ DEPLOYED (all sites; needs ≥2 authorities on the device and one download > 30 s)
- **Mechanism.** `client/src/elm/SyncManager/Update.elm`. (1) `BackendAuthorityFetch` (`:117-183`) re-issues the GET after `downloadRequestTimeout` (30 s) while the previous `HttpBuilder.get` — no `withTimeout` — is still alive; elm/http delivers its result whenever it arrives. (2) `BackendAuthorityFetchHandle zipper webData` (`:184-224`) saves the batch under the REQUEST's authority (`shard = currentZipper.uuid`, correct) but stamps it with `timestamp = requestTimestamp`, which is `model.downloadRequestTime` read at HANDLER time (`:76-78`), i.e. the NEWEST request's time — the "request identification" guard from `6393fae16` never bound the stamp to the request; it also overwrites `downloadAuthorityResponse` with the late data. (3) `BackendAuthorityFetchedDataSavedHandle timestamp` (`:232-326`) compares against the same model value (only a request issued in the ~3 s save window can differ), then `Maybe.map2 … model.syncInfoAuthorities (RemoteData.toMaybe model.downloadAuthorityResponse)` writes `lastFetchedRevisionId = max vid of the late batch` into the CURRENT zipper element — whichever authority is current now.
- **Sequence that misfires** (rural link; first 500-row batch for HC-A > 30 s): R1(A, base a0) → 30 s → R2(A, base a0) re-issued → R1 returns, A's cursor = max(R1) → R3(A, base advanced) returns empty fast → A `Success`, `determineSyncStatus` rotates to HC-B → R5(B, base b0) issued → R2 (A's 500 rows) finally returns: rows saved under shard A (harmless), but the cursor write lands on **HC-B** = max vid of A's rows. Next tick issues R6(B, `base_revision` = A's max vid) before R5 lands; R5's own write later sets B's cursor to its batch max, but R6 has already skipped every HC-B node with a `vid` between the two (`node.vid` is global) — never downloaded. A second variant (R2 empty) marks HC-B `Success` with `remainingToDownload = 0`, lifting the `viewBySyncStatus` gate (`Pages/Utils.elm:1479-1524`) early — self-healing next cycle.
- **Impact.** Silent, persistent gap on the device for the second authority — people/measurements missing, no error, nurse re-registers → duplicates (B-195 class). Repaired only by the debug-only "Reset revision ID to 0" or re-adding the HC. The General lane has the same non-binding stamp but a single cursor, so its worst case is re-downloading.
- **Evidence.** Scout's scratch elm-test (model with zipper on HC-B, request in flight at t=5000; deliver `BackendAuthorityFetchHandle zipperAtRequestA (Success {one person, vid 900})`, then the IndexedDB ack `{Authority, Success, "5000"}`) → `[("hc-A",100,Success),("hc-B",900,Downloading)]`. Existing `SyncManager/Test.elm:280-303` pins only the mismatch branch. Orchestrator re-read all four handlers and re-derived the sequence. Not sized: needs field conditions, not row counts; how many devices hold ≥2 authorities is a live question (`hedley_device` HC assignment).
- **Not a declined-class item:** no poison/stall/back-off — a correctness race in cursor bookkeeping.
- **Fix shape (guess).** Bind identity to the request: tag `BackendAuthorityFetchHandle` (and the General twin) with the request time captured at issue, drop a response whose stamp ≠ `model.downloadRequestTime`; also drop an authority response whose `Zipper.current zipper |> .uuid` is not the current authority; key the save-completion write off the same captured identity. `withTimeout downloadRequestTimeout` on the download GETs would stop the orphan from ever delivering.
