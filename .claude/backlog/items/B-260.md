### B-260 — Strict decoders on optional stats values: two dashboard enum sites lack the fallback their siblings have, and one required field is emitted unguarded from a nullable column — READY · CONFIRMED (both sides verified) · LOW · tier 4 · R25 units 4+8
- ⚠ **Found independently from both ends in the same round** — the client side by unit 4 and the server side by unit 8. Recorded once, deliberately: see the handoff's warning about the same defect entering twice under two ids.
- **Why it matters.** Every failure here is the **B-175 shape**: one bad value rejects `decodeDashboardStatsRaw` wholesale, so that health centre's devices never render a dashboard and keep refetching the same blob.
- **(a) Two `encounter_type` sites with no fallback.** `Backend/Dashboard/Decoder.elm:399` `optional "encounter_type" decodeWellChildEncounterType PediatricCare` and `:454` `optional "encounter_type" decodeNutritionEncounterType NutritionEncounterUnknown`. Both underlying decoders `fail` on an unknown string, and `optional` re-runs a present-but-failing decoder to failure — the mechanism proven in B-100. The two siblings in the same file **do** guard: `:282` `decodeWithFallback AcuteIllnessEncounterCHW …` and `:324` `decodeWithFallback NurseEncounter …`.
- **(b) An unguarded PHP emit into a strict `required`.** `hedley_stats.module:1062` emits `'diagnosis' => $row->field_acute_illness_diagnosis` — a LEFT-joined column whose field instance is `'required' => 0` — into `Backend/Dashboard/Decoder.elm:285` `required "diagnosis" decodeAcuteIllnessDiagnosis`, which starts with `string` and so fails on `null`. The sibling values in the *same* item are all guarded (`encounter_type` at `:1072`, `send_to_hc`/`isolation` at `:1064-1069`). **No live producer found** — `Backend/AcuteIllnessEncounter/Encoder.elm:26` always sends a diagnosis ("none" for `NoAcuteIllnessDiagnosis`) and nothing server-side creates these encounters — so this is a schema-level possibility, the closed-cohort shape of B-100, not an observed failure.
- **(c) A bare `list` where every sibling is element-tolerant.** `Backend/Dashboard/Decoder.elm:180` `required "signs" (list decodeFamilyPlanningSign)`, and `decodeFamilyPlanningSign` ends in `fail` (`Backend/Measurement/Decoder.elm:1529-1532`). Every other multi-value list in that decoder uses `decodeEverySet` or `decodeListDroppingUnknown`, whose docblock names exactly this scenario. All 14 server allowed values exist in the client enum today, so it is latent — it fires the day a family-planning method is added, breaking the dashboard on every device that has not updated yet.
- ✅ **Checked and safe, so nobody re-treads it:** every `decodeEverySet` site is tolerant (`Utils/Json.elm:60-64`), which is what makes the server's unconditional `explode(',', NULL)` → `[""]` harmless for `warnings` / `nutrition_signs` / `danger_signs` / `send_to_hc`; and `hedley_stats_extract_first_value` returns `NULL`, not `FALSE`, on empty (`:3990-3995`), so the nullable numeric fields cannot be poisoned.
- **Fix shape (guess).** `decodeWithFallback` at the two `encounter_type` sites; the element-tolerant list decoder for `signs`; an `!empty` guard on the PHP diagnosis emit, matching the `encounter_type` line beside it.
