### B-397 — `[ci skip]` on every commit plus zero required status checks means a PR can be merged with no CI having run at all — READY · CONFIRMED (orchestrator read the branch protection and the commit statuses) · MED · tier 3 · R34 unit 3 · ⚠ policy call, not a code fix
- **Mechanism.** CircleCI suppresses the **whole pipeline** — all ten jobs, there is no per-job filter in the config — for any push whose head commit message contains `[ci skip]`. The project convention (`CLAUDE.md`, "Commit Messages") is to append it to every commit unless the user asks for CI. GitHub then has nothing to enforce:
  ```
  $ gh api repos/TIP-Global-Health/eheza-app/branches/develop/protection --jq '.required_status_checks'
  {"checks":[],"contexts":[],"strict":false,…}
  ```
  Zero required contexts, so `gh pr merge` is never blocked by a missing or failing check.
- **Evidence.** The mechanism works as intended for documentation: of `develop`'s last ~25 commits only the four merge commits have builds; every `Backlog: …` commit has none. The failure case is real and recent — PR #2238's five commits are all `[ci skip]`, GitHub reports `state: pending, n=0` on every one, it merged, and its merge build went red on three jobs ([[B-395]]). Eleven of the twelve other recently-merged PRs show `success, n=10/11` on their head SHA, so #2238 is an outlier rather than the norm.
- **Impact.** The pipeline is advisory. A merged-but-untested PR is discovered only by the post-merge `develop` build, which blocks nothing and — as [[B-395]] shows — can sit red for days across four further merges.
- **Fix shape (guess).** Two independent options, both policy calls for the user rather than things to build unasked: make the ten job contexts required on `develop`, and/or exempt code-bearing commits from the `[ci skip]` convention. ⚠ Making contexts required interacts with the `[ci skip]` convention — a required check that never runs blocks every backlog commit too.
