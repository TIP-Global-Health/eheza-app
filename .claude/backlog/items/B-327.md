### B-327 — Device pairing: once a device is paired there is no way back to the pairing form, so when its access token expires (contrib restful deletes it) the device fails every sync forever and the only field remedy — clearing site data — loses unsynced records; LATENT until the first live expiry on 2030-03-19 — READY · CONFIRMED (client has no unpair path; contrib expiry code and live token table read) · LOW today · tier 4 · R29 unit 3 · ⏳ revisit before 2030-03
- **Mechanism.** `configured.device` is set only by `HandlePairedDevice` (`client/src/elm/App/Update.elm:1041-1050`), fed at boot from the SW cache (`:169-190`; 404 → `NotAsked`). The pairing form renders only while `device` is not `Success` (`App/View.elm:366-378`, `Pages/Device/View.elm:47-70`). No code path resets `device`, deletes `/sw/config/device`, or uses `refreshToken` (decoded, encoded, never read — `Device/Model.elm:9`, `Device/Encoder.elm:12`). A 401/403 from `/api/sync` is just an `Error` status via `maybeHttpError`; the cycle retries indefinitely. Server: tokens are minted with `restful_token_auth_expiration_period = P5Y` (`hedley.install:39-40`, `hook_install` only) and contrib restful deletes an expired token on first use (`server/hedley/modules/contrib/restful/modules/restful_token_auth/plugins/authentication/RestfulAuthenticationToken.class.php:78-83`, `restful_token_auth_delete_expired_tokens` default TRUE).
- **Live (ihangane, this seat, 2026-09-07).** `restful_token_auth_expiration_period = P5Y`; 5,725 tokens, **0 expired**, earliest `expire` **2030-03-19**, latest 2038-01-13. So nothing fires until 2030-03, after which devices expire one by one for eight years unless re-paired.
- **Impact when it fires.** Stuck device, all sites; data loss if the field remedy is "clear the browser". Correctness (stuck state), not the declined token-lifetime security class.
- **Fix shape (guess).** On a 401 from the backend treat the device as unpaired (`DELETE /sw/config/device`, `device = NotAsked`) so the pairing form returns without touching IndexedDB; or implement the refresh-token exchange the model already carries.
