### B-266 — WhatsApp uploads carry no UUID, so the sync POST's duplicate guard cannot fire and a retried batch sends the patient the same report twice — READY · CONFIRMED (both sides + IndexedDB schema verified) · MED · tier 3 · R25 unit 6
- **Mechanism.** `HedleyRestfulSync::handleChanges()`'s POST branch (`:509-519`) is idempotent only through the UUID: *"Check if node with provided UUID already exists. If it does, we don't do anything, as this is duplicate request."* — `if (!empty($item['uuid'])) { $nid = hedley_restful_resolve_nid_for_uuid(...); } if ($nid === FALSE) { $sub_handler->post('', $data); }`. Every other upload lane supplies that key (`SyncManager/Utils.elm:1245-1247`, `SyncManager/Encoder.elm:41-46, 158-165`). The WhatsApp lane does not: `encodeIndexDbQueryUploadWhatsAppResultRecord` (`SyncManager/Encoder.elm:55-78`) emits only `type`, `method` and `data`, and `encodeBackendWhatsAppEntity` emits `person, date_measured, language, report_type, phone_number, screenshot`. **There is no UUID to send** — the IndexedDB table has no uuid column (`client/src/js/app.js:293`, `whatsAppUploads: '++localId,screenshot,language,report_type,person,phone_number,fileId,syncStage'`). So `$item['uuid']` is undefined, `empty()` is true, and `post()` always runs; `field_uuid` is then auto-generated server-side by `hedley_device_assign_uuid()`, a **different** UUID each attempt.
- **Reachability.** `BackendUploadWhatsAppHandle` (`SyncManager/Update.elm:1645-1704`) deletes the local rows only on `RemoteData.Success`; on `Failure` they keep `syncStage = 1` and are re-selected next cycle (`app.js:973-1000`). So any outcome where the server commits but the client never sees the 200 — request timeout, Pantheon gateway timeout on a long batch, connectivity lost at the moment of response — re-posts the same records. The general and authority lanes share that delete-only-on-success model; the UUID check is exactly what makes *them* safe.
- **Impact.** Duplicate `whatsapp_record` nodes, and `hedley_whatsapp/scripts/send-messages.php` selects every published, non-concluded, under-attempt-limit record and sends one Twilio message per row — so the patient receives the same progress report twice. Also inflates any count of reports shared. Gated by the `report_to_whatsapp` flag; all sites where it is on. ⚠ Offline-first devices on poor connectivity are precisely the population that loses responses.
- **Sizing query for the user:** `SELECT person, date_measured, report_type, COUNT(*) FROM <whatsapp_record fields> GROUP BY 1,2,3 HAVING COUNT(*) > 1`, per site.
- **Fix shape (guess).** Give the WhatsApp row a client-generated UUID (new IndexedDB column + schema bump) and send it at the item level so the existing dedupe applies. A server-side dedupe on `(person, date_measured, report_type, screenshot fid)` avoids the schema bump but is weaker.
