- ✅ **The "catastrophic" half PROVEN, not assumed** — the risk is that `optional` might swallow the failure. It does not: NoRedInk/elm-json-decode-pipeline 1.0.1 `optionalDecoder` falls back ONLY when the field is ABSENT; when the field is present and the decoder fails it re-runs the decoder to fail with a structured error, and the source carries the comment *"(If it was present but fails to decode, this should and will fail!)"*. So one `false` → `decodeMonthlyValues` fails → `PatientData` fails → the whole `decodeSyncResponse` batch fails → scoreboard dead for the district. 📌 Durable: **`optional` is not a tolerance mechanism — it tolerates MISSING, never MALFORMED.** Any "the decoder is optional so a bad value is safe" claim is false in this codebase.

- ⭐ **The "is an untyped encounter an ANC visit?" product question was ALREADY ANSWERED by the client — trace before asking the user.** `HedleyRestfulIndividualEncounter` joins fields with `$require = FALSE`, and `hedley_general_join_field_to_query()` maps that to **`leftJoin`** (`$join = $require ? 'innerJoin' : 'leftJoin'`), so the encounter SYNCS with a null type instead of being dropped. Client: `required "prenatal_encounter_type" (decodeWithFallback NurseEncounter decodePrenatalEncounterType)` — `required` is satisfied (key PRESENT, value null) and `decodeWithFallback` = `oneOf [decoder, succeed fallback]`, so null → **NurseEncounter**. Note the asymmetry — `decodeWithFallback` tolerates a bad VALUE, `required` does not tolerate a missing KEY.
