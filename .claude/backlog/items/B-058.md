- 📌 LESSON: when fixing a bug in one module, GREP FOR THE PATTERN ELSEWHERE. B-098's `$person->field_X = ...; node_save($person)` after a long compute existed in hedley_reports too, and the backlog had it filed as a *different* (concurrency-contingent) finding — so it looked blocked when half of it was a live, unblocked data-loss bug.
- `hedley_ncda.module:988-989` `$person->field_ncda_data[...] = $encoded; node_save($person)` and `hedley_reports.module:1324-1325` `$person->field_reports_data[...] = $encoded; node_save($person)` — each does a full read-modify-write of the WHOLE person node (D7 node_save has no version guard). Both tasks are co-enqueued on EVERY triggering measurement write (`hedley_ncda_node_insert:96` + `hedley_reports_node_insert:159`, two separate queues in group `hedley`). Two concurrent workers → interleave load(stale)→compute→save(whole node) → last writer reverts the other's field to its pre-computation snapshot.
- Self-heal: partial (re-derives on the person's NEXT triggering measurement; stale indefinitely for quiescent/aged-out records). Fix: each worker writes ONLY its own field (targeted field_attach_update / reload-in-transaction), or serialize NCDA+Reports per person into one task. Severity MED (stale Child-Scoreboard / Statistical-Queries aggregate).
- **CONCURRENCY GATE ANSWERED (verification sweep 2026-07-06, repo evidence):** designed processing = ONE serialized drush run per 5 min (`infrastructure_setup/advancedqueue.sh:19` `drush @pantheon...live advancedqueue --all --timeout=300`, README:140-157 crontab/Jenkins `*/5`), core cron does NOT process AQ (`advancedqueue_use_cron` unset anywhere, contrib default FALSE), pantheon.yml has no cron. So: low-frequency bursty risk, not steady-state. Unknowable from repo: Jenkins vs plain cron in prod, actual run durations, ad-hoc operator drush.
