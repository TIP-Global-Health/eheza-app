### B-563 — Group session: a family whose child's page or activity row was shown more than five minutes ago is dropped from the open session — the mother and her children vanish from the attendance list, the participants list and every activity list until a reload — on the next group-measurement save or download — READY · MED-HIGH · tier 3 · CONFIRMED (code, every link read on 3778065f9) · ✅ REPRODUCED in the browser 2026-11-08 (local demo DB, recipe and outcome below) · the child-page route is DEPLOYED and years old · broadened by PR #2465 (B-548, release #2417) to every child shown on an activity page · R51 unit 3

  Once the child is no longer the shown one, nothing re-wants those keys: `fetchEditableSession` re-requests only keys still present as `NotAsked` (`Backend/Session/Fetch.elm:16-35`, `getIds`), and the only seeder of those keys, `HandleFetchedExpectedParticipants` (`Backend/Update.elm:475-516`), never re-fires while `expectedParticipants` is `Success`. Every editable session is rebuilt on a group-measurement revision from either origin — a download (`processRevisions`, `Backend/Update.elm:2512-2535`, `WeightRevision` and siblings return the recalc flag `:8168-8174`) and a local save of one height / weight / MUAC / nutrition-signs record (`processRevisionAndAssessNutritionGroup`, `:2089-2135`, dispatched at `:2898-2961`) — and the rebuild drops a child whose key is gone:

  `offlineSession.children` feeds `getChildren` / `getChild` (`Backend/Session/Utils.elm:17-30`), the participants summary and every activity list; `calculateOfflineSessionMeasurements` (`:10220-10230`) keeps only `Success` measurement sets, so the child's saved group measurements leave the session view as well. The child's fetch set also leases `FetchPerson` for everyone the child is related to (the `relatedTo` line above), so the **mother's** `people` key is forgotten with the child's, and `mothersData` (`:10026-10040`, same `filterMap` shape) drops her — the whole family leaves the session, not only the child.
- **Reachability.** Nurse or CHW in an open group session: (a) participant-first — open child A's page, go back, work on other children for more than five minutes, save any group measurement → A vanishes from the mother's children and the participants list; (b) after #2465, activity-first — any child shown on an activity page (the row the page loads for) counts the same way. A reload re-seeds everything from IndexedDB; nothing is lost on disk.
- **Impact / size.** Every site running group sessions. In a real session the nurse opens one child page after another, so after the first five minutes every save drops every family visited more than five minutes earlier: the attendance list, the To-Do / Completed tabs and the activity lists shrink to the last five minutes of work until someone reloads. Nothing is lost on disk; the family cannot be opened again in that session view (no card to tap) until the reload. The exposure is old (per-child fetch on the child page since before 2021-06, the forget loop since 2019-05 `f985c3c4d`) — the reproduction below shows there is no masking factor; a reload is simply how nurses have been recovering. Count not measurable server-side (device-local state).
- 🧪 **Reproduced 2026-11-08 (develop 164a799db bundle, local demo DB, fresh device on `127.0.0.1:3000`, Nyange I FBF group).** Checked in E2ETest B548MomA and B548MomB → participants page listed MomA/KidA and MomB/KidB → opened MomA's page, then KidA's page (Height form shown) → left for the participants page at ≈15:58 → waited 5 min 45 s on the participants page (still both families) → opened MomB → KidB → Weight 9.5 kg → Save. Participants page then listed **only MomB/KidB** (To Do 2 → 1, Completed 0); the attendance page listed only MomB; F5 brought MomA/KidA back. Exactly the chain above, with the mother dropped as well.
- **Already recorded, distinct.** B-548 / B-329 are the fetch gap this PR closed; B-299 / B-300 / B-330 / B-430 use the forget loop only as a refetch mechanism; no item records a dropped session child (grepped `dataWanted`, `App.Fetch.forget`, `offlineSession.children`, "vanish", "disappear").
- **Fix shape (first guess).** Keep a session's people out of the forget while the session itself is wanted (have `fetchEditableSession` re-want `FetchPerson` / `FetchChildMeasurements` for every expected child and mother, or make `forget` skip keys referenced by a `Success` editable session); or make `makeEditableSession` treat a missing key as `NotAsked` so the next cycle refetches instead of dropping. A test can pin it on the `makeEditableSession` seam: a `people` dict missing one expected child must not yield a session without that child.
