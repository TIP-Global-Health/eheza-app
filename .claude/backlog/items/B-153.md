### B-153 (original entry) — Stored NCDA blobs disagree with the code that writes them: ~1,317 children carry a `low_birth_weight` the current calculation would set — SYMPTOM CONFIRMED on live data / MECHANISM UNKNOWN · MED · found 2026-08-05 while dry-running the B-149 recalculation
- **Symptom, measured against a copy of `ihangane.live`:** of the 2,700 children `recalculate-low-birth-weight.php` selects, **1,317 have NO `low_birth_weight` key stored** — yet live's own code would set one for them. Sampled 10 per group and recalculated: the "unknown" group changed **0/10** (byte-identical blobs), the other groups **10/10**. So their blobs are current in every other respect and wrong only in this key.
- **Worked example (keep it, it cost the investigation):** person 1437226, born 2022-01-23. One `group_ncda` node 3507022 carrying `field_birth_weight = 3.4`, **visible** to `hedley_general_get_person_measurements` (51 triggering measurements). Replicating live's resolution logic in `drush php-eval` yields `3.4` → live's `$birth_weight < 2000` would store **TRUE**. Stored blob has **no key at all**.
- ⛔ **HYPOTHESES TESTED AND REFUTED — do not re-tread:**
  1. *Measurement invisible to the calculation* — refuted, node loads and is in the triggering set.
  2. *Blob predates the feature* (`low_birth_weight` added 2023-05-11, `7a50180ca`) — refuted: newest triggering measurement created **2025-12-16**, long after.
  3. *Measurement soft-deleted* — refuted: affected-set query returns 2,700 with and without excluding soft-deleted measurement nodes.
  4. *Bundle list differs on live* — refuted: `group_ncda` IS in `HEDLEY_ACTIVITY_NCDA_BUNDLES` on `origin/main`.
  5. *AQ task wedged in PROCESSING, permanently swallowing later triggers via the `hedley_general_add_task_to_advanced_queue_by_id` dedup* — NOT supported: **zero** NCDA items in PROCESSING on live; 6 in FAILURE (status 2), which is terminal and does NOT block re-enqueue (the dedup checks only QUEUED/PROCESSING). Live AQ status codes: QUEUED=-1, PROCESSING=0, SUCCESS=1, FAILURE=2, FAILURE_RETRY=3.
- ✅ **MECHANISM SOLVED 2026-08-10 — it is NOT a race. The B-058-clobber hypothesis is unnecessary; do not pursue it for this symptom.** Read the DEPLOYED code (`server/.pantheon-ihangane/profiles/hedley/modules/custom/hedley_ncda/hedley_ncda.module:521-531`) instead of develop's, and the cause is plain — two defects in the NCDA fallback:
  1. **The guard demands an unrelated field.** `if (!empty($ncda->field_birth_weight) && !empty($ncda->field_weight[LANGUAGE_NONE][0]['value']))` — `field_weight` is the child's CURRENT weight on that questionnaire, nothing to do with birth weight. No current weight ⇒ the recorded birth weight is discarded ⇒ `$birth_weight` stays empty ⇒ `if ($birth_weight)` is false ⇒ **no key written at all**.
  2. **`break` sits OUTSIDE the `if`**, at the end of the first iteration, so only the FIRST NCDA questionnaire is ever examined; a birth weight on any later one is unreachable.
- **Live-measured proof (ihangane.live, 2026-08-10):** 121,613 blobs total; 111,295 lack the key (mostly legitimate — no birth weight recorded). The population that matters is children who DO have a birth weight: **3,975 of them lack the key, and 3,963 (99.7%) have that birth weight on a node with ZERO `field_weight` rows** — defect 1 exactly. Residue of 12 unexplained (likely defect 2, not chased). Worked example: person 3544890, blob current in every other respect, birth weight 2000 g on `well_child_ncda` node 3544902 which has 0 `field_weight` rows.
- ✅ **ALREADY FIXED ON DEVELOP by PR #2036 (B-149), undeployed.** develop's fallback now reads `if (!empty($ncda->field_birth_weight[LANGUAGE_NONE][0]['value']))` with the `break` INSIDE the `if`. So no new code is needed for the mechanism — **what remains is deploy + regenerate**, and the compare-before-save guard (PR #2043) is what makes a full regeneration affordable.
