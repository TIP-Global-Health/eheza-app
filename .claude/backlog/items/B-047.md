### B-047 — Revoked/deleted nurse's PIN keeps working forever: client drops the `deleted`/`status` tombstone and re-saves the nurse as live — CONFIRMED-mechanism · QUEUED 2026-07-03, IMPLEMENT-DECISION DEFERRED (user queued it but will decide later whether to actually build; still brushes the R5-2 declined nurse-credential class, so re-confirm intent before starting the PR) · READY
- Server intentionally syncs unpublished/deleted nurse revisions as tombstones (`HedleyRestfulSync.class.php:132-153`, no status=1 filter; payload carries `status`+`deleted`). But `Backend/Nurse/Decoder.elm:25-40` reads neither `deleted` nor `status`; `Backend/Nurse/Encoder.elm:44` hardcodes `("deleted", bool False)`; the re-encode-on-save path (`SyncManager/Utils.elm` getDataToSendGeneral → bulkPut into `nodes`) therefore overwrites the local nurse row as live regardless of the tombstone. PIN gate (`nodes.js index()` ~:874-919, `{type,pin_code}` + `deleted == false`) then matches forever. Nurse bundle also has no `field_deleted`, and a hard node-delete removes revisions from the feed entirely.
- Framed as state-machine correctness (revocation channel architecturally can't reach the device), NOT the R5-2 plaintext/escalation issue — BUT "revoked nurse still logs in on a trusted device" may fall under the SAME "devices trusted / PINs low-value" call the user made (R5-2 declined). Fix if wanted: decode+carry `deleted`/`status` through nurse decoder/encoder + add `status==published && deleted==false` to the PIN query; add `field_deleted` to the nurse bundle. Severity HIGH-if-in-scope.
