### B-226 — Prenatal participant page (nurse): "Postpartum" opens a second encounter while an antenatal encounter is still open, orphaning the first — READY · CONFIRMED (anchor verified) · MED · tier 3 · R24 unit 5
- **Mechanism.** `Pages/Prenatal/Participant/View.elm` `viewActionsForNurse` (:219-335). `maybeActiveEncounterId` = newest encounter with `endDate == Nothing`. `postpartumEncounterButtonEnabled` (:288) = `postpartumEncounterInProcess || (lastEncounterType /= NursePostpartumEncounter && not encounterWasCompletedToday)` — it never consults `maybeActiveEncounterId`. With an OPEN `NurseEncounter` (`endDate` Nothing ⇒ `encounterWasCompletedToday` False) the button is enabled, and `postpartumEncounterButtonAction` (:303) takes the else-branch: `createNewEncounterMsg … NursePostpartumEncounter` → `PostPrenatalEncounter`, whose only guard is an in-flight POST for the same participant (`Backend/Update.elm:4847-4856`). Result: two open encounters on one pregnancy. Afterwards `postpartumEncounterInProcess` is True so First/Subsequent are disabled and the antenatal encounter is unreachable from this page. The CHW sibling `viewActionsForChw` (:374-398) guards exactly this: `encounterTypeButtonActive` returns `lastEncounterType == Just encounterType` whenever an active encounter exists — the nurse branch was not kept in step.
