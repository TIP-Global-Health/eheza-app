- ## SCOPING DONE 2026-08-03 (read-only against `ihangane.live`) — the blocker is solved

**The merge map is recoverable, and it is small.** The entry always said the blocker was that a merge leaves no explicit duplicate→original link. It does, in the revision tables: re-pointing a measurement writes a revision, so `field_revision_field_person` keeps the pre-merge value while `field_data_field_person` holds the current one. A node where those differ AND the old value is a soft-deleted person is a merge fingerprint.

| Query | Rwanda |
|---|---|
| soft-deleted persons | 159 |
| soft-deleted **relationships** with a soft-deleted endpoint | **139** |
| soft-deleted **pmtct_participants** whose `field_adult` is soft-deleted | **38** |
| revision rows naming a soft-deleted person | 754 |
| nodes showing the re-point signature | 150 |
| ⇒ **distinct duplicate→original pairs** | **18** |
| duplicates mapping to more than one original | **0 — unambiguous** |

**Only 18 of the 159 soft-deleted persons were merged.** The other 141 were deleted for other reasons and MUST NOT be touched — this filter is the answer to the entry's own "risk of resurrecting relationships legitimately deleted" caveat. `vhw.live` has zero soft-deleted persons, so this is Rwanda-only.

**The recovering query** (keep it, it is the expensive part to re-derive):
```sql
SELECT DISTINCT fr.field_person_target_id AS dup, cur.field_person_target_id AS orig
FROM field_revision_field_person fr
JOIN field_data_field_deleted d ON d.entity_id = fr.field_person_target_id AND d.field_deleted_value = 1
JOIN field_data_field_person cur ON cur.entity_id = fr.entity_id
 AND cur.field_person_target_id <> fr.field_person_target_id;
```

**Script shape:** build the 18-pair map; per pair find relationships and participations soft-deleted with that duplicate as an endpoint; re-point to the original, clear `field_deleted`, dedup against links the original already holds, clear `field_shards` so presave recomputes the union. Dry-run mode first, as the other backfill scripts have.

**Open question for the team, not for code:** whether un-deleting is wanted in every case — a 2022 merge may since have been corrected by hand. 18 people is small enough for a human to eyeball the dry run.

## LIVE RE-MEASUREMENT 2026-08-26 (read-only, post-deploy) — the merge count is now bracketed, and the repair set is 28 rows

Question asked: **how many merges actually happened on live?** The merge command records no explicit
duplicate→original link, so it has to be counted from fingerprints. Two independent ones exist, and
together they bracket it.

**Fingerprint 1 — who authored the soft-delete.** `_consolidate_patients_execute()` ends by setting
`field_deleted` on the duplicate and saving; run through drush without `--user`, that node revision is
authored by **uid 0**. The only other writer of `field_deleted` on a person is the VBO bulk action
`hedley_admin_mark_as_deleted_action()` (`hedley_admin.module:33`), reachable from the admin content
view, which always carries a logged-in uid. Taking the FIRST revision that set `field_deleted=1` per
currently-deleted person:

| author of the first deleting revision | persons |
|---|---|
| uid 720 | 97 |
| **uid 0 (CLI/drush — the merge signature)** | **28** |
| uid 443 | 22 |
| uid 286 | 12 |
| total | 159 |

**Fingerprint 2 — the measurement re-point** (the query already in this entry): **18 distinct
duplicate→original pairs, 18 distinct duplicates, none mapping to more than one original.**

**The two agree.** 17 of the 18 fingerprinted duplicates were soft-deleted by uid 0; the 18th was
deleted by uid 720 (an admin account finishing off a person whose measurements had already moved).

⇒ **Merges on `ihangane.live`: 17 confirmed, at most 28.** The 11 uid-0 deletes with no measurement
fingerprint are the blind spot — `_consolidate_patients_validate()` does **not** require the duplicate
to have any measurements, so merging a measurement-less duplicate executes, soft-deletes them, and
leaves fingerprint 2 empty while the delete cascade still takes their family links.
