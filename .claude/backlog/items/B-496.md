### B-496 — Acute illness + Prenatal: the diagnosis the device computed and acted on is never written to the encounter — 5 % of acute-illness encounters (123 of 2,401 replayed) and ~9 % of Bumbogo nurse prenatal encounters are stored as "none" although the writing build's own engine yields a diagnosis from their measurements and the device went on to record Next Steps for it — READY · CONFIRMED as a phenomenon (six-build replay harness + server revision trails; orchestrator re-ran the proxy) · **ROOT CAUSE CONFIRMED 2026-10-18 by reproduction** (the download gate on `HandleRevisions` swallows the device's own save; see the last bullet) · MED · tier 2 · all sites run the code, sized on ihangane · DEPLOYED · pair with B-168 (the participant twin) · ⚠ user to decide whether the tier-1 rule applies: the diagnosis is DETERMINED correctly on the device; it is the stored record that says "none", and the next visit's pathway reads the stored record

- ✅ **ROOT CAUSE (found and reproduced 2026-10-18, user asked "did you identify the root cause"; demo site reinstalled for it, no live data involved).** The service worker reports every LOCAL save back to the page as a `NewRevisions` message (`nodes.js` `sendRevisedNode` → `sw.js` `sendRevisions` → `ServiceWorker.Update` → `Backend.Model.HandleRevisions`), the same message the sync download uses. `HandleRevisions` gates on the sync manager's state, not on where the revision came from:
```elm
-- client/src/elm/Backend/Update.elm:2052-2062, 2548-2551 (develop; identical on origin/main; since 7dc377967, 2021-05-03, so in EVERY fielded build)
        HandleRevisions revisions ->
            let
                downloadingContent =
                    case syncManager.syncStatus of
                        SyncManager.Model.SyncDownloadGeneral _ ->
                            True

                        SyncManager.Model.SyncDownloadAuthority _ ->
                            True
                        ...
            if downloadingContent then
                processRevisions          -- applies the revision, runs NO assessment

            else
                case revisions of
                    [ SymptomsGeneralRevision _ data ] -> processRevisionAndDiagnoseAcuteIllness ...
                    [ PrenatalSymptomReviewRevision _ data ] -> assessPrenatalOnRevision ...
```
  When the save that completes the diagnosis lands while the background sync cycle is in a download phase (`/api/sync` or `/api/sync/<hc>` GET in flight), the revision is applied silently and `generateSuspectedDiagnosisMsgs` / `generatePrenatalAssessmentMsgs` never run for it. Nothing re-emits later: `generateSuspectedDiagnosisMsgsFirstEncounter` fires only when the diagnosis computed BEFORE the revision differs from the one AFTER, and from the next revision on both sides already yield the diagnosis. The UI computes `assembled.diagnosis` live from measurements, so the header, Next Steps and the progress report show the diagnosis while the encounter record keeps `none` — exactly the field pattern (113 of 123 with Next Steps, no revision ever carrying the diagnosis, the close PATCH built from the model copy still `none`). The warning popup is also skipped, which is the one thing the nurse could notice.

  - **Why ~5 % and why Bumbogo.** The window per cycle is the duration of the download GETs; a cycle runs every 10 min by default (`app.js` `getSyncSpeed`) and whenever the nurse taps sync. On a slow link each page takes seconds, and a busy HC's authority download runs page after page (`Still have data to download → noChange`), so the window is wide exactly where other devices upload a lot. Builds ≤ v1.14.3 dropped the whole revision instead of applying it (same loss, different shape), so the rate difference is environment, not code.
  - **Blast radius (same gate, persistence-bearing).** Acute illness diagnosis; prenatal diagnoses, `processRevisionAndUpdatePrenatalLabsResults`, report-to-origin; nutrition INDIVIDUAL assessment (`SaveNutrition` + `SaveFollowUp`) and GROUP assessment (`MeasurementOutMsgChild` follow-ups) — only acute + prenatal are measured on live data; the nutrition pair is a candidate for the replay harness. Well-child and the acute "assessment completed" branches only navigate/popup. NOT covered: participant updates dispatched from pages (`SetEddDate`, `SetNewborn`) — B-168 stays unexplained by this.
  - **Fix shape.** Gate on the revision's origin, not on the sync state: a local save's `NewRevisions` must always take the assessing branch (e.g. `ServiceWorker.Update` sends `HandleLocalRevisions`, or `HandleRevisions` carries a source flag set only by `SyncManager.handleNewRevisionsMsg`). Downloaded revisions keep the plain path. Repair of the stored rows is a separate, server-side pass: the R44 replay harness already lists them (123 acute + 51 prenatal in the year window). ⚠ Tier: the user's call stands (determined correctly, recorded wrongly, next visit reads the record).
