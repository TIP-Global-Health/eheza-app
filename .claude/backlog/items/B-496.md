### B-496 — Acute illness + Prenatal: the diagnosis the device computed and acted on is never written to the encounter — 5 % of acute-illness encounters (123 of 2,401 replayed) and ~9 % of Bumbogo nurse prenatal encounters are stored as "none" although the writing build's own engine yields a diagnosis from their measurements and the device went on to record Next Steps for it — READY · CONFIRMED as a phenomenon (six-build replay harness + server revision trails; orchestrator re-ran the proxy) · PLAUSIBLE on the drop site (three candidates in the message pipeline, none proven) · MED · tier 2 · all sites run the code, sized on ihangane · DEPLOYED · pair with B-168 (the participant twin) · ⚠ user to decide whether the tier-1 rule applies: the diagnosis is DETERMINED correctly on the device; it is the stored record that says "none", and the next visit's pathway reads the stored record
- **Found R44 unit 1** (diagnosis replay on the ihangane copy 2026-10-17). The replay was built to find engine regressions and found none (develop ≡ origin/main on 4,343 encounters); this is what was left when every engine difference was explained.
- **Evidence.** 123 of 2,401 acute-illness encounters (Ntarama 13/934, Bumbogo 69/869, Ruli 22/327, Kabuye 20/269) store `field_acute_illness_diagnosis = none` while develop, origin/main AND the build that wrote them all compute a diagnosis from the encounter's own measurements (fever-of-unknown-origin 44, cough-and-cold 28, malaria-uncomplicated 25, respiratory-uncomplicated 14, tuberculosis-suspect 8, respiratory-complicated 5, …). 113 of the 123 carry Next Steps records (`send_to_hc`, `medication_distribution`, `health_education`, `acute_illness_follow_up`), which the UI only offers once `resolveNextStepsTasks` is non-empty — so the device displayed the diagnosis. Server revision trails of nine (nids 5279923 5355288 5545962 5561306 5595057 5498817 5530792 5550433 5582977): every device revision is `none` — create, then close (`value2` set), then the uid-0 cron edit; **no revision ever carried the diagnosis, and the later close PATCH, built from the device's own model copy, still says `none`** — the loss is before the service-worker write, not in the upload lane. Prenatal: 51 rows (Bumbogo 50, Nemba 1) where every build computes `depression-not-likely` (22), `moderate/high-risk-of-preeclampsia` (21; 9 of them May–Oct 2026 on ≥ v1.17.0 robots, so not the v1.14.3 code gap), anemia (4), singles; nid 5551504 (v1.18.2 robot, 2026-05-20): `mental_health_signs` `q2-3` → `depression-not-likely` on all builds, 4 device revisions, all `none`. Rate by writing build (acute): fcc0cf1e4 1.4 % · efbff4534 6.4 % · 7ece1b2d0 7.7 % · 88419ca86 8.5 % — ~5× more frequent on devices past v1.14.3. Orchestrator proxy on the whole year: 1,063 of 2,816 acute-illness encounters store `none`; 544 of those carry a Next Steps record (upper bound — the replay's 123 is the credible figure).

  Three candidate drop sites: the silent `unwrap` no-op when the encounter is not `Success` at the moment the diagnosis message arrives; the active-page gate; the refetch window after a revision during which a second visit assembles with no history and `mandatoryActivitiesForAssessmentCompleted` / `initialEncounter` see a first visit. Which one is NOT proven — the replay evaluates the engine, not the pipeline. Established: the engine is not the cause; the loss is before the local write.
- **Reachability.** `processRevisionAndDiagnoseAcuteIllness` (`Backend/Update.elm:2064-2080`, 14 trigger revision types) and `assessPrenatalOnRevision` (`:2985-3325`) — every ordinary nurse/CHW save.
- **Impact.** An encounter stored as `none` shows no diagnosis in the progress report and Case Management, is counted as undiagnosed by the server reports, and a subsequent acute-illness visit derives its activity set from the stored diagnoses of previous encounters (`getAcuteIllnessDiagnosisByPreviousEncounters`) — so the next visit's pathway is wrong for these 5 %.
- **Fix shape (guess).** First make the drop visible: report the `unwrap ( model, Cmd.none, [] )` branches of both `updateEncounter`s and the `_ -> []` active-page branch to Rollbar with encounter id + diagnoses; log `mandatoryActivitiesForAssessmentCompleted = False` when previous-encounter data is empty but the encounter is not the participant's first. Then defer the diagnosis write until the encounter is loaded, or write it from a model-independent copy. Reproduce on a device before coding (B-168's recipe: fresh device, `verify-sync-lanes-in-browser`).
