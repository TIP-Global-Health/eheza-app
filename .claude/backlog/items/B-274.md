### B-274 — Acute Illness medication distribution: after a reload, switching a medicine from "not given (out of stock / allergy)" to "given" keeps the stored reason, so the record says both and the referral stays mandatory — READY · CONFIRMED (anchors + consumer verified) · MED-LOW · tier 3 · R26 unit 3
- **Mechanism.** The Yes/No update functions built in `medicationDistributionFormInutsAndTasks` are applied to the **raw** page-model form, not the form resolved against the saved measurement. `updateNonAdministrationSigns` (`Pages/AcuteIllness/Activity/Utils.elm:904-918`) removes the reason via `form_.nonAdministrationSigns |> Maybe.andThen (...)`, and `SetMedicationDistributionBoolInput` (`Update.elm:830-835`) runs `formUpdateFunc value model.nextStepsData.medicationDistributionForm`. When the page model is fresh — `acuteIllnessActivityPages` is an in-memory `Dict` (`App/Model.elm:319`) that `App/Update.elm:721-723` falls back to `emptyModel` for, so any reload or re-login empties it — `form_.nonAdministrationSigns` is `Nothing`, `Maybe.andThen` yields `Nothing`, nothing is removed. `medicationDistributionFormWithDefault` then restores the saved reason (`Utils.elm:1653`, `nonAdministrationSigns = or form.nonAdministrationSigns (Just value.nonAdministrationSigns)`) and `toMedicationDistributionValue` (`:1664-1684`) persists `distributionSigns = {Amoxicillin}` together with `nonAdministrationSigns = {MedicationAmoxicillin NonAdministrationLackOfStock}`. The "why not" question is only rendered for `Just False` (`:929-934`), so nothing on screen shows the stale reason. Compare `SetDangerSign` (`Update.elm:1028`), which resolves the form via `resolveFormWithDefaults` first.
- **Consumer of the stale reason.** `sendToHCDueToMedicationNonAdministration` (`:2225-2234`) → `Measurement.Utils.resolveMedicationsNonAdministrationReasons` (`Measurement/Utils.elm:1160-1185`), which reads `nonAdministrationSigns` alone and never checks `distributionSigns` → `expectNextStepsTaskFirstEncounter NextStepsSendToHC` (`:2119-2122`) keeps "Refer to HC" required after the medicine was given; `View.elm:1316-1337` routes the next task to SendToHC; `activityCompleted NextSteps` then needs a referral answer before the encounter can end. The progress report is NOT affected (`ProgressReport/View.elm:993-1013` checks `distributionSigns` first).
- **Same-shape sibling in the same file.** `SetMedicationDistributionAdministrationNote` (`Update.elm:845-878`) also works on the raw form: with a fresh model, `Maybe.withDefault (EverySet.singleton updatedValue)` replaces the whole saved set, so for a GI infection changing ORS's reason drops Zinc's saved reason (visible — Zinc's why-not reverts to unanswered and Save disables — so low).
- **Reachability.** First encounter, any medication-bearing diagnosis (`:2096-2101`). Record "No" + lack of stock / allergy, save. Reload or re-login (page models gone). Reopen Medication Distribution, answer "Yes", Save. Same-session re-edits take the correct path — traced both.
- **Impact.** Both sites, CHW and nurse. A contradictory stored record and a spurious mandatory referral. Needs a reload between the two edits, so LOW-MED frequency.
- **Siblings outside this unit — NOT traced.** The identical raw-form handler exists in `Pages/Prenatal/Activity/Update.elm:3491-3494`, `Pages/Prenatal/RecurrentActivity/Update.elm:1098-1101`, `Pages/NCD/Activity/Update.elm:1892-1895`, `Pages/NCD/RecurrentActivity/Update.elm:589-592`, and `Pages/Prenatal/Utils.elm:2836-2853` is a verbatim copy of `updateNonAdministrationSigns`. Their consumers were not followed; whoever builds this should check whether they share the referral consumer or only the contradictory record.
- **Fix shape (guess).** Apply `formUpdateFunc` to `resolveFormWithDefaults .medicationDistribution medicationDistributionFormWithDefault ...`, as the other multi-select handlers in the same `update` already do; same for the administration-note handler. The four sibling handlers are the same one-line change each if their consumers warrant it.
