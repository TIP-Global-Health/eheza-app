### B-522 — Sync download: a soft-deleted duplicate measurement clears the KEPT sibling from the device's in-memory encounter — every single-slot `*Revision` branch empties the slot on `deleted` without checking the uuid, and the nightly dedup always delivers the deletion after the survivor — READY · MED-LOW · tier 3 · CONFIRMED (code + scratch elm-test reproduced by the orchestrator + both copies' vids) · DEPLOYED (all sites; ≈113 affected pairs on ihangane, new ones every dedup night) · R47 unit 3
- **Mechanism.** The ~120 single-slot measurement branches of `handleRevision` share one shape:
  ```elm
  -- client/src/elm/Backend/Update.elm:5841-5855
          DangerSignsRevision uuid data ->
              ( mapPrenatalMeasurements
                  data.encounterId
                  (\measurements ->
                      { measurements
                          | dangerSigns =
                              if data.deleted then
                                  Nothing

                              else
                                  Just ( uuid, data )
                      }
                  )
                  model
              , recalc
              )
  ```
  `uuid` is not consulted on the `deleted` branch, so a deleted revision for *another* node of the same bundle empties the slot the kept node occupies. The family-nutrition helper (`:5281-5286`, keyed by `participantId`) has the same defect; the multi-row helper (`:5264-5269`, `Dict.remove uuid`) is correct, which is why group-session measurements are unaffected. `mapPrenatalMeasurements` (`Backend/Utils.elm:90-97`) only touches an encounter whose cache entry already exists.
- **Why the order always hurts.** The server sends revisions `ORDER BY node.vid ASC` (`HedleyRestfulSync.class.php:136-150`), and `delete-duplicate-measurements.php` (`hedley_admin/scripts`, nightly) keeps the highest-vid node and soft-deletes the rest through `$wrapper->save()` (`:84, :106-107`), which gives the deleted node a brand-new, highest vid. So the device always folds "kept row, then deletion of its sibling" → slot emptied. On `ihangane_post` every deleted-with-live-sibling pair has the deletion vid above the survivor's: prenatal 22/22, acute illness 22/22 (`acute_findings` 8, `symptoms_gi` 8, `acute_illness_vitals` 3, `acute_illness_danger_signs` 2, `treatment_ongoing` 1), nutrition 57, well child 11, NCD 1 (scout; orchestrator re-ran prenatal + acute illness). B-514's pair is one of them: kept 5627713 (`none`, vid 10800758) then deleted 5386418 (`fever`, vid 10812054) → `dangerSigns = Nothing`, neither row.
- **Reachability.** `SyncManager/Update.elm:71-73` → `HandleRevisions RevisionsFromSyncDownload` on every download cycle → `Backend/Update.elm:2543` `processRevisions` → `List.foldl handleRevision`. Precondition: the encounter's measurement cache is `Success` in memory — true once any encounter/activity page, progress report or Patient Record for it was opened in the session; entries are written only at fetch (`:1159/1166`) and never evicted (`Backend/Fetch.elm:591` forgets only on an explicit `forget`). Downloaded revisions run no assessment themselves (`:2050-2058` `downloadedContent` → plain fold).
- **Impact.** For the rest of the session the activity shows as not done and the value is missing from the encounter pages, progress report and Patient Record; any assessment the device re-runs on its next save in that encounter (prenatal CHW danger signs → emergency referral, acute-illness vitals/findings/GI symptoms → diagnosis) runs without the value; a nurse who re-enters the "missing" value POSTs a fresh duplicate, which the next dedup deletes — repeating the cycle on every device that had the encounter loaded. Recovery is a page reload: SyncManager refreshes only on Device/PIN/NotFound/SW pages after a 45 s+ sync (`SyncManager/Update.elm:120-128`, `Utils.elm:53-68`). A device that loads the encounter fresh from IndexedDB is fine (`nodes.js:513-518` `viewMeasurements` filters `deleted`). Both sites (714 deleted rows on ihangane, 539 on vhw); dedup deletions on ihangane 2026: 98 (Apr), 48, 50, 16, 18, 35, 9 (Oct). ⚠ The value feeds assessments → whether the tier-1 diagnosis rule applies is the user's call (B-496 precedent: persistence loss kept at tier 2).
- **Evidence.** Scratch `elm-test` (`scratchpad/ScratchDeletedSiblingTest.elm`, R47 session) driving `updateIndexedDb … (HandleRevisions RevisionsFromSyncDownload …)` with `prenatalMeasurements = {enc → Success {dangerSigns = Just (kept, …)}}`: "deleted revision for ANOTHER uuid leaves the kept row" **fails** (`Nothing`), "server order kept-then-deleted" **fails** (`Nothing`), "same uuid clears the slot" passes. Run by the scout and re-run by the orchestrator in a detached worktree of `origin/develop` 869cf3b3c.
- **Fix shape (first guess).** Clear a single slot only when the stored tuple's uuid equals the revision's (`Maybe.filter (\( id, _ ) -> id /= uuid)`-style, one shared helper for all ~120 sites, and compare the stored uuid in `familyMeasurementActionConsideringDeletedField`); the alternative is to mark the encounter's cache `NotAsked` on any deleted revision so it is re-read through the filtering JS path. Pair with B-514 (the dedup's vid rule) and B-223 (the two branches that lack the `deleted` guard altogether).
