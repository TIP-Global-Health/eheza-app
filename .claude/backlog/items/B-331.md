### B-331 — Backend error reporting: the Sentry SDK that `logs_glitchtip` needs is not in the deployed vendor tree, so every backend error on all four sites has been silently dropped since the 2026-08-23 release — Rollbar was disabled by the same update, and the module's own guard hides the failure — READY · CONFIRMED (module bail, main-tree and deployed vendor listings, live variables all read from this seat) · MED (operators; no patient data) · tier 3 · R29 unit 5 · ⭐ DEPLOYED (all sites)
- **Mechanism.** `server/hedley/modules/custom/logs_glitchtip/logs_glitchtip.module:259-266`: `logs_glitchtip_sentry_post` returns silently when `\Sentry\init` does not exist ("Composer dependencies not (re)built yet"). `logs_glitchtip_is_active()` (`:370-386`) checks only the enabled flag, the DSN and the local-environment heuristic — never that the SDK is loadable — so `hook_boot` still swaps the exception handler and registers the shutdown sender (`:61`), which discards everything. `hedley_update_7048` (`hedley.install:759-768`) disabled `logs_rollbar` and enabled this module.
- **Evidence.** `server/www/sites/default/files/composer/composer.json` requires `"sentry/sdk": "^3.6"` but the `composer.lock` beside it has 0 `sentry` entries and `server/www/sites/all/vendor/` holds only `autoload.php composer paragonie ramsey twilio`; `composer_install` (`server/scripts/helper-functions.sh:203-212`) runs plain `composer install`, which honours the stale lock (the `composer update --lock` step lives only in `.ddev/config.local.yaml.example:42`). Deployed: `server/.pantheon-ihangane` `origin/master` (`6b5922ba3`, 2026-08-25) `sites/all/vendor` = the same five entries, `installed.json` 0 sentry, profile carries `logs_glitchtip`. Live ihangane variables: `logs_glitchtip_enabled=1`, `logs_glitchtip_dsn=https://…@glitchtip.gizra.com/7`, `environment=ihangane`, `severity_level=3` — configured, and nothing can leave. (Self-hosted GlitchTip, so the sync-failure watchdog message carrying the failed item's patient fields — `HedleyRestfulSync.class.php:529-543`, shipped verbatim by `:313 captureMessage` — is not a third-party PHI question; note it when trimming.)
- **Impact.** Since the release the backend error trail is dblog only — the post-deploy Rollbar triage this backlog relied on (`rollbar-postdeploy-triage-2026-07`) has no successor feed. Identical on all four sites.
- **Fix shape (guess).** Rebuild and commit the lock/vendor (`composer update --lock` in `sites/default/files/composer`, then deploy), and make the failure visible — `hook_requirements` reporting the SDK as missing and/or not swapping the exception handler when it is. Verify per site with a listing of `sites/all/vendor/sentry`. See also B-332 (buffer wiped by `drupal_static_reset()`), which survives this fix.
