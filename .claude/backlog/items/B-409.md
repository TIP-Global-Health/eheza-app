### B-409 — The native install/reset/upgrade scripts end with a bootstrap check that is missing its pipe, so a fully successful run reports "Installation failure!" and exits 1 — READY · CONFIRMED (orchestrator read all four sites and the git history) · LOW · tier 4 · R34 unit 4 · dev-only
- **Mechanism.** The identical line appears in four places:
  ```bash
  -- server/install:165
  -- server/scripts/reset:164
  -- server/upgrade:84
  -- server/upgrade:168
  BOOTSTRAP_SUCCESS=`drush status grep "Drupal bootstrap" | grep "Successful"`
  ```
  The intent is plainly `drush status | grep "Drupal bootstrap" | grep "Successful"`. As written, `grep` is passed to `drush status` as its `item` argument — drush's own documented example for that argument (`drush status version` → "Show all status lines that contain version information") says it *filters* status lines, so filtering on `grep` yields nothing, `BOOTSTRAP_SUCCESS` is empty, and the script prints **"Installation failure! > Drupal Bootstrap could not complete successfully"** and exits 1 at the end of a run that fully succeeded.
- **Reachability.** The documented native install path (`cd server && ./install [-d] [-l] [-y]`, CLAUDE.md and README). With `-l`, auto-login is skipped too. Not in CI — CI installs via `ddev restart` — and not in the ddev path, which is why it has survived since the 2017 initial commit (`git log -S` shows the line has never been edited).
- ⚠ **Not run.** The conclusion rests on drush's documented argument semantics, not observation; the alternative is that drush ignores the stray argument and the check works by accident. Either way the line does not read what it claims to. One local `drush status grep "Drupal bootstrap"` settles it.
- **Why it was never caught.** [[B-157]](f) already records that `ci-scripts/test_shell.sh:20` globs `find ci-scripts server/scripts -name '*.sh'` and therefore never checks these extensionless scripts. This is the defect that gap was hiding.
- **Fix shape (guess).** Insert the missing `|` in all four places.
