### B-305 — Well Child immunisation (Burundi): pre-fix DTP-standalone records hold the DTP form's contents and keep blocking the booster from being re-recorded — READY · CONFIRMED (follow-up from the #2178 review; live-counted) · LOW · tier 4 · data task, not code
- **What is wrong.** B-277's fix (PR #2178) is forward-only. Every DTP-standalone save between `b52857711` (2023-10) and the fix reaching production stored the DTP primary form's contents — in the usual case a `VaccinationValue EverySet.empty EverySet.empty AdministeredPreviously`, since the DTP task was untouched that session. The nurse's actual booster entry was never stored anywhere, so **no repair-from-data exists**. While such a record stands, `immunisationTaskCompleted TaskDTPStandalone` (`isJust measurements.dtpStandaloneImmunisation`) reports the task complete, `generateVaccinationProgressForVaccine` keeps the child "behind" on the booster, and a re-edit pre-fills from the bad value.
- **Live scale (vhw.live, 2026-08-30 — vhw is the only Burundi site, and `allVaccineTypes` gates `VaccineDTPStandalone` on `SiteBurundi`).** `well_child_dtp_sa_immunisation`: 2 nodes, both zero `field_administered_doses` rows, both `administered-previously`. `child_scoreboard_dtp_sa_immunisation`: 0 nodes.
- **Remediation shape.** Mark the pre-fix records deleted (`field_deleted`, the same soft-delete the daily duplicate sweeps use — consumers already filter on it): the task reopens at the child's next encounter and the booster gets recorded correctly. Every record created before the fix deploys is corrupt by construction (it holds the other form's contents), so the cutoff is the deploy date, not a value signature. **Re-count on the release day** that ships PR #2178 to vhw.live — more records may accrue until then.
- **Relations.** Root cause [[B-277]] (fixed, PR #2178). Same "delete so it re-asks" shape as the B-122 data repair (#2008).
