### B-108 — 🅿 PARKED by user 2026-07-21 after BOTH candidate fixes were built, high-reviewed, and rejected. ⚠ DO NOT re-pitch "make the migration continue past a bad date" in any form without reading this entry.
**The premise was wrong: the abort is protective.** This is install/CI/demo tooling. Stopping before bad data exists is the SAFE behavior; the only genuinely painful part of the original finding is "row unlogged" (you can't tell which CSV row to fix). Both ways of continuing past the error were traced end-to-end and are WORSE than the abort:
- **Option "skip the row" (prepareRow returning FALSE)** — ❌ REJECTED. contrib `MigrateSource::prepareRow` (`source.inc` ~:407) saves a **STATUS_IGNORED map row** on FALSE. No migration in this module sets `highwaterField` or `track_changes` (grep: 0 hits), so `getNextRow` rule 4 hits `continue` forever → **a corrected CSV is never re-imported on a plain `drush mi`**; recovery needs `--update` or a full rollback. Current behavior is BETTER here (the aborting row leaves no map entry, so a re-run retries it). Also: 17 handlers use `->sourceMigration()` and there are **zero `createStub` implementations**, so `createStubWrapper` returns NULL → dependent measurements/participants save with **empty entity references**. Silent orphaning, quieter and worse than the abort.
- **Option "blank the field + saveMessage"** — ❌ REJECTED, and this one is the dangerous one. `field_expected` (individual_participant, pmtct_participant) and `field_birth_date` are `'required' => 0` in the field instances, so `node_save` accepts the blank; REST then emits `{"value": null}`, but the Elm decoders use **non-nullable `requiredAt [ …, "value" ] decodeYYYYMMDD`** (`Backend/Session/Decoder.elm:17`, `Backend/IndividualEncounterParticipant/Decoder.elm:16`, `Backend/PmtctParticipant/Decoder.elm:16`; only `value2` is nullable). Batches decode with a plain `list` → **one bad record jams the authority download lane for every device on that health center** — the known poison-batch class ([[improvement-1b-poison-batch-not-quick-fix]]). Converts a loud install-time failure into a silent production sync jam.
- Only remaining sane shape (also not taken, user parked instead): keep the throw, add the migration name + `currentSourceKey()` + offending value to the exception so the operator knows which row to fix.

⚠ **SEPARATE LATENT BUG found while working this, still unfixed and worth its own item:** the date regex is **shape-only** (`/^\d\d\d\d-\d\d-\d\d$/`), so **`2020-02-31` and `2019-02-29` pass and `DateTime::createFromFormat('!Y-m-d', …)` silently rolls them into a different, wrong date** (2 March). This is real data corruption that nobody would notice, is independent of the abort question, and is fixed by one `checkdate()` call in the shape check. Not shipped only because B-108 as a whole was parked.
