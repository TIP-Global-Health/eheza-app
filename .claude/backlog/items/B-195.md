### B-195 — Individual encounters: the create-button db-lag race mints DUPLICATE participants in ALL NINE flows, and the app can only ever see one of them — READY · CONFIRMED (mechanism agent-traced in prenatal, structurally verified in all nine; counts live-measured) · **tier 2** (⬆ promoted from 3 by the user, 2026-08-24, on the widened scope) · ongoing · R21 wave B, WIDENED 2026-08-24

## 🎯 2026-08-27 — user direction: fix the causes so the Jenkins scripts can be RETIRED

User: *"the script deals with the consequences of the problem. We want to resolve the problems, so
the script won't be needed."* The two daily scripts have different root causes:

**`delete-duplicates.php` (same-UUID nodes) — largely solved already.** `HedleyRestfulSync::handleChanges()`
is idempotent on UUID: it resolves the nid for the incoming UUID and skips the post if it exists
(traced in [[B-266]]). Standing population 2026-08-27: **2 UUIDs / 4 nodes**. The gap is that the
guarantee is application-level only — `field_data_field_uuid` has **no unique index** on the value
column, so any non-sync write path or race bypasses it. Retirement route: make UUID uniqueness a DB
constraint, run the script once more, stop it. ⚠ **B-266 must land first** — the WhatsApp lane sends
no UUID, so the server mints a fresh one per attempt and a unique constraint would not catch it.

**`delete-duplicate-measurements.php` — the real work, and it is B-195's mechanism one level down.**
`saveMeasurementCmd` (`Backend/Utils.elm:241`) picks create vs update from `savedValueId`:
`Nothing -> sw.post`, `Just id -> sw.patchFull`. `savedValueId` is the page's read of the encounter's
measurement cache, so a stale read POSTs a second measurement instead of PATCHing the first — a
create-or-update decision made from a lagging read. There is **no in-flight guard on saves**:
`SaveMuac` sets `saveMuac = Loading` but never tests it, because `9b8648644` excluded measurement
saves deliberately (*"those pages navigate in the same update as the save, so their window is one
frame rather than a round-trip"*). **197 handlers across 11 `Backend/*/Update.elm` files.**

Two candidate fixes:
1. Guard each save on its existing `Loading` slot — mirrors `9b8648644`; mechanical, 197 sites.
2. Make the second save a PATCH rather than a no-op by feeding the created id back into the cache.
   Better, because it closes the class rather than the symptom. **Blocked today**: `saveMeasurementCmd`
   uses `withoutDecoder` and discards the new id, so the client never learns it.

⛔ **The trigger is NOT yet pinned, and the fix must not be chosen until it is.** The activity pages
dispatch the save and `SetActivePage` in the same update, so the plain double-tap story does not
obviously survive its own frame. The strongest evidence — `nutrition_nutrition`, `nutrition_muac`
and `nutrition_weight` all duplicated in one encounter at one timestamp (2026-08-21 10:27:59) —
points at a whole activity being submitted twice rather than one button tapped twice.
📌 B-195's own history is the warning: its entry proposed a fix that had already shipped two months
earlier, because the mechanism was re-traced but the surrounding code was not re-read.

**Suggested split:** this belongs in its own item — B-195 is participants; this is measurements plus
an explicit goal of retiring a production script. First work item is pinning the trigger, which is a
client-side investigation, not a live query.

## 🛠 2026-08-27 — proposed guard for encounters and measurements

**The view captures the id, so guards that read the message cannot work.** Elm builds the click
handler during `view`: the message is `SaveMuac personId saved value` with `saved` as it was at
render time. If the view is dead, every further tap dispatches the same stale `Nothing`, however
correct the model has become. This rules out both obvious designs:

- ❌ **`Loading`-slot guard** — clears as soon as the local write succeeds, so the next tap POSTs
  again. This is why groups reach six copies rather than two.
- ❌ **Fixing the cache so `savedValueId` populates** — the frozen DOM never re-reads the model. And
  this half is not even broken: `NutritionMuacRevision` (`Backend/Update.elm:6955`) already patches
  `nutritionMeasurements` with `Just (uuid, data)`.

**Guard: enforce the uniqueness invariant in `postNode` (`client/src/js/nodes.js:329`).** It is the
single choke point for every create of every measurement and encounter type, and today mints a fresh
UUID unconditionally (`makeUuid()` → `json.uuid = uuid` → `table.put(json)`). Resolve the business
key first and upsert — PATCH the existing non-deleted row instead of creating:

| record class | business key |
|---|---|
| measurement | `type` + its `*_encounter` field (plus `person` for group-session measurements) |
| encounter | `type` + `individual_participant` + `scheduled_date` |

**These are exactly the keys the two nightly scripts group by**, which is what makes this the change
that lets them be deleted.

**Why here, not in Elm:** one function vs 197 handlers across 11 files; downstream of every write
path (activity pages, `GlobalCaseManagement`, sync replays); and the only place that sees the write
regardless of what a frozen view captured.

**Already indexed** — no schema work for the lookup. `app.js:325` has `[type+individual_participant]`
as a compound index for encounters and every `*_encounter` field indexed for measurements.

**On `isPostInFlight` specifically (user asked 2026-08-27):**
- **Encounters already have it** — all ten per-program creates check it (`Backend/Update.elm:4848,
  4899, 4931, 4963, 4995, 5027, 5059, 5091, 5123, 5224`), from `9b8648644`, live since v1.18.1.
  Keep it; nothing to add.
- **Do NOT add it to the 197 measurement handlers.** `HandleSavedMuac data -> { model | saveMuac =
  data }` resolves the slot as soon as the local IndexedDB write lands — milliseconds — so a frozen
  DOM tapped over seconds sails past it. Six identical MUAC values in one encounter is direct
  evidence the slot cleared between taps. The `postNode` upsert subsumes it entirely: once the write
  is idempotent on the business key, a repeat is harmless whatever its timing. Adding both means 197
  edits the backstop makes redundant.
- The only residual value would be suppressing a genuinely simultaneous double-tap before it reaches
  the SW — saving a redundant write, not preventing a duplicate record. Not worth 197 edits.

**Cheaper interim than any guard:** fix the crash (Rollbar #117) — it removes the trigger on the page
producing most of the duplicates, in one file.

**Confirm before building:**
1. ⚠ **That no measurement bundle legitimately repeats within one encounter.** The script assumes it
   universally (keeps only the newest for every bundle) — strong evidence, but the one assumption
   that would destroy data if wrong.
2. Group sessions need `person` in the key; the script special-cases `session` for this.
3. **Upsert = last write wins.** Right for the frozen-DOM case (the nurse's latest value); confirm
   it is acceptable clinically.
4. Does **not** cover multi-device (the server's UUID guard already does) and does **not** repair
   existing damage.
5. Does not fix the crash itself (Rollbar #117 is worth its own item) — the point of guarding here
   is that duplicates become impossible *while* crashes persist.

Extends to B-195's own participant level with key `(individual_participant, person, encounter_type)`,
but only for the types the product gate confirms are one-per-person.

| `aheza_child`, `family_nutrition_muac_child`, `family_nutrition_photo` | `FamilyNutritionMeasurements` — `Dict PersonId` | one per **child** in the family | encounter + **person** |
| `participant_consent` | `MotherMeasurements.consent` — `Dict ParticipantConsentId`, commented *"we could have multiple consents in the same session"* | one per **form** signed | session + person + **participant_form** |
| `acute_illness_trace_contact` | `FollowUpMeasurements.traceContacts` — `Dict AcuteIllnessTraceContactId` | one per **traced contact** | none — exempt from uniqueness |

`acute_illness_trace_contact` carries `field_acute_illness_encounter` like any measurement, so a key
of type + encounter would collapse a whole contact-tracing list to one contact.

**`delete-duplicate-measurements.php` destroys the family-nutrition case today.** It special-cases
`person` for `session` only, and `hedley_general_get_encounter_types()` includes the `family_*`
types (`hedley_general.module:300`), so it groups a family encounter's per-child rows by encounter
alone and marks all but the newest deleted. On `tip-somalia.live`, encounters 1410 and 2402 each
hold two children; every record of the second child was deleted in one sweep at **2026-05-11
23:26:47**:

| encounter | child kept | child deleted | nodes lost |
|---|---|---|---|
| 1410 | 1403 | 1406 | `aheza_child` 1413, `family_nutrition_muac_child` 1414, `family_nutrition_photo` 1415 |
| 2402 | 2395 | 2398 | `aheza_child` 2405, `family_nutrition_muac_child` 2406 |

Small only because family nutrition is new: 991 encounters on Somalia, none on the other three
sites. It grows with the program. `participant_consent` and `acute_illness_trace_contact` have zero
nodes on all four sites, so those two are latent, not damage.

**For individual encounters the key holds.** Across every duplicate group all time on
`ihangane.live` — including rows already marked deleted — none spans more than one person:

| encounter type | duplicate groups | groups with 2+ persons |
|---|---:|---:|
| nutrition | 34 | 0 |
| prenatal | 14 | 0 |
| acute-illness | 12 | 0 |
| well-child | 7 | 0 |

**What this changes in the design.** The business key is per bundle class, not universal:

- individual-encounter measurements — `type` + its `*_encounter` field
- group-session measurements — `type` + `session` + `person`, and `participant_consent` also
  `participant_form`
- family-nutrition child bundles — `type` + `family_nutrition_encounter` + `person`
- `acute_illness_trace_contact` — no uniqueness at all

The same four rules are what the nightly script needs. Its family-nutrition data loss is live and
independent of this item.

## 2026-08-27 — What gate 1 means for the `postNode` design

**The key is a table, not a rule.** A generic "group by whichever `*_encounter` field the JSON
carries" would collapse a contact-tracing list to one contact and merge two children's family
records. `postNode` needs an explicit per-type spec with the four cases, and it is the same spec
`delete-duplicate-measurements.php` needs.

**The read side already draws two of these lines.** `viewMeasurements` (`nodes.js:485`) sorts a
type's rows DESC by `vid` to take the newest — *except* for `person` and `family_nutrition_encounter`
(`nodes.js:549`), because those repeat per person. The write-side spec should mirror that
distinction, not invent a second vocabulary.

**No Dexie version bump.** `shards` (`app.js:324`, v32) indexes every `*_encounter` field including
`family_nutrition_encounter`, plus `person`. `session` is *not* indexed — but group measurements are
already read by person (`viewMeasurements('person', uuid)`), so the guard can query
`where('person').equals(json.person)` and filter `type` + `session` in JS over a person's handful of
group rows. This matters: a version bump is a lockstep change across `dbVersion` (app.js), `dbVerno`
(sw.js) and `HEDLEY_RESTFUL_CLIENT_SIDE_INDEXEDDB_SCHEMA_VERSION` (hedley_restful.module).

**Liveness is `deleted`, not `status`.** The client filters `item.deleted !== true`
(`nodes.js:424, 490, 628`). A lookup that ignores it would resurrect a row the nurse or the nightly
sweep deleted.

**The upsert branch is small.** `patchNode` (`nodes.js:244`) already does `table.update(uuid, json)`
plus a `PATCH` change row. `postNode` becomes: resolve the key → live sibling found, take the patch
path with its UUID → otherwise mint a UUID as today.

**Photos keep working.** The upload row is registered by `shardChanges.hook('creating')` off
`obj.data.photo` (`nodes.js:1316`), independent of method, so a PATCH change registers the upload
like a POST. `family_nutrition_photo` is the one photo bundle keyed per person.

**Change ordering holds.** Upload reads `shardChanges.where('shard').equals(authorityId)`
(`app.js:1030`), which returns primary-key order within the shard, so a local POST still precedes
the PATCH that follows it for the same UUID.

**Still uncovered:** two devices writing the same measurement (the server's UUID guard), and
`acute_illness_trace_contact`, which is exempt by design.
