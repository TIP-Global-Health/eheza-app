### B-195 — Individual encounters: the create-button db-lag race mints DUPLICATE participants in ALL NINE flows, and the app can only ever see one of them — READY · CONFIRMED (mechanism agent-traced in prenatal, structurally verified in all nine; counts live-measured) · **tier 2** (⬆ promoted from 3 by the user, 2026-08-24, on the widened scope) · ongoing · R21 wave B, WIDENED 2026-08-24
- Anchor: `Pages/Prenatal/Participant/View.elm` `viewActions` — `maybeSessionId` comes from db participants-by-person, which LAGS a just-POSTed create, so each extra tap fires `createNewSessionMsg` again; the client then assumes one active pregnancy (`List.head`) making extras unreachable. Same lag at encounter level (`createNewEncounterMsg`).
- Data: (a) **48 persons hold ≥2 client-active antenatal participants (150 total; reproduced exactly)** — distinct UUIDs, same server-second bursts; person 951194 = 8 pairs in one second (7 empty encounters + 1 real with 28 measurements); person 5560979 = 5 pairs 2026-05-30. (b) **328 (participant, day, type) duplicate-encounter groups = 1,156 encounters, 815 with ZERO measurements**; CHW types dominate.
- Consequence: which duplicate `List.head` picks is arbitrary → fragmented pregnancy records; inflated ANC/visit counts; the husks are EDD-null immortals feeding B-194.
- Fix direction: writer guard — disable/ignore create while the person's session POST is pending; server-side "one open antenatal participant per person" dedup would also stop multi-device copies. Repair shape: mark the 815 husks + 102 surplus participants deleted after picking the survivor.


## ⬆ WIDENED 2026-08-24 — this is a FAMILY, not a prenatal defect (user: *"Widen B-195 to cover all the family case"*)

Prompted by the user's observation while reviewing PR #2142: *"there should not be more than one participant for a person at Well child. It's not like pregnancy where one woman has multiple pregnancies."* That is right, and it exposes the entry's original framing as too narrow — the race is not prenatal-specific, and for the one-per-person flows every duplicate it creates is unambiguously wrong.

**The pattern is structural and present in all nine flows.** Every `Pages/<Flow>/Participant/View.elm` posts `emptyIndividualEncounterParticipant …` for its own `IndividualEncounterType`, and every one resolves the person's existing participant with `List.head` over a db read that LAGS the just-issued POST. Verified present in: AcuteIllness, ChildScoreboard, FamilyNutrition, HIV, NCD, Nutrition, Prenatal, Tuberculosis, WellChild. So the write side can mint a duplicate in any flow, and the read side then hides it.

⭐ **The consequence the original entry understated: a surplus participant is INVISIBLE TO THE APP BUT VISIBLE TO REPORTS.** `List.head` picks one arbitrarily, so the other's encounters can never be reached, edited or concluded from the client — while they sync to every device and are counted by the dashboard and the server reports. That asymmetry is how the well-child instance surfaced (B-208): the dashboard was reading encounters the app cannot show.

⛔ **Do not read the top two rows as damage.** For antenatal and acute-illness a second participant is normal, and only *concurrently active* duplicates count — that is what the original entry's traced figure measured: **48 persons / 150 client-active antenatal participants**. Restricting to `field_date_concluded IS NULL` gives 1,119 antenatal persons, still far above 48, because that column is not the client's activity test. **Trust the traced 48 for antenatal; treat the raw rows for the other types as upper bounds until the per-type semantics are confirmed.**

**⚠ GATE — one product question decides the size of this item: for which of the nine types is a person allowed more than one participant?** Well-child is answered (no). Antenatal and acute-illness are answered (yes). The remaining six are inference, and each "no" converts that row from an upper bound into a defect count.

**Fix shape, now differentiated by class:**
- **One-per-person types** — the guard is unambiguous and belongs on BOTH sides: the client refuses to create when the person already holds a participant of that type, and the server enforces one per (person, type) so multi-device copies cannot slip past a client guard. This is strictly easier than the prenatal case and should be built first, with well-child as the reference implementation.
- **Many-per-person types** — the original writer guard stands: disable or ignore create while the person's POST is in flight, plus a server rule of one *open* participant per person, which needs the client's own activity predicate to define "open".
- **Repair** is per class too: for one-per-person types, merge the surplus participant's encounters onto the survivor and mark it deleted — the app cannot do this itself, since it cannot see the surplus. For prenatal, the original shape stands: 815 husks + 102 surplus participants marked deleted after picking a survivor.

**The entry's primary fix direction is done and deployed.** `Backend/Update.elm:4725` refuses
`PostIndividualEncounterParticipant` while a create for that person is in flight, with a comment
naming this exact defect ("two open pregnancies"):

  episodes"*) guarded this handler — in **v1.18.0, released 2026-07-07**.

**So the item is now repair and read-side, not a writer guard.** What remains:

1. **The accumulated damage is untouched** — all 90 well-child surplus records are still
   `status = 1`. Nothing has ever cleaned them up, and the app cannot: `List.head` hides them.
2. **The read side is unchanged.** Every `Pages/<Flow>/Participant/View.elm` resolves the person's
   participant with `List.head` over `db.individualParticipantsByPerson`, so a surplus participant
   is unreachable from the client while syncing to every device and being counted by reports.
3. **A residual client window, now evidently rare.** `isPostInFlight` blocks on `Loading` only
   (`Backend/Utils.elm:45-53`, deliberate). `HandlePostedIndividualEncounterParticipant`
   (`Update.elm:4739`) caches the new participant into `individualParticipants` (by id) but **not**
   into `individualParticipantsByPerson`, which is what the views read; `Backend/Fetch.elm:452`
   refetches only when that entry is `NotAsked`, so a stale `Success` never refreshes. Between
   participant-success and the auto-created encounter's navigation the page still offers the button
   over a stale read. Fix shape: on success merge the participant into
   `individualParticipantsByPerson` **only when that entry is already `Success`** — writing a
   synthetic singleton into an absent entry would satisfy `Fetch.elm:452`'s membership test and the
   app would then believe it is the person's only participant — otherwise `Dict.remove` it (the
   `Backend/Fetch.elm:576` `forget` shape) to force a refetch.
4. **Server-side uniqueness** for the one-per-person types still has no equivalent, but the live
   numbers make multi-device a small residual rather than the main source.

⚠ **The GATE still decides the repair's size** — for which of the nine types may a person hold more
than one participant. Well-child no; antenatal and acute-illness yes; six unconfirmed.
