### B-544 — Person registration, person edit, Relationship and Receive Stock: the on-entry form resets run only for in-app taps (`SetActivePage`); the Android/browser back button reaches the same pages through `UrlChanged`, which resets nothing but the GPS reading, so a half-filled registration, an abandoned relationship choice or a signed stock form comes back for the next patient — READY · LOW · tier 4 · CONFIRMED (code) · DEPLOYED · R49 unit 2
- **Mechanism.**
  ```elm
  -- client/src/elm/App/Update.elm:1154-1159 (inside SetActivePage)
                  onEntry msgs =
                      if model.activePage == page then
                          []

                      else
                          msgs
  ```
  `onEntry` issues `Pages.Person.Model.ResetCreateForm` / `ResetEditForm` / `ResetPostPersonRequest`, the Relationship `Reset` (`:1172-1198`), the Acute Illness participant `SetViewMode ManageIllnesses` (`:1201-1205`) and `Pages.StockManagement.Model.Reset` (`:1229-1232`). `UrlChanged` (`:1494-1543`) sets `activePage` from the URL and clears only `coordinates` (B-390's fix). All four routes round-trip through `Pages/Router.elm:423-425, 436, 483`, so history back lands on them via `UrlChanged` alone; nothing in `js/app.js` or `lifecycle.js` intercepts `popstate`, and the e2e helpers navigate with `page.goBack()` (`client/e2e/helpers/common.ts:63`).
- **Impact.** Only UNSAVED state returns — every successful save already resets (`HandlePostedPerson`, `HandlePatchedPerson`, `HandlePostedRelationship`, `SaveReceiveStock`). What returns is exactly what the three resets were added to prevent: (a) a half-filled registration shown for the next registrant; (b) an abandoned `relatedBy` that the Relationship view lets win over the stored value (its own comment at `App/Update.elm:1167-1171`); (c) a signed, abandoned receive-stock form savable with today's date. Same defect, the other navigation path.
- **Fix shape (first guess).** Issue the same reset messages from `UrlChanged` when `activePageByUrl url /= model.activePage` — inside `UrlChanged` that comparison is TRUE only for navigation that bypassed `SetActivePage` (back, forward, typed URL), the opposite of the in-app-tap case in memory `setactivepage-sets-page-before-urlchanged`. Or move `onEntry` wholesale into `UrlChanged` under that guard.
