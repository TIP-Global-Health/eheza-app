## Verification lessons (apply during triage)
- ⭐ **`optional` DOES tolerate a present `null` (R26 unit 7).** `NoRedInk/elm-json-decode-pipeline` 1.0.1 wraps the inner decoder in `oneOf [ decoder, Decode.null fallback ]`. The asymmetry is: `required` fails on missing OR null; `optional` yields the fallback on missing OR null and fails only on a present non-null value the inner decoder rejects; `decodeWithFallback` tolerates that too. The earlier line "`optional` tolerates MISSING but never MALFORMED" is right only for non-null malformed values.
- ⛔ **The read-the-DEPLOYED-code rule needs a second clause: the deployed checkout can itself be stale (2026-08-13, B-170).** `server/.pantheon-ihangane`'s WORKING TREE sat at `255815b7f` (2026-05-11) while `origin/master` was `e52219e15` (2026-07-07) — reading the files gave a two-months-old answer that reversed the conclusion (the working tree still declared `field_obstetric_history`; the deployed code had dropped it). **Always read via `git show origin/master:<path>` in that checkout, and check `git log -1 origin/master` first.** Same trap class as B-153, one level deeper.
- 📌 **"A live error is ongoing" does not mean "the code is still wrong" (B-170).** Rollbar occurrences after a deploy can come entirely from devices running PRE-deploy builds — and a coordinated client+server field removal makes stale clients fail on MORE records than before, so the error rate can look untouched (or worse) by a fix that actually worked. Date the fix, date the deploy, then ask which build the erroring devices are on. Pairs with B-168's finding that nothing forces a PWA update.
- ⛔ **A red Elm job on CI is not evidence about the diff until the log is read (2026-08-12/13).** FIVE failures across one day were all the same infrastructure flake: `-- PROBLEM DOWNLOADING PACKAGE --` … `NoResponseDataReceived` fetching `https://github.com/<pkg>/zipball/<ver>/` (hit `elm/browser 1.0.2`, `Gizra/elm-debouncer 2.0.0`, `ccapndave/elm-update-extra 4.0.0`, plus one elm-review config compile with no detail). **Root cause is structural: CI caches nothing** — no `~/.elm` restore — so every Elm job re-downloads every package from GitHub on every run, and any zipball hiccup reddens an unrelated PR. Diagnose with `curl -s https://circleci.com/api/v1.1/project/github/TIP-Global-Health/eheza-app/<job>` → walk `steps[].actions[].output_url` (public project, no token needed; a CircleCI token is NOT available in this environment, so targeted rerun-from-failed is the user's click, not mine).
- 📌 Same run: the e2e jobs' failure surfaced as **"Main.js not found - Elm compilation failed"** in a separate `Verify Elm compiled` step, NOT in `Install and build client` — the dev `gulp build` path prints the download error and still exits 0. B-144 hardened `gulp publish` only; **the dev/e2e build path still swallows Elm failures**, and only that standalone verify step catches it. Candidate item if the class recurs.
